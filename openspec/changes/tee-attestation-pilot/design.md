## Context

`tee-confidential-node` 的三条硬前提已定（D-TEE-1 运营方与密钥释放权分离、D-TEE-2 节点内强制预算与发布审查、
D13 本地校验以 KMS 释放凭据为主）；**Q2（证明链）与 Q4（首个场景）本试点已定稿**
（D-TEE-3 条件式默认、D-TEE-4 首选跨院队列交集），但两条都**不是实测**：Q2 未拿到机器、
Q4 未取得业务方书面确认与假名键方案。它们决定：

- 能不能买到/租到机器；证明服务（DCAP / CSV 证明服务）怎么接；
- KMS 的证明校验逻辑写哪一套；
- 换链时是否要改协议与凭证格式（**理想情况：改实现不动协议**）；
- 第一年的投入能不能换到真实可用的产出（场景价值与工程量）。

仓库现状（试点必须与之一致，不得另起一套）：

- `apps/connector/src/domain/tee.ts` 已定义 `TeeEnclave` 抽象（`seal` / `run`）与 `TeeAttestation`
  （`enclave` / `measurement` / `level: 'software' | 'hardware'` / `isolation: 'none' | 'hardware-enclave'`）；
- `SoftwareSealedCompute` 是**同进程**实现：进程内 AES-GCM 密钥、明文本就在同一进程内存、无远程证明，
  其源码注释已写明「不提供任何隔离或保密性」，`level` 只能是 `software`、`isolation` 恒 `none`；
- 平台的执行环境标注口径见 D9 与 CTL-09：**软件隔离不得表述为 TEE**。

## Goals / Non-Goals

**Goals**
- 用可证伪的证据回答 Q2 与 Q4，产出「默认选项 + 触发条件」，而不是一句偏好。
- 明确划清「哪些事今天就能做（不需要硬件）」与「哪些事没硬件就做不了」，让后续排期不被卡住也不被误导。
- 验证「换硬件实现不必改协议」这一设计假设：证明提供者接口 + 凭证里的 `attestation{quote_digest, measurement, tcb}` 够不够。

**Non-Goals**
- 不实现 C2 全链路、不做 KMS 生产实现、不接真实患者数据、不采购硬件。
- 不追求多厂商证明链的完整适配，只做到「能选、能验、能换」的判定深度。

## Decisions

### P0 SoftwareSealedCompute 的边界（本试点最重要的一条）

**SoftwareSealedCompute 可以替代硬件 TEE 吗？——分两问，答案相反：**

| 问题 | 答案 | 理由 |
|---|---|---|
| 能不能用它**把接口、协议、回执链、闸门逻辑先跑通**（开发与测试床）？ | **可以，而且应该** | `TeeEnclave` 契约本来就是为「换实现不动调用点」设计的；软件实现能在没有硬件时跑通 seal→run→回执的骨架，提前暴露接口缺口 |
| 能不能用它**作为 C2 的上线实现**（真实数据出域到可信空间节点）？ | **绝对不行** | ① **无隔离**：同进程、同一把进程内密钥、明文此前已在该进程内存中，宿主与运维（root / ptrace / core dump）照样可读——这与「运营方看不到内存」的 C2 前提直接冲突；② **无远程证明**：`measurement` 只是源码 SM3，不是硬件签发，持有方**无法区分真假**，同谋的运营方可以替换代码并自签一份「证明」；③ **密钥释放失去判据**：KMS 只能在证明可验证时释放，软件证明不可验证 → 要么不释放（跑不起来），要么释放（C2 的承诺就成了空话）；④ 无侧信道防护、无 TCB 版本概念 |

**因此写死的规则**：
- 软件实现的证明 MUST 恒为 `level=software`、`isolation=none`，并在所有对外材料与元语里如实标注（D9 / CTL-09）；
- **C2 的编译期判定 MUST 要求 `level=hardware`**：软件实现无论怎么声明，都 MUST NOT 被接受为目标节点；
- 本试点用软件实现产出的任何结果，**只能证明「协议与接口够用」，不能作为 C2 的可用性证据**；
- 若长期拿不到硬件，正确路径是 **C1（MPC/安全聚合/PSI，数据不出域）或 C3（聚合出域）**，而不是「软件 TEE 假装 C2」。

### P1 Q2 证明链选型的判据与候选

候选：**海光 CSV**（D9 既定硬件目标）、**Intel TDX**、**AMD SEV-SNP**。判据（每项给出实测或明确来源，缺实测即标「未实测」）：

1. **可获得性**：能否买到整机/租到云上机密机型（试点期就能点亮，而不是等 3 个月）；
2. **信创与国产化**：甲方或医院是否有硬性要求；若「应替尽替」适用，CSV 权重最高；
3. **证明链成熟度**：证明服务与校验库是否可用（DCAP 的 QVL/PCK 体系 vs 厂商证明服务）、
   能否在**离线/受限网络**下校验（院内环境常见约束）；
4. **KMS 集成难度**：quote 解析、度量提取、TCB 版本比对、证明有效期管理的实现成本；
5. **性能与运维**：内存加密与远程证明开销量级、机型内存上限（决定哪些分析能在节点内做）；
6. **换链成本**：该候选的 quote 结构与 TCB 语义能否被现有 `TeeAttestation` 契约吸收（不改协议即换链）。

**判定方式**：按判据打分给出**默认推荐 + 触发条件**（例：无信创要求且试点期要快速点亮 → 云上 TDX/SEV 机型先打通、
CSV 作为生产目标；有信创要求 → CSV 优先，云上机型只作开发床）。结论必须写明「哪几条是实测、哪几条是推断」。

### P2 Q4 场景候选的判据

候选 A：**跨院队列交集**（药物警戒：A 院暴露、B 院结局，需按主体配对）。
候选 B：**亚组与切点重算**（RWS 分层：同一批数据换分层维度/时间切点重算）。

| 判据 | 关注点 |
|---|---|
| 数据可得性 | 合成数据能否构造出真实的研究形态（尤其 A 需要的「同一主体跨院出现」） |
| 是否需可对齐假名键 | A 需要（PSI 或全空间共享盐），这本身是新的合规与工程议题；B 不需要 |

**判定**：**首选 A**，**备选 B**。理由不是 A 更容易，而是**只有 A 能让 C2 的存在成立**——
协议 §4.5.4 的选型原则是「能用 C3 解决的，不得使用 C2」，B 属于「C3 能做但要重跑」，
若拿它当首个场景，等于用 C2 换效率，说不过这次信任面的代价。B 的定位是**第一条演示链路**
（工程量最小、复用度最高），不是论证依据。

**A 的合成数据闭环证据（本仓新增，可复跑）**：

- 用例 `apps/connector/src/mdop/node/c2-session.spec.ts`：两院各封一份**共享假名键**的合成队列
  → 节点内证明 → KMS 释放 → 解封 → 跨院主体配对 → 发布审查 → 只出 C3 → 回执成链 → 销毁；
  断言配对后的队列规模、暴露/结局与率，且 C3 载荷里没有任何主体键；
- 同文件用 `joinableBounds`（`apps/connector/src/mdop/node/pairing.ts`）断言：**只用两院边际计数时
  交集的可行区间宽度 > 0** —— 这是「不可判定」的证明式表述，不是估计；
- 节点内配对算子的语义在 `pairing.ts`；真实部署里它是注册中心签发的 `wasm` 模块
  （协议 §5.1：分析逻辑只许 `wasm`/`oci`，`system` 不许承载 `collab`）。

**A 的硬前置（缺一不启动真实数据）**：① REG 路径 + 医院**书面接受**运营方与 KMS 归属；
② **可对齐假名键**方案定稿（PSI 或共享盐，须医院接受该对齐基础设施）；
③ 配对算子的 wasm 模块入库 + 注册中心签发清单；④ 预算与发布审查在节点内强制（已落地）。
① ②是合规与方案项、③④是代码项；**② 未定之前只跑合成数据**。

### P3 接口替身验证（不需要硬件，本试点即可完成）

在不改变 `TeeEnclave` 语义的前提下，用软件实现跑通骨架：

```
持有方 seal（去标识投影） → 证明提供者（软件实现，level=software 占位）
  → 释放占位（mock KMS，按 D-TEE-1 的判据逐条打桩）
  → 节点内执行（复用算子清单与执行器）→ 发布审查（minCell + 二次抑制）
  → 只出 C3 → 回执链 → 链头锚定
```

**验收点**：把软件实现换成硬件实现时，**除证明提供者与 KMS 客户端之外不需要改任何调用点**；
`attestation{quote_digest, measurement, tcb}` 能容纳三种候选链的信息。任一处要改协议，即为设计缺陷，须回写
`tee-confidential-node` 的 design。

> 2026-09-25 状态：该验收点**已落地为可复跑用例**——骨架在
> `packages/mdop/src/attestation/pilot-harness.spec.ts`（测试替身，不进产物），释放判据本身在
> `packages/mdop/src/attestation/release.ts`（生产代码，KMS 实现只需调用）。其中「TDX 换 CSV」用同一段
> 管线代码跑两遍且结果一致，用测试固化了「换链不动调用点」。
>
> 同日补：**连接器侧**用仓库既有的 `TeeEnclave` / `SoftwareSealedCompute` 再跑一遍
> （`apps/connector/src/mdop/pilot-tee.spec.ts`）——节点内执行那一半走既有抽象（换硬件＝替换它的实现），
> 证明与 KMS 由独立提供者承担。「软件提供者 vs 硬件替身」共用同一段管线的用例，把
> 「换硬件只换两个类」从协议核一路证到连接器侧。**软件提供者过不了 C2 判定**这一点仍有用例钉住。

### P3 已产出的发现（2026-09-25）

**发现 1：跨链的 TCB 版本不可互比，`min_tcb` 不能只写一个字符串。**

三种链的 TCB 表达不在同一体系：CSV 用年月（`2026-06`），TDX / SEV-SNP 用点分数字（`3.1.2` / `1.55`）。
最初按「数值比大小」实现比较，单测立刻暴露问题：合约写 `min_tcb: "2026-06"`、节点报 `tcb: "3.1.2"` 时，
数值比较会判成「3 < 2026 → 过旧」，从而**误拒一条完全合法的证明**。

处理（已落地并有用例固化）：
- `AttestationPolicy.min_tcb` 支持两种写法：单个字符串（只在该链的版本体系内可解释）或按链给出
  （`{ csv: "2026-06", tdx: "3.1.2" }`）；
- TCB 比较**先判版本体系**：体系不同即「不可比」，判定侧按 fail-closed 拒绝，并在错误信息里提示改用按链阈值；
- 该形状扩展向后兼容协议 §9.3 的单字符串示例（已同步补注）。

**发现 2：错误码复用而非新增。** `packages/mdop` 里 `E_ATTESTATION_FAILED` 早已定义却从未被使用
（死词表）。本轮直接**复用它**承载「证明不可信 / 验签不过 / 已过期」，只新增两个真正需要区分的码
（`E_MEASUREMENT_NOT_ALLOWED`、`E_TCB_TOO_OLD`）；原设计稿里的 `E_ATTESTATION_INVALID` 已全量改名，
避免造出一个与既有码同义的近义词。

**发现 3：`AttestationPolicy` 是复用的第二处。** `packages/mdop` 的标签格模块里已有 `AttestationPolicy`
（C2 边校验在用）。本轮没有另立类型，而是扩展它（新增 `allowed_measurements`、放宽 `min_tcb`），
使编译期判定与证明判定共用一份策略形状——否则「合约怎么写」会出现两个真相源。

**发现 4：证明报告缺两个协议已要求、契约里却没有的字段（本轮补齐）。**
协议 §9.4 的文字要求是「报告 MUST 包含代码度量、TCB 版本、一次性公钥，并绑定节点身份」，
但实现期的证明形态只有 `measurement` / `quote_digest` / `tcb` / 两个时间戳：
- **没有一次性公钥** → 数据密钥无处可释（KMS 只能释放到「某个默认密钥」或干脆不释放）；
- **没有身份绑定** → 一份验得通的证明可以被搬到**别的节点**顶上（证明与身份脱钩）。

两者都补进 `AttestationReport`（`ephemeral_public_key` / `node`），并在 `verifyAttestationClaims` 里
对硬件实现**必填**（缺即 `E_ATTESTATION_FAILED`）；`mapVendorQuote` 缺这两项也直接拒——「不得产生半份证明」。
调用方给出期望节点（`node`）时，`verifyAttestationForC2` 还要求两者一致。这是**换链代价验证顺带抓出来的
协议级缺口**，不是实现细节。

**发现 5：KMS 只需要一个客户端接缝，判据必须只有一份。**
本机演练的 `LocalDevKms` 与将来自建/共管 KMS 的差别只在「谁能用、密钥在哪」，
判定逻辑完全共用 `evaluateKeyRelease`（D-TEE-1）——它现在同时被：平台侧编排、节点侧客户端、
以及演练 KMS 调用。释放凭据 `KeyReleaseWarrant` 里带了**封给哪把一次性公钥的指纹**，
因此「拿别次会话的凭据重放」在节点侧就会被判出来（有用例），不必依赖运营方的自觉。

**发现 6：`anchorRecord` 是零调用方的死 schema，「不得伪造交易号」当时只写在平台一处（2026-09-26 补）。**

骨架的验收口径里含「回执链 → 链头锚定」这一步，但实现期**没有任何调用方产出或解析 `anchorRecord`**；
「链不可达进补偿队列」的判据只存在于平台回执链服务里（判的是存证适配器回执的 `0xLOCAL:` 前缀），
协议核里那条 schema 则形同虚设——典型的「规格写了、代码没做」。

处理（已落地并有用例固化）：把这条判据收进协议核，新增
`packages/mdop/src/anchor/anchor.ts#anchorChainHead`——未接链 / 写入失败 / 写入端没给出交易号 →
`status=pending`，且记录里**没有 `tx_id` 键**；写入成功 → `anchored` + 交易号 + 时间戳；
链头形状非法则**直接抛错**（调用方 bug 不得静默降级成 pending）。两处骨架（协议核侧与连接器侧）
都改用它，并在 `tee-confidential-node` 的 orchestration-kernel 规格里补了对应场景（追溯表钉到符号与用例）。

未合并项：平台回执链服务仍走自己的适配器判据（两者都 fail-closed，但合并需要动平台落库形状，另立）。

**发现 7：`collateral` 是**新增的协议字段**——按「换链不改协议」的规则登记，而不是就地扩展（2026-09-26）。**

本变更的规格写着：若接入某条链时发现既有契约装不下，**MUST 记录为设计缺陷并回写设计文档，MUST NOT 直接就地扩展字段**。
`collateral` 正是这样一次扩展，因此在这里登记而不是悄悄加进 `AttestationReport`：
- **为什么必须加**：气隙/受限网络只能预取材料后离线校验，而既有契约（`measurement` / `quote_digest` / `tcb` / 两个时间戳）
  **没有任何字段能表达「材料什么时候取的、什么时候失效」**；不加就只能靠实现内部约定，换链即失效。
- **影响面**：`AttestationReport.collateral`（种类 / 摘要 / 取回时间 / 自身有效期）+ 严格解析；
  `TrustedRootWithCollateral` 要求真实信任根声明「必须随带的种类 + 离线刷新窗口」；
  `createHardwareAttestationVerifier` 产出「验 quote + 判材料时效」的校验器（缺料 / 过期 / 超窗口 / 时间倒挂一律拒）。
- **为什么不塞进既有字段**：`quote_digest` / `tcb` 的语义与「材料时效」不同，混用会让第三方离线核验无从对齐。
- **规格与证据**：本变更 `attestation-provider` 新增「未随带材料」「材料过期或超出离线刷新窗口」两个场景并钉进追溯表；
  D-TEE-3 的残余项 ① 因此从「实现时必须带」收窄为**运维动作**（刷新节奏与厂商根台账）。

**发现 8：一次性公钥从未进入硬件签名覆盖的 `report_data`——按「换链不改协议」的规则登记，而不是就地扩展（2026-09-26/27）。**

本变更的规格写着：若接入某条链时发现既有契约装不下，**MUST 记录为设计缺陷并回写设计文档，MUST NOT 直接就地扩展字段**。
`report_data` 正是这样一次扩展（与发现 7 的 `collateral` 同例），因此在这里登记而不是悄悄加进 `VendorQuote` / `AttestationReport`：
- **为什么必须加**：`ephemeral_public_key` 只被校验「存在且形状合法」，`mapVendorQuote` 原样搬运；`LocalDevKms` 用它算 `ephemeral_key_digest` 并把释放凭据绑上去。但 `VendorQuote` **没有**硬件签名覆盖的绑定字段，全仓 `packages/mdop` 里 `report_data` 零命中——绑定关系**无法表达**。后果：提供者可返回一把**未被 quote 覆盖**的任意公钥，KMS 把 DEK 加密给攻击者指定的密钥，「证明绑定密钥释放」在密码学上是空的。
- **影响面**：`VendorQuote.report_data` + `AttestationReport.report_data`；`mapVendorQuote` 校验「公钥派生值 == `report_data` 中的绑定值」，缺失或不符 → `E_ATTESTATION_FAILED`（**不得产生半份证明**）；`verifyAttestationClaims` 对硬件实现**必填并校验绑定**；`evaluateKeyRelease` 绑定不成立即不释放（fail-closed，**不回退**）。
- **为什么不塞进既有字段**：`quote_digest` 是原生 quote 整段的摘要，语义是「这份 quote 是哪一份」而不是「硬件签了哪把一次性公钥」；`ephemeral_public_key` 是**被**绑定的对象本身，不能自己证明自己进了签名；`collateral` 是信任材料时效；`ephemeral_key_digest` 在释放凭据上、发生在释放**之后**。混用任一字段都会让第三方离线核验无从对齐，也让「未进硬件签名」无法被表达。
- **字段命名与形状（已定，2026-09-27）**：命名就用 `report_data`（SGX / TDX / SEV-SNP 对 64 字节绑定数据的行业统一叫法；本仓 `apps/api/src/privacy/tee/adapters/confidential-compute-attestation.adapter.ts` 所消费的 `AttestationReport` 已用该名）。协议层形状为 `sm3:<64hex>`——对归一化未压缩点 `04‖x‖y` 做 SM3，与 `measurement` / `quote_digest` 同一摘要口径，派生函数与 `publicKeyKid` / `ephemeralKeyDigest` 同源。
- **装填约定与责任边界（2026-09-27 补，原方案缺口）**：协议层只存 `sm3:<64hex>` 摘要。接入真实链时，适配器装填硬件 64 字节 REPORTDATA 的约定 = **前 32 字节放该 SM3 摘要、其余置零**。校验方必须从**原始 quote** 里取出 REPORTDATA，与协议字段 `report.report_data`（厂商 API 或称 `report.data`）比对——「硬件覆盖」这一步由 `TrustedRoot.verifyQuoteDigest(quoteDigest, report)` 的实现承担（它拿得到整个 report，也拿得到原始 quote）。协议核的 `mapVendorQuote` / `assertEphemeralBoundToReportData` 只核「公钥派生值 == `report_data`」，不代替从原始 quote 取出 REPORTDATA 的硬件覆盖核验。
- **规格与证据**：`tee-confidential-node` 的 trusted-space-node 新增三个场景（一次性公钥未进 `report_data` / `report_data` 与公钥派生值不符 / 一次性公钥已绑定进 `report_data`）并钉进追溯表。

### P4 离线/受限网络下的证明校验（**条件化前置**：仅当节点部署在院内；公开资料，2026-09-25 检索）

**适用范围**：本节「离线预取 / 离线刷新窗口」成立的条件是「**可信空间节点部署在院内**」（气隙或受限网络）。
C2 节点的默认形态是运营方/监管侧在**云上**运营（见 `tee-confidential-node/design.md` D1：中立第三方/监管侧优先），
云上节点有外网，collateral 可在线取（TDX 走 PCCS / Intel PCS；CSV 走厂商证明服务 / 自托管 trustee；SEV-SNP 走 AMD KDS）
——此时离线预取与离线刷新窗口**不再是共同前置**。
「院内无外网」只约束**医院连接器**；连接器本来就不需要证明（长轮询出站 + 本地计算，见 DECISIONS D-CN-4；
`tee-node/providers.ts#nodeCapabilityAdvertisement` 里持有方连接器通告的 `tee` 恒为 `null` 是设计意图）。

**若确要院内节点部署**，院内无外网仍是该部署形态的约束，下列离线路径**原样有效**。D-TEE-3 原先写的是「三家都缺可靠公开来源，须先做实」——本轮检索后
可以给出**各家机制不同的可自托管路径**，并把残余未实测项收窄成两条（见本节末）。

| 链 | 院内可自托管的校验路径 | 证据 |
|---|---|---|
| **Intel TDX** | ① **PCCS**（Provisioning Certificate Caching Service）私有化部署：官方设计指南给出缓存填充模式（含一次性填充后内网自服务）；② 校验库可直接吃「预先取回的 collateral」做**完全离线校验**（`dcap-qvl` 自述支持 "Fetch collateral from a PCCS or Intel PCS, **or verify fully offline**"） | Intel 官方 PCCS 设计指南与缓存填充模式文档；`dcap-qvl` crate 文档 `[公开资料]` |
| **海光 CSV** | 走**自托管的证明与参考值服务**：CoCo **trustee** 的 `attestation-service`（含策略引擎）支持 Hygon CSV 证据，**RVPS** 提供参考值（可离线供给）；CNCF 官方博客（2025-10-08）称该方案**已在海光 CSV 平台上生产部署**；OpenAnolis SIG 有 trustee 参考值配置的实践文档（2026-06） | CNCF blog（TPM + CoCo/trustee on Hygon CSV）；openanolis SIG 文档（Attestation-Service + RVPS；CSV 磁盘加密测试过程）`[公开资料]` |
| **AMD SEV-SNP** | VCEK → ASK → ARK 证书链校验：VCEK 从 AMD KDS 取一次后**缓存**，之后离线验签（第三方实现普遍如此：解析 report、缓存 VCEK 与证书链、离线验签） | 多个第三方实现与产品文档（含「对厂商公开的根证书离线验证、不逐轮联网」的表述）`[公开资料，非厂商权威]` |

**残余未实测项（两条；仅当节点部署在院内时，部署前必须先定，不因选哪条链而消失）**：
1. **collateral 新鲜度策略**：CRL / QVL / VCEK 会轮换，TCB 恢复（TDX TCB Recovery）也会改变参考值。
   气隙院内网络拿不到在线更新，必须定「离线刷新窗口 + collateral 过期即拒（fail-closed）」，
   否则会出现「拿半年前的 CRL 放行」这条隐通道。
   - **判据这一半已落地为代码（2026-09-26 补）**：`AttestationReport.collateral`（种类 / 摘要 / 取回时间 /
     自身有效期）进证明契约并走严格解析；`TrustedRootWithCollateral` 把策略（**必须随带的种类** +
     **离线刷新窗口**）做成真实信任根的**必填字段**；`createHardwareAttestationVerifier` 产出
     「验 quote + 判材料时效」的校验器——缺料、已过 `next_update`、超出刷新窗口、时间倒挂一律拒
     （`E_ATTESTATION_FAILED`，KMS 不释放密钥）。用例见 `collateral.spec.ts`、
     `pilot-harness.spec.ts`，规格场景已进本变更的 `attestation-provider` 并钉进追溯表。
   - **剩下的仍是运维动作**：谁多久进一次院内网刷新、厂商根怎么带进来并留档（下面的第 2 条）。
2. **厂商根的获取程序**：三家都需要一次（可带出/带入的）渠道把厂商根与中间证书带进院内，
   过程必须留档（谁在何时带入了哪份根），否则「信任根从哪儿来」说不清。

**对结论的影响**：D-TEE-3 的两条分支（信创→CSV / 无信创→云上 TDX）都不因「离线校验不可行」而失效，
也**不因本节被条件化而改写选型结论**。云上默认形态下 collateral 在线可取，上述两条残余**不是**共同前置；
**仅当节点部署在院内**时：第 1 条残余项的判据已经织进契约
（真实信任根必须声明 collateral 策略，装配不出「只验 quote、不看材料新旧」的校验器），
剩余的是运维节奏与台账；第 2 条（厂商根获取程序）仍是**纯运维/合规动作**，没有任何代码能替它完成。

## Risks / Trade-offs

- **拿不到硬件的风险**：试点期无法点亮真实证明 → 结论降级为「暂定」；缓解：先租云上机密机型打通接口，
  把「生产机型选型」留到有采购条件时；本试点**不会**因此变成「用软件实现顶上」。
- **场景评估偏乐观的风险**：合成数据上能闭环 ≠ 真实数据上能落地；缓解：首选场景必须附前置条件清单
  （合规、医院接受、假名键方案），未满足即不启动。
- **换链成本被低估**：三种链的 TCB 语义差异可能渗进协议；缓解：P3 的验收点就是「不改协议即换链」，把它做成可证伪的。
