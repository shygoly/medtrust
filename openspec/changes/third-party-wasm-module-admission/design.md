## Context

`connector-wasm-sandbox-disproportionality` 已提供「平台签名 Wasm + 合约固定 SM3 + 能力受限沙箱（零导入、超时、内存上限、worker 线程）」的执行机制（`algorithm-sandbox` 能力），但只跑平台自研的单个 AssemblyScript 模块。本变更把这套机制打开给**第三方算法**：药企 / 学术方把自己的分析代码跑到院内数据上，而平台不得因此失去「医院审过、同意跑这一份代码」的核心承诺。

约束：零能力沙箱里传统病毒（syscall / 网络 / 文件 / 进程）本就跑不起来；真实威胁是**借合法输出通道外泄、资源 DoS、结果造假 / 引偏、引擎逃逸、供应链身份**五类。信任根是 SM2 CA（存控制面 SQLite，已挂卷持久化）、合约固定 SM3、输出闸门、已加固的连接器容器（非 root / 只读根 FS / 无外网出口）。

## Goals / Non-Goals

**Goals:**
- 让第三方算法**安全可插拔**：不改连接器代码、不逐院重部署、医院能按哈希审计并同意。
- 把「防外泄 / 防 DoS / 防造假 / 防逃逸 / 供应链」五类威胁**逐层封死**，全程 fail-closed、不回退。
- 支持 Rust 与 AssemblyScript 两种源码语言。

**Non-Goals:**
- **不接受不透明第三方二进制**（不设 Tier C）。
- 不提供真 TEE / 远程证明（`attestationLevel` 仍如实标 software，正交标 `executionIsolation`）。
- 不做通用「跑任意语言源码」的解释器沙箱（见 Decisions）。

## Decisions

### D1. 只两层（A / B），源码-only；用「平台复现构建」作为排除机制
准入只设 Tier A（平台自研源码）与 Tier B（第三方源码、平台构建）。合约固定的 SM3 **必须由平台从提交源码复现产出**——于是不透明二进制**结构性地无法入册**（复现不出 SM3 就签不了、固定不了），而不是靠一条「政策上拒绝」的软规则。
- 备选：接受二进制 + 黑盒静态 / 动态分析（Tier C）。**否决**：黑盒测试永远不完备（测试数据上乖、真实数据上作恶），且「同意跑一个看不透的东西」与知情同意自相矛盾——花最多安全力气换最少保证。

### D2. 语言：Rust + AssemblyScript（编译到 Wasm），不上解释器 / DSL
两者都是编译到小而静态、确定性好的 Wasm，SM3 = 算法本身，零能力实例化是结构性的、好审计。
- 备选：把 Python/Lisp 解释器编译进 Wasm、喂源码（「不用编译」）。**否决**：并没省掉编译，只是把一个大解释器搬进「被签名 + 被合约固定 + 被审计」的包里，放大审计面与攻击面、削弱确定性。若将来确需 Python 体验，另立变更走「受限确定性 DSL（Starlark / 小 Lisp）+ 解释器与源码双哈希」，不在本变更。

### D3. 输出通道是防外泄的主战场
零能力沙箱里数据出去的唯一通道就是合法输出，火力集中于此：宿主只喂**最小整数列投影**（原始标识不进模块）→ 输出走**窄低熵 schema**（整数计数、限定值域）→ **行序不变性差分**抓「用顺序偷藏」→ 最后仍过**输出闸门**（小格<5 抑制、行级拦截）。其余四类威胁分别交给静态白名单、资源上限、OS 兜底、存证吊销。

### D4. 引擎优先 Wasmtime（第三方档），保留 V8 兜底
Tier B 跑的是不可信代码，用 Wasmtime 的 **fuel（指令预算）+ epoch 中断**做确定的资源上限，比裸 V8 的 watchdog 更硬、更适合。Tier A 可沿用基线的 V8。引擎 pin 版本并跟 CVE 更新。

### D5. OS 层纵深兜底，复用现有容器加固
沙箱 worker 再罩一层 OS 限制（seccomp 断 syscall、无网络命名空间、只读 FS、cgroup 限 CPU / 内存），让「引擎逃逸」撞第二堵墙。直接扩现有连接器加固（非 root / 只读根 FS / 无外网），不新起信任面。

### D6. 保密审查通道解 IP，不牺牲可审计
第三方可 NDA 交源码，平台审 + 构建，对医院只公开 `SM3 + 审查背书`。「要源码」不等于「要开源」；真到「连 NDA 都不给源码」的，排除在外——对一个卖「可信」的平台是加分。

### D7. 影子发布抓「测试规避」
新模块先在一家医院真实数据上「只算不发结果」，与参考比对、DPO 可查；干净后 canary → 全量。堵住「在合成测试集上乖、在真实数据上变脸」。

## Risks / Trade-offs

- **源码人审不完备** → 不单靠人审：复现构建 + 沙箱动态测试（一致性 / 确定性 / 资源 / 防外泄 / 模糊）+ 影子 + 运行时兜底，五层纵深。
- **复现构建难做** → 锁工具链、断网、hermetic；两独立构建器对拍；不可复现即拒（宁拒不放）。
- **Wasmtime 引入原生依赖 / 运维成本** → 分档（Tier A 留 V8、Tier B 用 Wasmtime）；引擎 pin + 跟 CVE。
- **第三方 IP 顾虑挡住参与** → 保密审查通道；真拒绝给源码的挡在外面（可接受、甚至可取的过滤）。
- **OS 兜底与现有加固 / ali29 单机冲突** → 复用现有加固增量加 seccomp/cgroup；ali29 上 seccomp profile 与 hardening overlay 一并落地（重建连接器须带 `-f compose.hardening.yaml`）。
- **确定性被非确定特性破坏** → 特性白名单禁 threads / 共享内存；浮点走 IEEE-754 确定路径；跨运行时对拍。

## Migration Plan

- **前置**：`connector-wasm-sandbox-disproportionality` 先归档，`algorithm-sandbox` 成基线。
- **分步落地**：① Rust 工具链 + 复现构建（闸 2）② 静态白名单校验（闸 1）③ 沙箱动态测试闸（闸 3，含防外泄）④ 影子发布（闸 4）⑤ 运行时兜底：Wasmtime + OS 限制 + 吊销（闸 5）。
- **回滚**：第三方准入是纯增量——无固定模块的合约仍走内置 TS 路径（`executionIsolation: none`）；可整体关闭第三方准入而不影响既有链路。
- **ali29**：连接器镜像 + seccomp profile；控制面库挂卷已解决（重建 api 须带 hardening overlay）。

## Open Questions

- 每种分析类型的**独立参考实现**从哪来（一致性闸的基准）？先覆盖已有的 L1.5 / L2，还是每类都要一个？
- ~~V8 上的**指令预算等价物**（watchdog + interrupt）是否够硬，还是 Tier B **强制** Wasmtime？~~
  **已决（2026-09-20）**：不强制，且 **D4「引擎优先 Wasmtime」按决策不做**。fuel 买的是「确定性资源裁决」，
  而裁决不确定的唯一后果是偶发任务失败（fail-closed 方向），不产生错误结果；算法正确性由闸 2（可复现源码 +
  人审）与闸 3.1（独立参考实现逐字段对拍）保证。资源上限本身保留（超时 terminate + 内存上限）。
  Wasmtime 的另一项收益「进程隔离防引擎逃逸」仍留在 P-CTL-5。登记见 D-CN-5 落地补注 / CTL-24 note。
- **窄数据 API** 的确切边界：除有上限内存外，是否给一个只读游标式的数据读取接口，还是全部预投影一次性喂入？
- **吊销状态分发**：连接器如何及时拿到吊销（长轮询下发吊销名单？合约撤固定即失效？两者叠加？）。
- 影子**时长 / canary 家数**的具体阈值，谁来判定「干净」（平台 + 首院 DPO 双签？）。
