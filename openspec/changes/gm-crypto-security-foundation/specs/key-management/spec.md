# Key Management Specification

## ADDED Requirements

### Requirement: Vault Connection

The system shall establish secure connection to HashiCorp Vault for key management operations.

#### Scenario: Initialize Vault client on module startup

- **WHEN** the NestJS application starts
- **THEN** the Vault service initializes a client connection
- **AND** the client uses VAULT_ADDR from environment configuration
- **AND** the client authenticates using VAULT_TOKEN
- **AND** the connection is validated before accepting requests

#### Scenario: Vault connection fails

- **WHEN** Vault is unreachable during initialization
- **THEN** the system logs a connection error
- **AND** the application startup fails with a descriptive error message
- **AND** the error indicates Vault connectivity issue

---

### Requirement: Data Encryption Key Retrieval

The system shall retrieve data encryption keys (DEK) from Vault's KV secrets engine.

#### Scenario: Retrieve encryption key by ID

- **WHEN** a service requests a data encryption key using keyId
- **THEN** the system reads from Vault path `secret/data/medical/{keyId}`
- **AND** the system returns the key value from the response
- **AND** the key is a hex-encoded string suitable for SM4 encryption

#### Scenario: Key does not exist

- **WHEN** a requested keyId does not exist in Vault
- **THEN** the system throws a "Key not found" error
- **AND** the error includes the keyId that was requested
- **AND** the operation fails without exposing other key information

---

### Requirement: Dynamic Database Credentials

The system shall retrieve short-lived database credentials from Vault's database secrets engine.

#### Scenario: Request database credentials

- **WHEN** the application requests database credentials
- **THEN** the system reads from Vault path `database/creds/medical-app`
- **AND** the system returns a username and password
- **AND** the credentials are dynamically generated by Vault
- **AND** the credentials have a limited TTL (time-to-live)

#### Scenario: Credentials expire and renew

- **WHEN** database credentials approach expiration
- **THEN** the system requests new credentials from Vault
- **AND** the database connection pool is updated with new credentials
- **AND** existing connections are gracefully drained and replaced

---

### Requirement: Key Encryption with Transit Engine

The system shall use Vault's Transit secrets engine to encrypt data encryption keys (envelope encryption at rest).

#### Scenario: Encrypt DEK with KEK

- **WHEN** a data encryption key needs to be stored encrypted
- **THEN** the system calls Vault Transit encrypt endpoint
- **AND** the system provides the plaintext DEK as base64-encoded input
- **AND** Vault encrypts the DEK using a key encryption key (KEK)
- **AND** the system receives and stores the encrypted DEK ciphertext

#### Scenario: Decrypt DEK with KEK

- **WHEN** an encrypted DEK needs to be used
- **THEN** the system calls Vault Transit decrypt endpoint
- **AND** the system provides the ciphertext
- **AND** Vault decrypts using the KEK
- **AND** the system receives the plaintext DEK for use

---

### Requirement: Key Caching

The system shall cache frequently-used encryption keys in memory to reduce Vault API calls.

#### Scenario: Cache encryption key on first retrieval

- **WHEN** an encryption key is retrieved from Vault
- **THEN** the system caches the key in memory
- **AND** the cache entry has a TTL of 5 minutes
- **AND** subsequent requests within TTL use the cached key

#### Scenario: Cache expires and refreshes

- **WHEN** a cached key's TTL expires
- **THEN** the next request fetches a fresh key from Vault
- **AND** the cache is updated with the new key and TTL
- **AND** the system logs cache refresh events for monitoring

#### Scenario: Cache invalidation on key rotation

- **WHEN** a key rotation event is detected
- **THEN** the system immediately invalidates the cached key
- **AND** the next request fetches the new key version from Vault
- **AND** old cached keys are not used after rotation

---

### Requirement: Audit Logging

The system shall log all key access operations for security audit trails.

#### Scenario: Log key retrieval

- **WHEN** an encryption key is retrieved from Vault
- **THEN** the system logs the keyId, timestamp, and requesting service
- **AND** the log does not include the actual key value
- **AND** the log is sent to the audit logging system

#### Scenario: Log failed key access

- **WHEN** a key retrieval fails (not found, permission denied)
- **THEN** the system logs the failure with keyId and error reason
- **AND** the log includes the requesting service for security monitoring
- **AND** repeated failures trigger security alerts

---

### Requirement: Key Rotation Support

The system shall support key rotation without application downtime.

#### Scenario: Rotate encryption key

- **WHEN** a new version of an encryption key is created in Vault
- **THEN** the system can decrypt data encrypted with old key versions
- **AND** the system encrypts new data with the latest key version
- **AND** Vault automatically handles key versioning

#### Scenario: Re-encrypt data after rotation

- **WHEN** a key rotation is completed
- **THEN** the system provides a utility to re-encrypt existing data
- **AND** the utility reads data encrypted with old key
- **AND** the utility re-encrypts with new key version
- **AND** the process can run incrementally without locking tables

---

## Implementation Notes

- Use `node-vault` npm package for Vault client
- Store Vault configuration in environment variables (VAULT_ADDR, VAULT_TOKEN)
- Consider using Vault AppRole authentication for production instead of static tokens
- Implement connection pooling and retry logic for Vault API calls
- Cache keys in-memory using a Map with TTL, or use a library like `node-cache`
- Monitor Vault health endpoint and implement circuit breaker pattern
- Document key naming conventions (e.g., `patient-{field}-key`)
- Set up Vault policies to restrict key access by service
