# 设计：空间 · 能力包 · 分发边界（三轴解耦）

> 本文件是 `space-and-pack-decoupling` 的**决策记录**。`D-SPD-1` … `D-SPD-19` 于交付日经用户逐条裁决，
> 落地前不得静默变更；与八件套元语冲突时以元语为准，并停下说明。
> 关联：[`ARCHITECTURE.md`](../../../ARCHITECTURE.md) · [`DOMAIN.md`](../../../DOMAIN.md) · [`DECISIONS.md`](../../../DECISIONS.md) · [`DESIGN.md`](../../../DESIGN.md) · [`TRUST.md`](../../../TRUST.md)

## Context

需求把三件事压在了一起：**多领域可信空间**、**用户加入多个空间**、**基座开源 + 插件式（部分不开源）**。现有一份多空间分析（DOC1）与一份基座解耦方案（DOC2）各只覆盖一条轴，且合起来有三处硬冲突（见 `proposal.md` 的 Why）。

**关键认识**：这三件事是三条**彼此正交**的轴。把任意两条合并，都会产生"看起来对、做下去打架"的方案：

| 轴 | 单元 | 谁决定 | 载体 |
|---|---|---|---|
| **A 空间**（隔离与治理） | 每个空间 | `operator` | `cp_space` + 每空间 CA 根 |
| **B 能力包**（领域逻辑） | 每个领域 | 平台 / 生态 | SPI + 打包插件 |
| **C 分发边界**（开源 / 闭源） | 每个可装载单元 | 开源策略 | T0 / T1 / T2 三层 |

**已有强资产（必须保住）**：双平面（control-plane / connector-local）；`cp_ca_keypair.spaceId` 为主键的按空间 CA 根（最难的密码学隔离已做对）；`D-CN-2` / `D-CN-5` 的签名 Wasm + 零能力沙箱 + 五道闸 + 可吊销 + NDA 保密审查通道。**最后一项正是"部分插件不开源"的现成载体。**

## Goals / Non-Goals

### Goals
- 三条轴一次定死，消除互相打架。
- 让"用户加入多个空间"与"行业隔离"在**同一套空间模型**里成立。
- 基座可开源、插件可闭源，且**闭源不削弱可验证性**。
- 隔离强度可随合规 / 部署演进，**不必现在决定电力是否独立部署**。

### Non-Goals
- 不做用户自建空间（`operator` 建域）。
- 不做开放注册（邀请 + 审批）。
- 不做"每空间一套物理库"（隔离强度是部署选择，不是数据模型）。
- 不做用户级明暗主题切换（`DESIGN.md` 目前只有暗色）。
- 不在本变更内实现全部行业包与估值引擎（本变更是**契约与抽缝**，包实现归后续变更）。

## Decisions

### D-SPD-1：三条轴正交，不得互相顶替

**结论**：空间（隔离与治理）、能力包（领域逻辑）、分发边界（开源 / 闭源）三者正交。**行业不是空间的字段**，而是空间**绑定的包的集合**；同一行业允许多个空间（上海医疗空间 / 北京医疗空间）。

**理由**：DOC1 §7 已指出"空间与行业包正交"；若把行业做成空间的 1:1 属性，就无法表达"同行业多空间"，也无法表达"一个空间绑定多个兼容包"。

### D-SPD-2：空间 = 治理与行业边界

**结论**：空间承载**三件合约给不了的东西**：① 独立信任根（CA 根 / 密钥）② 独立策略与代码集（pack 绑定 + 合规 profile + 出域模板 + 准入白名单）③ 独立成员与可见性域。

**理由**：业务场景的**访问控制**确实由合约承担（`D-DC-2` 已明确"闸门参数属合约"），不需要空间隔离。但合约管"能不能读数据"，**不管"知不知道数据存在、谁在参与"**。行业隔离的实质是 ①②③ 的打包。

**边界**：空间是**逻辑**隔离边界，不是物理库边界——给 control-plane 表加 `spaceId` 不违 `D7`（`spaceId` 是元数据，不是行级医疗数据）。

### D-SPD-3：场景下移为「协作」

**结论**：业务场景（药物注册 / 疫苗不良反应监测 / 真实世界研究）**不建空间**。访问控制由合约承担；聚合视图与**可见性作用域**由轻量「协作」承担。协作**不承载隔离、无独立 CA、无独立策略集**。

**理由**：合约不覆盖**元数据泄漏**——两家竞争药企在同一空间做 RWS，合约不阻止它们互相看见对方的目录与成员。协作的作用域正是补这一块，而不是再造一层隔离。

### D-SPD-4：隔离维度是设计决定，隔离强度是部署选择

**结论**：隔离强度分档——**逻辑（行级 `spaceId` + `Guard`）→ 密钥级（每空间独立 CA / 密钥，强制不复用）→ 库级 → 实例级 → 基础设施级**。同一套空间模型支撑全部强度；跨实例用联邦（`cp_federation_trust` + `cp_remote_catalog`）互联。

**理由**：**不要把部署假设烧进代码**。只要每张域内表都带 `spaceId`、跨空间无共享状态，"把一个空间迁到独立实例"就是机械操作。反之若现在就写死"行业 = 独立实例"，以后想在同实例跑两个行业就得重写。

**推论**：默认逻辑隔离（含密钥级）；谁需要强隔离就把某个空间整体迁到独立实例。

### D-SPD-5：闭源准入公理

**结论**：一个环节可以闭源，**当且仅当**它 (a) 不接触原始数据 (b) 不决定数据放行与否 (c) 其输出可被开源侧独立复核 / 对拍。**违反任一条 → 必须开源或至少可审。**

**理由**：内核开源后，闭源**挡不住**用户绕开（写个开源实现替换即可）。因此"保证不发生"的属性只能落在开源机制里；闭源的价值仅在保护 IP。

### D-SPD-6：三层（T0 / T1 / T2）与六根缝归属

**结论**：

| 层 | 内容 | 开源要求 |
|---|---|---|
| **T0 内核机制** | 沙箱 · 闸门引擎 · 签名 / 吊销 · URN / 合约 · 存证 · 空间上下文 · 准入引擎 | **必开源** |
| **T1 可审声明式** | 出域模板 · 合规 profile · 去标识代码 · 数据源投影语义 · 术语编码声明 | **必开源**（可数据化则数据化） |
| **T2 可闭源打包** | 域内算子（Wasm / OCI）· 估值引擎 / `MeteringProvider` · 局部数据源适配实现 | 可闭源 |

六根缝归属（按 `D-SPD-5` 公理，非拍脑袋）：

| 缝 | 层 | 判定理由 |
|---|---|---|
| S1 数据源适配 | T1 接口 + T2 实现 | **投影 / 下推语义开源**（决定谁能看到哪些列）；实现可在数据持有方本地闭源（持有方自担） |
| S2 算子包 | T2 | 已在零能力沙箱 + 五道闸内，闭源安全 |
| S3 出域策略 | **T1 强制开源** | 决定放行 + 泄漏关键 → 闭源等于无法验证它不泄漏 |
| S4 计量口径 / 估值 | T2 | 聚合后、不碰原始、可对拍 → 符合公理 |
| S5 合规 profile | **T1 强制开源** | 监管与客户必须能审 |
| S6 术语与去标识 | **去标识代码 T1 强制开源**；词典为数据可许可 | 处理原始标识符 → 必须能证明真脱敏 |

### D-SPD-7：估值引擎不开源

**结论**：估值引擎**移出 `space-kernel/value`**，作为 T2 插件经开放的 `MeteringProvider` 接入。内核只提供 **开放 SPI + 开放兜底口径**。

- 无闭源插件时走兜底口径，并**如实标注**（沿用 `attestationLevel` 的如实标注精神），**禁止静默假装**已用算法口径。
- 可复核性为必需：结果记录 `meter id / version / digest`，并强制与兜底口径**对拍**。
- 估值过程与结果仍须过出域闸并上链（DOC2 §7 的工程约束不变）。
- `settlement` 公式留在内核（通用），`contribution` 口径由 `MeteringProvider` 供给——当前仓库**没有**该接口，仅有 [`settlement.service.ts`](../../../apps/api/src/runtime/settlement/settlement.service.ts) 里裸的 `contribution` 入参，本变更补齐。

### D-SPD-8：闭源插件只接受 Wasm / OCI

**结论**：闭源插件（含估值引擎）**只接受 Wasm / OCI 形态**，沿用 `D-CN-2` / `D-CN-5`：源码-only 复现构建 + 平台 SM2 签名 + 零能力沙箱 + 五道闸 + 可吊销 + NDA 保密审查通道（"要源码不等于要开源"）。

**理由**：进程内 TS 私有包三选一都不可行——发可读 JS（等于开源）、混淆（弱）、或出进程。

**强制手段**：由于 **保密只保护 IP、不保证行为**（`D-SPD-5`），"必须用官方估值引擎"只能靠 ① 许可（法律）② 存证（技术）③ 合约条款（业务），**不得依赖代码保密**。

### D-SPD-9：权威三层（内核 / 包 / 空间）

**结论**：

- **内核**拥有机制：沙箱、闸门、签名、吊销、`system` 算子类别；
- **包**拥有领域算子与合规章；
- **空间**只拥有数据产品、合约、成员、启用集、品牌——**MUST NOT 自审算子**。

**理由**：用户空间不得自建准入路径，否则合规闸被租户绕过；同时 `D-MDOP-5` 的 `system` 算子边界（只许 source / declassify / merge 三类）属机制层，不得由空间或包扩张（扩张须显式立决策）。

### D-SPD-10：装配 = 部署白名单 + 空间运行期启用集

**结论**：`SPACE_PACKS` 从**启动 env**（一进程一行业）降为**部署白名单**（本部署被授权跑哪些包）；真正的绑定是**空间运行期启用集** `space.enabledPacks`。包注册表必须**运行期可变**。**连接器 = 多空间 × 多包并存。**

**理由**：这是 DOC2 与"多领域多空间"最直接的冲突点。一个进程一行业，无法承载用户自建 / 多领域空间；且一家医院可能加入不同行业的空间。

### D-SPD-11：成员两层，机构为权威、人为派生

**结论**：新增 `cp_space_member(spaceId, subjectType, subjectId, role, status, joinedAt, ...)`。

- **机构 ↔ 空间**（权威）：受邀 / 审批的对象是机构；资质审核挂在机构层；域内角色（`org-admin` / `data-provider` / `data-consumer` / `auditor`）落在成员表；数据产品、合约、密钥的权属主体是机构。
- **人 ↔ 空间**（派生 + 例外）：由机构入域**派生**；支持**个人直接受邀**（跨机构协作）。

`User.participant_id` 单值改为**多空间成员资格集合**。

**理由**：邀请在业务上通常针对机构（一家医院加入空间），而"切换空间"操作的是人。DOC1 §L2 已点出这个建模分歧。

### D-SPD-12：`cp_participant` 保持全局，不采用 `(spaceId, org)` 联合唯一

**结论**：机构身份唯一化——`cp_participant.org` **保持全局唯一**；跨域关系放成员表；域内角色移出 `cp_participant`。

**理由**：DOC1 硬阻碍 #1 假设"参与者按空间复制"，但那会**分裂机构身份**、并使资质与配额在每个域重复一份。正确模型是"全局机构 + 按空间成员关系"。

**推论（缩小改造面）**：只有**域内活动表**需要 `spaceId`——合约、结算、MDOP、证书、CA、联邦信任、数据产品、审计；**身份 / 主体表保持全局**。DOC1 的"28 张表全加 `space_id`"据此收敛。

### D-SPD-13：`Tenant` 与 `cp_participant` 合一

**结论**：`cp_participant` 为**机构身份的权威**；`Tenant` 降级为参与方的**商业属性**（资质 / 配额 / 订阅 / 财务）1:1 扩展，**不再有第二套机构实体**。

**理由**：现状 `Tenant`（主库）与 `cp_participant`（控制面）都是机构，是同一现实对象的两半；[`tenant.service.ts`](../../../apps/api/src/tenant/tenant.service.ts) 目前是内存 `Map` 空壳，合并成本低。

### D-SPD-14：入域 = 邀请 + 审批（不开放）

**结论**：两条入域路径、同一张成员表、同一状态机 `invited → pending → active → suspended | rejected`。

- **邀请**：一次性 + 有期 + **不可枚举** token + 绑定被邀主体（机构 USCC 或用户）；
- **审批**：机构提交加入申请 → `operator` 审批；资质腿复用 `cp_org_certification_application`；
- **安全红线**：token 不可枚举 + 过期即废；角色授予需授权并留痕；入域 / 邀请操作进审计链。

### D-SPD-15：空间品牌与主题

**结论**：级联 = **平台默认**（`DESIGN.md` Vital Ink）→ **实例品牌**（部署配置兜底 + admin 设置页）→ **空间主题**（`cp_space.branding`）。

- **可覆盖（品牌层）**：logo、favicon、系统标题、短名、主色、强调色。
- **不可覆盖**：`DESIGN.md` §2「状态 → 语义色」唯一映射（§2 自注"★ 最高价值"）、功能层（布局 / 间距 / 字号 / 组件）、能力层（有哪些页面）。
- **术语 ≠ 主题**：术语由 **pack 术语表**提供并受守护（`P-CTL-8` C2 表述红线、[`check-tee-claims.mjs`](../../../scripts/check-tee-claims.mjs) denylist）；空间**只能选择，不能自造**。
- **联邦边界**：本地空间可注入全量主题；**远端空间只展示名称 + logo，不注入 CSS**（防跨实例样式注入 / 追踪 / 钓鱼）。
- **安全**：logo 服务端 sanitize（禁 SVG 脚本）或转 PNG；限 MIME / 尺寸 / 体积；**禁外链**；走对象存储 key（沿用 [`control-plane/index.ts`](../../../packages/database/src/control-plane/index.ts) 的机构 `logoKey` 先例）；**只接受结构化 token 值**（禁任意 CSS）；主色需过对比度校验。
- **治理**：[`DESIGN.md`](../../../DESIGN.md) §1.1 由"唯一主题"改为"默认主题 + 受约束覆盖层"（**动 UI 元语，须登记决策**）；标题不得硬编码（当前 [`layout.tsx`](../../../apps/web/src/app/layout.tsx) 写死 "MedTrust - 医疗可信数据空间"）。

### D-SPD-16：权威术语 = 空间 / 平面

**结论**：规范词 = **空间（Space）** 与 **平面（plane）**。「信任域」退回 [`DOMAIN.md:919`](../../../DOMAIN.md) 的描述性措辞，**不得**进入规则名、字段名、守护判据、覆盖矩阵列名。

**理由**：`DOMAIN.md` 已用"信任域"描述**平面**，而 DOC1 的第一条硬不变量是「**平面 ≠ 空间**」；若两者都叫信任域，`D7`（一表一平面）与空间隔离规则在文字与机检层面**不可分辨**。另：可信数据空间的成立前提是参与方**不互信**，把空间叫"信任域"在语义上恰好说反。

### D-SPD-17：准入空间化

**结论**：`cp_module_admission` / `cp_module_revocation` / `cp_connector_registry` 增加 `spaceId`；范围 = `global`（平台签名，全空间可用）| `per-space`（第三方，仅该空间）。跨空间越权准入为负例。

**理由**：第三方算子在一个空间准入不应自动在另一个空间可跑；用户空间不得自审算子（`D-SPD-9`）。

### D-SPD-18：基座纯度守护

**结论**：新增 `scripts/check-kernel-purity.mjs`：① 基座目录不得出现行业词（denylist）② 依赖方向单向（基座 MUST NOT 引用行业包；行业包 MUST NOT 互相 import）③ 双行业包装配测试。P0 先以**候选目录基线**报红（当前布局尚无 `space-kernel` / `industries`），再逐文件核对。

**注意**：denylist 含 `meter` / `CDM` / `CIM` 等易误伤词（`meter` 会命中 `parameter`），实现须按**词元 / camelCase 边界**匹配，不能裸子串。

### D-SPD-19：开源治理与许可卫生

**结论**：全仓**无 LICENSE 文件**（仅 `apps/api/package.json` 有 `license` 字段）→ 明确内核许可 + SPDX 头；查 `vendor/ai-factory` 许可；清 demo 数据与真实机构名；核对词典许可（SNOMED CT 等，见 [`plan-templates.ts`](../../../apps/api/src/mdop/plan-templates.ts) / [`observation.transform.ts`](../../../apps/api/src/fhir/transforms/observation.transform.ts)）；建**三方 conformance kit**（包作者无需内核私有件即可自检）。

## Risks / Trade-offs

| # | 风险 | 对策 |
|---|---|---|
| R1 | **假解耦**：目录分了，接口签名仍带行业词（DOC2 已见 `query_omop` 类先例） | `check-kernel-purity` + 命名评审 + 双行业包装配测试 |
| R2 | **假隔离**：加了 `spaceId` 但查询漏过滤 → 静默跨空间泄漏 | 仓储层**强制注入** + 越权负例测试；不靠逐个 service 自觉 |
| R3 | **跨空间密钥复用** | `cp_ca_keypair` 已按空间；把"密钥不复用"写成不变量 + 负例 |
| R4 | **闭源插件被开源实现替换** | 接受之（`D-SPD-5`）；靠许可 + 存证 + 合约，不靠保密 |
| R5 | **元语跨册漂移**：分册后覆盖矩阵"一表一平面"被跨册破坏 | 分册规则**先于**拆分动作立好 |
| R6 | **S1 / S5 分两次做** | 六根缝**一次**带上 `spaceId`（DOC1 §7 已警告：否则六根缝各改两遍） |
| R7 | **主题破坏可用性 / 可访问性** | token 白名单 + 对比度校验 + 语义色不可覆盖 |

## Migration Plan

| 阶段 | 内容 | 验收判据 |
|---|---|---|
| **P0 契约** | 本变更集落地；`check-kernel-purity` 先红；术语裁决同步 | 守护可跑、能红、有负例 |
| **P1 抽缝** | 六根 SPI（含 `spaceId`）+ 部署白名单降级；**零行为变更** | `pnpm test` 全绿；双包装配 |
| **P2 空间上下文** | `SpaceGuard` + `AsyncLocalStorage` + 仓储强制注入 | 单空间行为零变更；越权负例报红 |
| **P3 计量 SPI** | `MeteringProvider` 开放 + 兜底口径 + 如实标注 | 无闭源插件也可跑通；有则对拍 |
| **P4 数据隔离** | 域内活动表加 `space_id`；旧数据回填默认空间；覆盖矩阵同步 | `check:meta` 全绿 |
| **P5 准入空间化** | 准入 / 吊销 / 连接器注册加 `spaceId` | 跨空间越权准入负例 |
| **P6 成员与邀请** | 两层成员 + 邀请 / 审批 + 多空间切换 | 一人多空间可登录并切换 |
| **P7 品牌与主题** | 级联 + token 覆盖 + 术语边界 | 主题不越白名单；对比度达标 |
| **P8 协作作用域** | 协作对象 + 可见性过滤 | 竞争方互不可见 |
| **P9 前端** | `[spaceId]` 路由 + 切换器 + 导航按空间过滤 | `check:nav` 全绿 |
| **P10 连接器多栈** | 多空间 × 多包；密钥分栈；本地策略按空间重算 | 一连接器服务两空间，密钥不复用 |
| **P11 开源拆分** | 许可 + conformance kit + 守护分册 | 内核可独立构建 / 测试 |

**关键排期判断**：**P1 不能省**（省了则电力包 fork 出第二套编排）；**P10 不能晚于交付**（晚了会先用"共用密钥 + 单栈"糊过去，形成跨空间密钥复用这一事后极难纠正的安全债）。
