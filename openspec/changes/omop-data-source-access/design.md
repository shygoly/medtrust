## Context

**现状（本会话核实）**：连接器没有任何数据库接入能力。`local-data-loader.ts` 用 `readdirSync`/`readFileSync` 读 JSON；`fhir-gateway.ts` 是纯内存映射函数，不发起连接；`apps/agent`（Python）独立读 `AGENT_DATA_PATH` 下的 `patient-*.json`，依赖里无任何数据库驱动。全仓搜 `omop|cdm_source|person_id` 无实质命中。

**已实测的约束**（本地 Docker `postgres:16-alpine` + 最小 CDM v5.4 子集 + 视图层 + 受限账号，7 项断言全过）：

| 验证项 | 结果 |
|---|---|
| 受限账号读 CDM 视图 | 成功 |
| 受限账号读底表 `cdm_raw` | `permission denied for schema cdm_raw`（直接标识物理不可达） |
| 受限账号写 CDM 视图 | `permission denied for view person` |
| 受限账号在 `results` 建表 | 成功（队列 SQL 必需） |
| 视图行级过滤 | 底表 4 行 → 视图 3 行，被过滤者对研究方**不可见** |
| `cdm_source` / `vocabulary_version` 可读 | `5.4` / `v5.0 31-AUG-24` |
| 视图列不含直接标识 | `person_id, gender_concept_id, year_of_birth` |

并以 OHDSI Book Ch9 的 lisinopril 队列 SQL 跑通端到端：底表 4 人 → 1 人被**医院视图层**挡、1 人被**研究方队列定义**挡、2 人入队。两层过滤独立生效，且医院那层在研究方之前。

**信任边界约束**：PEP、输出闸门、审计链都在连接器进程内。数据访问若落在它之外，闸门可被绕过。

**行业对照**：OHDSI（分析包持 JDBC 直连，靠人审 + 社区信誉）、vantage6（节点配置持凭据，按 label 注入算法容器，靠镜像摘要白名单）、DataSHIELD/Opal（服务器持 resource，算法只能调白名单函数）。三者算法拿到的都是「能访问数据的句柄」。EDC/IDS 与国内《可信数据空间技术架构》都**未规定**这一层——EDC 明言后端接入靠自写扩展。

## Goals / Non-Goals

**Goals:**
- 让连接器能对接真实 OMOP CDM 库，且**不破坏零导入沙箱模型**。
- 把「医院可自主掐断」做成物理机制（数据库权限），而非平台承诺。
- 接入即可验证：契约不满足就拒绝接入，不静默降级。

**Non-Goals:**
- 不做 Circe 队列编译器与 FeatureExtraction（另立变更）。
- 不做通用数据库适配（只接 CDM）。
- 不做 OHDSI SQL 全量方言翻译（第一版只 PostgreSQL）。
- 不改现有文件数据路径（并存）。

## Decisions

### D1. 数据库句柄由连接器**独占**
Wasm 模块 MUST NOT 获得数据访问能力；Python agent MUST NOT 另开独立连接。
- 理由：PEP / 输出闸门 / 审计链都在连接器内，句柄必须与它们同进程边界。给 Wasm 开数据 API 会同时废掉闸 1（零导入）、最小列投影、行序不变性差分——那是整个防外泄模型的地基。
- 备选：按 vantage6 模型把连接串注入算法容器。**否决**：vantage6 的信任模型是「审镜像 + 锁摘要」，即**信任算法**；我们的承诺是「不信任算法」，两者不能混用。
- 备选：agent 直连以跑联邦训练。**否决**：会形成第二个数据入口，闸门与守卫要维护两套。agent 应从连接器取切片。

### D2. 只接 OMOP CDM，不做通用数据库适配
- 理由：CDM v5.4 把表名/字段/类型/主外键定死，**结构是规范而非探测结果**。这让「不反射表结构即可生成 SQL」成立，也让研究定义跨院复用成为可能（联邦网络的技术前提）。通用适配则要反射 + 映射，工程量与审查面都是另一个量级。
- 代价：未做 CDM ETL 的医院接不进来。这是可接受的过滤——CDM 化本身就是联邦分析的入场券。

### D3. 视图契约 + **双权限域**（不是「只读账号」）
医院提供：底表在 `cdm_raw`（连接器无权限），视图在 `cdm`（同名同结构、去直接标识、可行级过滤），另给 `results` schema 的建表权。
- 理由：实测证明这三件事同时成立且互不冲突。视图层是**医院 DBA 完全掌控、随时可 revoke 的第零道闸**，位于我们所有软件闸门之外——这比任何平台承诺都硬。
- **「只读」是错的**：队列 SQL 必须建 cohort 表。按纯只读配置会在首次上线失败，且错误信息（权限拒绝）容易被误判为契约不成立。接入手册必须写明双权限域。
- 备选：给 CDM 表直接 SELECT 权限。**否决**：放弃了行级过滤与列裁剪这个医院侧控制点。
- 备选：连接器侧再做一次去标识。**不替代**：那是平台承诺，视图是医院自己的机制，两者叠加而非二选一。

### D4. 三参数配置，不做元数据探测
`cdmVersion` + schema 名（cdm / vocabulary / results）+ `dbms` 方言。
- 理由：CDM 结构先验已知（D2）。需要从库里读的只有**语义版本**（`cdm_source.cdm_version`、`vocabulary.vocabulary_version`）与**覆盖统计**，前者用于校验、后者用于目录，都不是「编译 SQL 所需的表结构」。
- `concept_id` 的语义依赖词汇表版本，故 `vocabulary_version` 必须记录并随结果留痕——同一 id 在不同版本可能改变含义。

### D4b. 投影下推到 SQL，两条数据路径在「投影载荷」汇合
文件路径是「JSON → `InternalRecord[]` → `LocalStore` → 内存 map/filter → 投影」；CDM 路径 MUST NOT 照搬这个形态（把表拉进 `LocalStore` 再筛），而是**把列裁剪与行过滤写进 SQL**，取回的结果直接就是最小列投影。
- 理由：千万行级 CDM 全量拉进 Node 内存工程上不可行；更重要的是，接库之后「投影」天然发生在 SQL 里，这与数据最小化是同一件事，不是额外负担。
- 结构后果：两条路径在**投影载荷**（最小整数列）这一点汇合，之后的沙箱、输出闸门、存证链路**完全不变**——算法模块的零导入判据不因数据源类型而改变。
- 这条是动手前复核既有代码时发现的：初稿 spec 曾写成「原始行级数据 MUST NOT 被复制到连接器本地存储」，与现有 `data-space-connector`「原始医疗数据 MUST 仅存储于连接器本地存储」直接矛盾，且没抓住要点。真正的约束是**不全量拉取 + 投影下推**，已据此修正。

### D5. 接入校验 fail-closed，不降级
必需表存在、视图不含直接标识列、权限边界符合预期（底表不可达 / 视图不可写 / results 可写）、`cdm_source` 与 `vocabulary_version` 可读。任一不过即拒绝接入。
- 理由：与 D-UC-2 一致。「契约没配好就退回文件模式」会让医院以为接通了，而实际跑的是别的数据。

### D6. 方言抽象留接缝，第一版只实现 PostgreSQL
- 理由：实测已证明方言翻译不可回避（SQL Server 的 `DATEDIFF(DAY,a,b)` 在 PG 上必须改写）。但全量翻译器是独立工程（OHDSI 为此造了 SqlRender），而国产库（达梦、人大金仓、OceanBase）SqlRender 亦不支持。
- 做法：定义 `SqlDialect` 接缝，先只实现 PG；不假装支持未实现的方言——请求未实现方言时明确报错。

### D7. 凭据只存在于连接器侧
数据库凭据 MUST NOT 出现在控制面、任务载荷或派发记录中。
- 理由：借鉴 vantage6 的 `databases[].env` 模型（凭据在节点配置，按请求的数据源注入）。控制面一旦持有院内库凭据，「数据不出域」就只剩口头承诺。

### D8. 本变更只交付**机制**，不开放 CDM 上的生产分析语义
实施时发现：文件路径的 `matchesMedication` 是**模糊字符串匹配**（双向子串 + 别名正则），服务于非标准化自由文本；CDM 的正确做法是按 `concept_id` 匹配。更根本的是，CDM 的 `condition_occurrence` 包含**全部诊断**（慢病、既往史），不等于不良事件——正确的药物警戒需要「暴露后时间窗内发生」的定义，那是队列 + time-at-risk，属于 Circe 变更的职责。
- 决定：本变更交付投影下推的**机制**（SQL 侧列裁剪/行过滤 → 投影载荷 → 沙箱，受控数据下与文件路径逐字段一致），**不把任何分析类型在 CDM 上接入生产派发**。CDM 类型的数据产品派发一律 fail-closed，报「CDM 数据源的分析语义（队列定义 / 时间窗）由 Circe 变更提供，当前未开放」。
- 理由：在数据访问变更里发明临床语义是越权；把「全部诊断当不良事件」这种近似放进生产，会产出看似正常、实则误导的 PRR/ROR——比不开放更糟。
- 药物引用按 `concept_id` 解析（名称仅做 `concept.concept_name` 的精确不区分大小写匹配），**不移植**文件路径的模糊匹配；解析不到即 fail-closed，不把所有人当作未暴露。

### D9. 联邦训练切片由连接器投影，特征与标签口径归连接器（2026-09-21 用户定夺）
实施 4.3 时发现：agent 按任务 spec 的 `dataPath`（控制面可指定）自读演示 JSON——文件含姓名 / 生日，绕过连接器去标识；而且它训练的**不是合约指向的数据产品**，而是镜像里烘焙的 Synthea 文件。标签是 agent 对**英文诊断原文**跑的肾病正则，连接器却已把诊断规范化成中文术语。
- 决定：连接器按合约的 `dataProductId` 投影训练切片 `{schema, featureKeys, rows, labels}`（7 项数值观测按固定顺序、0/1 标签），随 RunLocalRound 请求交给 agent；agent 只做结构校验、拒收切片外字段，无切片即本轮失败；spec 带 `dataPath` 在控制面与 agent 两处都拒；agent 镜像不再内置患者文件。
- 标签口径迁移（`esrd-proxy@1`）：词表 = agent 旧英文正则 ∪「肾」。在演示数据（示范甲 140 + 示范乙 150 人）上与旧口径**逐人一致**。
- 切片只在本次调用里从数据产品取数，**不替换**共享的 LocalStore（执行队列有并发）。
- 备选（否决）：连接器只投影数值观测 + 诊断列表、标签仍由 agent 算——诊断列表整体越过连接器边界，数据最小化更弱，且口径分散在两处。
- **后果（如实）**：训练数据从「镜像里的 Synthea 文件」变为「合约指向的数据产品」。现有演示训练合约指向 `dp-insulin-panc-*`（胰岛素-胰腺炎注入数据），肾病阳性 0 / 5000——**演示训练的标签将全为 0**；要让演示有意义，须把联邦训练合约改指向带肾病标签的数据产品（演示数据配置，另议）。特征方面现有演示数据都没有观测值，特征全为 0（与旧行为相同）。

## Risks / Trade-offs

- **视图性能未验证** → 本地实测仅 4 行，无法反映千万至亿行级 CDM 上带行级过滤视图对索引使用的影响。**缓解**：接入前在目标院真实数据量上做基准；若视图成为瓶颈，退路是物化视图（由医院侧刷新，控制权不变）。**此风险未消除，不得在对外材料中声称性能已验证。**
  - **进展**：合成千万行级基准（2026-09-21，100 万人 / 1000 万用药 / 1000 万诊断，热缓存，`apps/connector/scripts/omop-view-benchmark.sh`）：只裁列的视图零开销（规划器内联，索引计划相同）；带行级过滤（NOT EXISTS 退出名单）的视图**照常走索引**，另加一次退出名单主键的反连接，选择性查询慢 1.25–1.5×（绝对值 +2.5～+7.7 ms），未出现视图导致的顺序扫描。「视图让规划器放弃索引」这一具体担忧在所测查询形态下不成立，暂不需要物化视图；**真实分布与目标院硬件仍未验证**，接入前仍须在目标院真实数据上做基准。
- **方言翻译工作量被低估** → **缓解**：第一版锁定 PG 并显式拒绝其它方言；国产库支持单独评估后另立变更。
- **`results` schema 中间结果堆积在医院库** → **缓解**：纳入既有 retention 约束，任务结束即清理，并在接入校验中要求 `results` 可清。
- **医院 DBA 按「只读」配置导致上线失败** → **缓解**：接入校验对这一情形给出专门错误信息（区分「权限不足」与「契约不成立」），接入手册显著标注双权限域。
- **CDM ETL 质量参差**（字段缺失、概念映射不全）→ **缓解**：接入校验只覆盖结构性一致；数据质量属 OHDSI DQD/Achilles 的范畴，第一版只做统计留痕并在目录如实呈现，不做质量裁决。
- **新增 PostgreSQL 驱动依赖进连接器** → 扩大连接器攻击面。**缓解**：驱动版本锁定；连接器已在 `compose.hardening.yaml` 下以非 root / 只读根 FS / internal 网络运行。

## Migration Plan

1. **并存不切换**：文件数据源路径保留，按数据源类型分派。已有 Synthea/JSON 演示链路不受影响。
2. **接入顺序**：医院侧建视图层 + 受限账号 → 连接器配置数据源 → 跑接入校验 → 校验通过才允许该数据产品被合约引用。
3. **回滚**：移除数据源配置即回到文件模式；医院侧 `REVOKE` 即可单方面切断，无需平台配合（这是设计目标，不是副作用）。
4. **ali29**：连接器新增数据源配置与凭据注入；凭据不进控制面库，故控制面无需迁移。

## Open Questions

- 视图 vs 物化视图：性能基准做完才能定，物化视图会引入刷新时效问题（研究结果对应哪个时点的数据）。
- `results` schema 的清理时机：任务结束即清，还是保留一个可追溯窗口（便于争议时复核）？后者与 retention「阅后即焚」口径冲突，需要定夺。
- 多数据源：一家医院是否可能有多个 CDM 库（如不同科室/不同 ETL 批次）？若是，数据产品与数据源的对应关系需要显式建模。
- CDM 5.3 与 5.4 并存：是否需要同时支持？字段差异会影响生成的 SQL。
- 词汇表版本不一致：跨院联邦时各院 `vocabulary_version` 不同，`concept_id` 语义可能有差异——这属于结论可信（EVIDENCE）的范畴，本变更只负责如实记录，但需确认由谁裁决「版本差异是否影响本次研究」。
