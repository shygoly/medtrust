## Context

MDOP v0.2 已把「数据在可信空间内受控流动」定义为 **C2**，并写明其完整语义（§4.2 R4/R5、§4.3 能力匹配、§9.2–§9.4 通道/信封/密钥释放），但**默认关闭**：没有任何节点通告 TEE 能力，编译器对 C2 边一律报 `E_CAPABILITY_MISMATCH`（D-MDOP-6）。代码现状：

- `packages/mdop/src/label/lattice.ts` 的 C2 分支已实现（要求 `target.tee` 且合约 `attestation_policy.tee` 含该 kind），并有正反例用例；
- 连接器的能力通告把 `tee` 恒置 `null`，本地能力检查 `C2 → cap.tee !== null` 已就位（`operator-whitelist.ts`）；
- 平台的能力读取已把心跳里的 `mdop.tee` 映射为 `NodeCapability.tee`，但没有任何节点会填；
- TRUST **P-CTL-8** 已如实登记该缺口（含「不得表述为数据没出医院」的边界）。

触发本变更的是业务侧事实：**跨院主体配对、亚组重算、非线性/影像模型、受预算约束的探索**这四类问题在 C3 通道上无解（协议 §4.5 有判定表与四个例子）。同时硬件前提已经具备（海光 CSV / Intel TDX / AMD SEV-SNP + DCAP/CSV 证明链），KMS 释放策略的工程模式成熟。

## Goals / Non-Goals

**Goals**
- 让可信空间节点成为 MDOP 的**一等节点**：身份、密钥、能力通告、证明、凭证、调度、销毁、回执全流程与医院连接器同构。
- 把「数据出域」换成可验证的形式：**密文出域 + 只在被证明过的代码里解密**，且密钥释放由持有方/中立方控制的 KMS 决定，平台不接触数据密钥。
- 用负例把边界钉死：伪造证明、度量不符、TCB 过旧、证明过期、节点越权出口、平台索取密钥——每一种都必须 fail-closed 且留痕。

**Non-Goals**
- 不做 C1（MPC/安全聚合/PSI）——与 C2 正交，另立变更；本期不碰 SPU/MP-SPDZ。
- 不做多可信空间节点互联与跨空间联邦。
- 不做 GPU TEE 上的大模型训练；本期只做统计与降密类算子。
- **不做度量白名单的签名化签发与吊销**（「与算子清单同一套机制」是升级路径、不是本变更的交付）：
  本变更按 INV-TEE-01 用**部署配置副本**（平台侧是上限、节点侧是本地允许集），换版/吊销靠重新部署；
  升级须另立变更（涉及清单 schema、长轮询投递与吊销状态机）。
- **不做 ε-差分隐私加噪与预算账本**（TRUST P-CTL-3 待接入）：节点内的强制项是
  **小单元格抑制 + 二次抑制 + 发布审查 + 查询预算账本**；`dp` 字段只**如实记录声明**（缺省 `none`），
  `mode=epsilon` **不代表已加噪**。ε 加噪与账本另立变更（`output-gate` 消费 epsilon + 账本）。
- **不做国密 AEAD（SM4-GCM）的引入**：本期 C2 信封的载荷密文用 **AES-256-GCM**，`payload.cipher`
  如实标注算法名。这是对 **D8**「通信用国密加密」的**临时偏离**（Node 无原生 SM4-GCM，仓内 SM4 为
  CBC 且无完整性校验），登记在 DECISIONS D8 落地补注；收回须引入受审计实现或自研并过安全评审，
  另立变更/安全评审项。**偏离期间不得把 C2 信封表述为国密信封**。
- 不在真实患者数据上演练；真实数据上线前须先完成 REG 合规路径与医院对运营方的书面接受。

## Decisions

### D1 运营方与信任模型：中立第三方/监管侧优先，密钥释放权与节点运营权分离

可信空间节点由谁运营，是这套方案能否签下来的第一决策——**技术选型其次**。

- 默认推荐：节点由**中立第三方或监管侧**运营；药企作为申请方使用算力，**不持有数据密钥**。
- 若药企自建节点，必须有医院**书面接受**，且满足两条：① KMS 由持有方（医院）自建或与运营方共管；② 运维权限（引导、固件更新、主机 root）纳入合约与审计范围。
- 平台 MUST NOT 持有数据密钥，也 MUST NOT 拥有「绕过 KMS 直接取解密能力」的路径；平台只编排（下发作业、收集证明摘要、锚定回执）。
- 明确写出**我们信任什么**：CPU 厂商证明根、被测代码度量、KMS 策略实现；**我们不信任**：可信空间节点运营方对内存的访问（由 TEE 与证明约束）、平台、申请方。侧信道不在本期防护范围（见 Risks）。

### D2 节点身份与密钥：与医院连接器同构，自持密钥、只提交公钥

可信空间节点是参与方（URN 形态 `urn:tds:<space>:participant:<id>`），沿用 D-MDOP-3：密钥本地生成（0600）、注册只提交公钥、平台不代生成；证明报告里的**一次性公钥**用于封装数据密钥，二者分离（长期身份密钥签回执，一次性公钥收密钥）。

### D3 证明与度量：白名单同源、短有效、每次会话重新证明

- 证明报告 MUST 覆盖：代码度量（算子/公证代码的哈希）、TCB 版本、一次性公钥、节点身份绑定；
- **度量白名单来自部署配置**：平台侧 `MDOP_ATTESTATION_MEASUREMENTS` 是**上限**、节点侧
  `TEE_NODE_MEASUREMENTS` 是本节点允许集的本地副本；合约可进一步收窄 `allowed_measurements`，
  交集为空即拒（不退化成「不限」）。**与「同源签名 + 可吊销」的差距如实标注**：现状是人工同步的
  配置副本（换版/吊销后须重新部署），签名化签发与吊销**不在本变更范围**（见 Non-Goals）——
  在它落地前，任何文档/MUST NOT 把它写成「已经与算子清单同一套机制」；
- 合约给出 `min_tcb`，低于下限即拒；
- 证明**短有效期**（缺省 10 分钟）且**每次计算会话重新证明**：一次证明长期复用等于把「一次性检查」当成「持续保证」；
- 证明摘要与度量写入**执行凭证的签署范围**：各院签名覆盖「在哪个度量下执行」，换代码即失效。

### D4 密钥释放：证明绑定 + 策略校验，平台不在链路上

1. 节点启动算子实例 → 生成证明（含一次性公钥）；
2. 节点向 KMS 提交：证明报告 + 执行凭证 + 信封里的 `key_id`；
3. KMS 校验：证明链到厂商根有效、度量在允许清单、TCB ≥ 下限、证明未过期、凭证签名完整且在有效期、合约未终止、`key_id` 属于本作业的片段；
4. 全部通过 → KMS 用一次性公钥加密数据密钥返回；密钥只存在于该实例内存；
5. 实例退出即失效；再次计算重新走 1–4。

**负例即拒**：任一校验不过返回拒绝并留痕（`E_ATTESTATION_FAILED` / `E_MEASUREMENT_NOT_ALLOWED` / `E_TCB_TOO_OLD` / `E_KEY_RELEASE_DENIED`），**不回退到明文或旧密钥**。

### D5 数据入节点：只有 `seal` 能产生 C2，入口守卫核对「合约声明过的切片」

- 持有方侧用 `seal` 算子把本节点 C0（去标识投影，非全量底表）封装为 `mdop.env/1.0` 信封；AEAD 的 AAD 绑定作业 id、凭证号、合约哈希——换作业即解密失败；
- 节点入口守卫逐项核对：信封签名、合约与用途、`allowed_ops`、有效期、水印；未在合约声明内的数据产品切片一律拒收；
- **最小投影**是硬要求而非建议：TEE 能解密不等于可以随便送（侧信道不在防护范围）。

### D6 节点内执行与发布审查：闸门在节点内、由被测代码强制

节点内的算子来自注册中心清单（与院内同一套 `wasm`/`system` 语义），执行器在 TEE 内运行；**发布审查（minCell + 二次抑制）与查询预算在节点内执行**，出域前由被测代码强制，而不是靠运营方自觉。**DP 加噪不在本期**（只记录 `dp` 声明，见 Non-Goals）——它是硬约束的另一半，落地前不得按「已具备 ε-DP」表述。

### D7 出口：只有 C3，且 R5 不可逆出

节点内解封后的数据视为该节点 C0；离开节点的**只有经发布审查的 C3**（`export: C3_only` 写在信封策略里并由出口守卫强制）。R5：节点内 C0/C1 MUST NOT 以任何形式回流到原持有方以外的节点。

### D8 查询预算：防「把远程终端交给申请方」

缺少预算约束时，C2 会退化成用大量允许出域的小统计量反推个体——后果与直接出明细同级。因此：

- 查询预算账本以「数据集 × 快照版本」计量，**节点内维护、以持有方本地账本为准**（与 §10.1 同口径）；
- 亚组/切点重算必须在预算内；超限即拒，并把拒绝原因回执到作业；
- 同一申请方的累计输出受查询审计（差分查询检测）。

### D9 凭证与审计：证明进签名范围，回执链覆盖节点

执行凭证的签署内容在现有 `{core + 快照}` 基础上，**增加证明摘要与度量**；可信空间节点与医院连接器一样，每个事件（解封、执行、出口、销毁）出签名回执并成链，链头由平台锚定上链。

> **实现期修正（2026-09-25）**：原文写「增加证明摘要与度量」把两类东西混在了一起，实现时立刻撞车——
> quote 摘要每次重新证明都会变（缺省 10 分钟有效期），而凭证核心是一次性冻结的，两者放在一起会导致
> **每次执行都判「证明与凭证不一致」**。正确分工是：
> - **凭证核心 `attestation`**（可选）= `{tee, measurement, min_tcb}`：稳定的**代码身份与策略**，
>   各持有方签署它，含义是「本院批准在这份代码下执行」；
> - **KMS 会话释放凭据** = 本次证明的处置结果（quote 摘要、度量、TCB、有效期），逐次产生（D13 的凭据）。
>
> 执行前把两者与实际证明对起来（`attestation/execution.ts` 的 `verifyC2Execution`）；协议 §7.5 已同步补注。

### D10 销毁：`PurgeOrder` 覆盖节点，收齐全部回执才 `PURGED`

终态销毁流程扩展：`nodesToPurge` 须包含参与过的可信空间节点；节点本地擦除（内存 + 临时盘）并出签名回执；平台收齐**含节点在内**的全部回执才进 `PURGED`。

### D11 失败模式：全部 fail-closed，且失败原因可审计

| 失败 | 行为 |
|---|---|
| 证明验签失败 / 链不到厂商根 | KMS 拒释放 + `E_ATTESTATION_FAILED` + 审计 |
| 度量不在白名单 | KMS 拒释放 + `E_MEASUREMENT_NOT_ALLOWED` |
| TCB 低于合约 `min_tcb` | KMS 拒释放 + `E_TCB_TOO_OLD` |
| 证明过期 | 拒绝执行；连接器出口守卫**拒投** |
| 节点掉线 / 超时 | 作业超时 → `REJECTED`，不发后续 `StageDispatch` |
| 平台尝试索取数据密钥 | 无该接口；试图实现即为设计违背（用例断言不存在） |
| 节点试图投出非 C3 | 出口守卫拒绝并留痕（回执链） |

### D12 与既有 C3 通道的关系：可混用，编译期按边判定

同一条作业可以一部分阶段在院内本地执行（出 C3），一部分在可信空间节点执行（C2 入、C3 出）。编译器按每条边独立判定 C2 条件；已上线的 C3 通道与本期 C2 通道**互不影响**（未声明 C2 的作业行为不变）。

### D13 医院侧如何独立校验证明：以「KMS 释放凭据」为主，原始 quote 自验为可选增强

七项复核第 4 项要求 C2 目标「证明可被**本地独立校验**」，MUST NOT 只信平台的登记结果。三种候选：

| 方案 | 评价 |
|---|---|
| ① 节点暴露只读证明端点，连接器直连拉取 | **否决**。医院连接器通常只出站到平台，未必可达药企/第三方节点；且给节点开了入站端点，与「连接器不开入站」的既有取向相反，攻击面变大 |
| ② KMS 出具可离线核验的释放凭据（quote 摘要 + 度量 + TCB + 有效期 + KMS 签名），随凭证/要约下发 | **采用**。网络方向不变；复用现有回执链与离线核验工具（`scripts/verify-receipt-chain.mjs` 同族）；KMS 本就是唯一的密钥释放决策点，避免出现两个「谁说了算」的真相源 |
| ③ 医院侧自行拿原始 quote 走 DCAP/CSV 校验 | **保留为可选增强**。最独立，但要求医院侧能访问厂商证明服务与 CRL（多数院内环境不允许），且须实现多厂商 quote 解析 |

**决策要点**：默认走 ②；KMS 必须由持有方自建或与运营方共管（D-TEE-1），因此「信任 KMS 的校验结论」在默认形态下是**自证**，不是把信任转给第三方。若某院具备 ③ 的能力，可在合约中要求「释放凭据 MUST 附带原始 quote，持有方可自行复核」——这条作为升级路径写进合约，而不是默认要求。

**落地落点**：释放凭据的验签在连接器本地复核里（第 4 项），验签用的 KMS 公钥来自**部署配置或合约**，MUST NOT 从平台消息里取（否则平台被攻破即可连公钥一起换）。

> **2026-09-25 落地修正**：上面那句「随凭证/要约下发」**不成立**——凭据是逐会话产生的，
> 而凭证与要约都在执行之前。真实载体见 **D14**（节点 → 平台 → 持有方两条控制面消息），
> 校验落点也相应改为「会话后核验见证」，而不是「复核第 4 项」。

### D14 会话见证的载体：节点 → 平台 → 持有方，转发不构成信任

**问题（本轮复核发现的缺环）**：D13 选的是「持有方用 KMS 释放凭据独立校验证明」，但凭据是**逐会话**产生的
（证明缺省 10 分钟有效期），因此它**不可能**像 D13 原文写的那样「随凭证/要约下发」——凭证与要约都在
执行之前。原实现里凭据只存在于节点会话内、平台只落库摘要，于是「独立校验」没有任何载体，
只能退化成「信平台的登记结论」，正是 D13 要避免的。

**决策**：见证走控制面，**两条消息**，平台只搬运不背书：

```
节点 ──AttestationReport（证明报告 + 释放凭据）──▶ 平台 ──AttestationWitness（原样转发）──▶ 各持有方
```

- **必须送本体，不送摘要**：只给摘要时持有方**验不了**（摘要不可验签）。本体是
  「报告 + 凭据」，后者带 KMS 签名；一次性公钥已在报告里，wrapped key 只有节点实例能解，
  平台看到也解不开。
- **平台不代替持有方下结论**：平台不声称验过厂商 quote（它没有证明根）；它做的是
  ① 严格解析（跨网络输入：未知字段/缺字段/非法形状一律拒）、
  ② 用**部署配置里的 KMS 公钥**验签并核对合约策略与凭证期望、③ 登记本体并把同一份本体转发出去。
  平台能「不给」，但做不到「伪造」——这正是可以接受它做搬运工的理由。
- **持有方与平台各自判**：持有方拿本院签过的 `core.attestation[node]` 与见证对拍
  （换代码/换链型即拒），判据复用协议核里的 `verifySessionWitness`（不另写一套）。
  通过记 `WITNESS_VERIFIED`、拒绝记 `WITNESS_REJECTED`，两者都进审计回执链——
  「验过没有」是可查事实，不是日志里的一句话。
- **一次会话一条历史**：登记以**释放凭据摘要**为会话键（`sessionKey`），同一节点同一度量的多次会话各留一行；
  为此 `warrantDigest` 必须覆盖**逐会话变化的字段**（一次性公钥、`issued_at`），否则同秒内的两次会话
  会算出同一个摘要，第二次的凭据就换不掉第一次的（「每次会话重新证明」被摘要口径吃掉）。

**仍未闭环的一半**：这条链的**发送端**（节点组件上报 `AttestationReport`）随 `apps/tee-node` 落地，
因此 §6.7 只剩「组件接线」未做——协议、平台侧、持有方侧都已落地并有用例。

### D15 C2 数据面的传输：平台中继（只转运不解密）

**问题**：C2 信封怎么从持有方**到**节点？此前没有任何路径——FLOW-MDOP-02 因此登记不了，
§9.2/§9.3 的演练也无从跑起。

**两条候选与取舍**：

| 方案 | 判断 |
|---|---|
| ① **持有方直连节点**（连接器打节点入站/长轮询） | **否决为默认**。院内网络的出站白名单通常只放平台；节点开入站与既有取向（参与者只外联、不开入站）冲突，攻击面也更大。保留为「网络已打通的专线场景」选项。 |
| ② **平台中继**（持有方投平台 → 平台转节点） | **采用**。复用既有出站通道与认证（连接器/节点都长轮询同一个控制面），网络方向不变。 |

**平台在中继中的角色（必须写清楚，否则会被误读成「把数据交给平台」）**：

- 平台拿到的是**密文 + 密钥封套**：数据密钥用**目标节点本次会话的一次性公钥**封装，平台没有那把私钥，
  **解不开**；信封本身还有持有方签名与 AAD 绑定（换作业/换凭证/换合约即解不开）。
- 平台只做**可判定的检查**：信封由持有方签名；合约在本作业的合约列表里且**声明了证明策略**；
  AAD 的作业与合约与信封自身一致；**密文摘要**与信封声明一致（不解密也能查完整性）；
  目标必须是**本作业的片段节点**（不能借中继送到计划外的节点）；信封未过期。
- 平台**不**做发布审查、**不**做解封、**不**持有任何解密能力；这些仍在节点内由被测代码强制（D-TEE-2）。
- 中继消息入发件箱（幂等键 = 密钥 + 目标），由目标节点长轮询取走；平台在队列里短暂持有密文，
  投递后按既有清理机制删除。审计只留**句柄与摘要**，不在中继表里再存一份密文。

**节点侧一次接收做四件事**（`tee-node/relay-receive.ts` + `stage-dispatch.ts`）：跑会话 → 登记句柄
（`ArtifactReady`，不含载荷）→ 投递 C3（`ResultDeliver`，数据面）→ 上报会话见证（D14）→
**上报阶段状态**（`StageStatus`：成功带摘要与等级、失败带错误码）。C3、见证与状态都用**节点自己的身份密钥**签。
阶段状态不是可选项：平台按它推进下游、按错误码退避重试——节点不报，多阶段作业就停在第一个节点阶段。

**节点是一等参与方，不只是「跑一次算好的阶段」**（`tee-node/node-messages.ts#NodeMessageRouter`，
2026-09-25 落地）：平台下发的五类消息各有处置判据——要约（本地九项复核 → **节点自己签名接受**；
平台收齐全部片段签名才签发凭证，所以节点不接受就永远拿不到凭证）、凭证（存下并当场校验，含执行环境
快照比对）、C2 信封（按**已复核片段里的入边**绑定到阶段）、阶段派发（与信封**会合**：两个来源无先后
保证，先到的一方只登记、不误报失败）、销毁指令（销毁制品 + 签名回执，链上 `PURGED`）。
节点签入的快照是**执行环境快照**（算子摘要 + 期望 + 本节点当下证明能力），环境漂移即
`E_SNAPSHOT_CHANGED`——该语义登记为 **D-TEE-5**。

**节点的 wasm 执行接线**（`tee-node/wasm-runner.ts` + `tee-node/executor.ts`，2026-09-25 落地）：
`MdopStageExecutor` 对 `wasm` 类算子要求本节点接入沙箱，节点此前没有接线（用例里自己塞假 runner），
真实部署下 `pair` 阶段会一步也跑不了。现在：宿主按**摘要**从节点本地模块库取字节（取不到即拒，
不现取平台），**显式声明调用形状**（`abi: 'pairing@1'` = `run(inOff,parties,n,strata,outOff)`；
既有 L1.5 仍是缺省的 `table@1`，其行为一行未改），宿主适配把投影装成数字列、回填聚合量并做不变量校验。
**对齐与分层留在宿主**：模块只认「已对齐的下标与标志」，因此 §3.12b 的两种对齐方案都不改模块与这段代码。

**一个阶段可能有两条落点**（`tee-node/stage-dispatch.ts`，2026-09-25 落地）：产物**还有同节点下游**
（如跨院配对结果要接着做降密）→ 只跑阶段、C2 制品留在本节点制品库，**只登记句柄、不投递载荷**；
没有同节点下游 → 才是该节点的终点产出，走发布审查与出口。判据只取**片段里的结构事实**，
不新增协议字段。一次阶段也可以吃**多份**封存输入（跨院配对＝两家各一条）：齐了才跑、一次会话解封全部。

**仍未闭环的部分**：节点的**长轮询循环**（把发件箱里的中继消息取回来并派发）与
**节点侧合约副本的获取与验签**（现在由装配方注入，见 tasks §3.15）。

## Risks / Trade-offs

- **侧信道不在防护范围**：TDX/SEV-SNP 不防内存访问模式分析。缓解：最小投影、噪声、查询预算；并在文档与合约里写明，不宣称「TEE 内数据绝对安全」。
- **信任锚从医院转向多方**：CPU 厂商 + 代码度量 + 运营方 + KMS。缓解：运营方与 KMS 分离、度量白名单取自部署配置（**签名化签发/吊销为后续项**，现状靠人工同步）、证明短有效期、全链路回执与锚定。
- **合规性质变化**：数据出域属委托处理，需 REG 路径与医院书面接受。缓解：本变更把合规材料列入必要交付，未完成不进真实数据。
- **性能与成本**：TEE 内存与加密开销明显，大影像训练不现实。缓解：本期只做统计类；大模型训练留待 GPU TEE。
- **运营方成为新的单点**：节点停机即作业不可用。缓解：与 C3 通道并存，非必要不使用 C2。

## Migration Plan

1. **治理先行**：修订 D-MDOP-6 / D9，TRUST P-CTL-8 → CTL-29，DOMAIN/FLOWS/ARCHITECTURE 同步；`check-meta-docs` 0 error。
2. **协议与 schema**：`packages/mdop` 落地信封、`seal`、`attestation_policy`、凭证扩展与错误码；补负例用例（伪造/过期/度量不符）。
3. **单节点 MVP（合成数据）**：一个可信空间节点 + KMS，跑通「证明 → KMS 释放 → 节点内执行一个降密阶段 → 只出 C3 → 回执与锚定」。
4. **两院 C2 汇聚**：两院 `seal` 上送 → 节点内跨院合并（**首个真实增量能力＝跨院主体配对**，
   见 D-TEE-4 首选 A；备选是亚组/切点重算，仅作演示链路）→ 平台只收 C3。
   本步的**前置**：可对齐假名键方案定稿（跨院 PSI 或全空间共享盐）+ 配对算子（`wasm`/`collab`）入库并由注册中心签发清单。
5. **补齐硬约束**：查询预算账本与发布审查在节点内强制；查询审计。**ε-DP 加噪不在本期**（只记录声明，见 Non-Goals / P-CTL-3）。
6. **真实数据前的合规闸**：REG 路径 + 医院书面接受运营方与 KMS 归属；未完成则只跑合成数据。

### 已落地的可跑部分（2026-09-25，代码与本节同批）

**运行时装配（不需要硬件）**：`apps/connector/src/mdop/node/node-session.ts` 把节点侧各部件串成一次
真正的 C2 会话——**证明（每次会话重新证明）→ 入口守卫 → KMS 释放 → 解封（AAD 绑定 + 密文完整性对拍）
→ 节点内执行 → 发布审查 → 只出 C3 → 回执成链 → 销毁**。两处可插拔接缝：证明提供者（`AttestationProvider`）
与 KMS 客户端（`KmsClient`，判据共用 `evaluateKeyRelease`）。端到端用例：
`apps/connector/src/mdop/node/c2-session.spec.ts`（两院合成数据 + 跨院配对 + 全套负例）。

**两阶段执行（配对 → 降密，2026-09-25 落地）**：会话拆成「跑阶段」与「出口」两半
（`runStage` / `executeLocalStage` + `publish`），发布审查**只做一次**并由降密算子
（`tee-node/declassify-op.ts` 把 `NodePublicationReview` 注册成 `declassify.small_cell@1.0.0`）承载。
于是首个场景在合成数据上真的端到端可跑：两院 `seal` → 平台中继 → 节点内 `pair`（C2 制品**不出节点**）
→ 节点内 `decTee` 过闸门 → C3 → 投递平台 → 平台收集。用例：
`apps/connector/src/mdop/tee-node/stage-dispatch.spec.ts`（7 条，含三条负例与出口判据四例）。
注意：节点**守护进程的长驻循环与注册/心跳接线仍是部署动作**，本步落地的是库级装配。

**如实边界（不得含糊）**：该会话用**替身**证明提供者与本机演练 KMS 跑通的是**接口与协议**，
不是「C2 已可用」——软件提供者在本用例中被断言**必然跑不通**（`E_CAPABILITY_MISMATCH`）。
可部署的节点组件（`apps/tee-node`：身份登记、心跳、证明代理、真实 KMS 客户端）与硬件前置仍待落地。
