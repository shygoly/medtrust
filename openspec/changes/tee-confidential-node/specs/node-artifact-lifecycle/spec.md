## MODIFIED Requirements

### Requirement: C0 不出节点
连接器的数据面出口 SHALL 只投递 C3 制品，例外是**声明了 C2 的作业可以把 C2 信封投给合约指定的可信空间节点**；两种情况下的目标都 MUST 在本地合约声明的范围内。

任何把 C0 或 C1 制品发往本节点之外的尝试，MUST 被拒绝、抛错，并记录审计，与编译和复核的结论无关。

C2 信封的投递在下列任一条件下 MUST 被拒绝（fail-closed，不得「先投后核」）：
- 本地合约没有 `attestation_policy`（即该合约不允许 C2），或拿不出本次会话的证明声明；
- 目标节点的证明无法被**本地独立校验**（证明过期、度量不在允许清单、TCB 低于 `min_tcb`、证明链不可信）；
- 信封的 `policy.export` 不是 `C3_only`，或其 AAD 绑定的作业/凭证/合约与本作业不符。

被拒投递 MUST 写入签名回执，并可被离线工具核验。

#### Scenario: 尝试投递 C0 制品
- **WHEN** 有代码路径试图经数据面把一个 C0 制品投给平台
- **THEN** 出口 MUST 拒绝投递，并记录审计

#### Scenario: 接收方不在合约里
- **WHEN** 一个 C3 制品的投递目标不在本地合约的接收方列表中
- **THEN** 出口 MUST 拒绝投递

#### Scenario: 合约不允许 C2
- **WHEN** 连接器尝试把 C2 信封投出，而本地合约副本的条款里没有 `attestation_policy`
- **THEN** 出口 MUST 拒绝投递并记录审计

#### Scenario: 拿不出本次证明声明
- **WHEN** 连接器尝试把 C2 信封投出，但没有本次会话的证明声明（只有对方「自称可信」）
- **THEN** 出口 MUST 拒绝投递

#### Scenario: 证明过期的目标
- **WHEN** 目标节点的证明在投递时已过期，或声明层面（级别/链型/度量/TCB）不合规
- **THEN** 出口 MUST 拒绝投递（不得因平台的登记结果而放行）

#### Scenario: 未声明 C2 的作业尝试投递
- **WHEN** 作业与合约均未声明 C2，而连接器尝试投递 C2 信封
- **THEN** 出口 MUST 拒绝

## ADDED Requirements

### Requirement: C2 制品与句柄
送入可信空间节点的 C2 信封 SHALL 在两侧都登记句柄：持有方侧登记「已送出」句柄，节点侧登记「已接收」句柄。
- 句柄 MUST 带**密文摘要**（`digest`，`sm3:<64hex>`），且 MUST NOT 携带任何明文制品内容。
  **明文摘要刻意不随信封/句柄携带**（2026-09-26 更正）：带上它，持有密文的任一方（含平台）
  就能用它**确认明文内容**（内容预言机）；明文完整性由 AEAD 认证标签 + AAD 绑定保证，
  不需要也不应该额外给一个可对拍的摘要。
- 节点侧**对外句柄** MUST 与执行凭证编号关联：`ticket_id` 是句柄 schema 的必填字段，
  缺少（或为空）即被拒绝登记（`parseArtifactHandle` 的硬判据，有负例）。**合约经 `job_id` 关联**——
  登记时由登记方补上 `job_id` 与 `node`（句柄 schema 不含这两项），合约列表以作业为权威；
  句柄**不冗余存 `contract_id`**（同一事实两处存储必然漂移）。
- 节点内解封产生的 C0 制品 MUST 留在节点内，MUST NOT 出现对外句柄。

#### Scenario: 句柄摘要与内容不符
- **WHEN** 投递的密文摘要与登记句柄的摘要不一致
- **THEN** 接收方 MUST 拒绝该投递并留痕

#### Scenario: 句柄缺凭证关联
- **WHEN** 登记一个句柄但没给 `ticket_id`（或给了空串）
- **THEN** 登记 MUST 被拒绝——句柄必须能追溯到执行凭证，否则无法归属到某次会话

#### Scenario: 登记节点内的 C0 句柄
- **WHEN** 节点试图为解封后的 C0 制品登记对外句柄
- **THEN** 系统 MUST 拒绝

### Requirement: 节点内制品的 TTL 与销毁
节点内制品（密文、解封后的中间结果、查询账本副本）SHALL 设有 TTL，并在作业终态收到 `PurgeOrder` 时销毁。
- 节点 MUST 在销毁后出签名回执，回执 MUST 列出被销毁的句柄集合。
- 销毁回执 MUST 由**发出方自己**签名；平台 MUST 核对回执声明的 `node` 与消息层已认证的发送方一致，
  并验证签名（形状合法不等于本人签）。任一不符即拒——否则任何已认证参与方都能替别家
  「宣布已销毁」，把作业推成 `PURGED`，而对方机器上可能还留着制品。
- 销毁 MUST 覆盖内存与临时盘；重复指令 MUST 返回同一回执。
- 销毁后按原句柄读取 MUST 失败。

#### Scenario: TTL 到期
- **WHEN** 节点内制品超过 TTL 而未收到销毁指令
- **THEN** 节点 MUST 自主销毁并出具 `ttl` 原因的回执

#### Scenario: 销毁后读取
- **WHEN** 销毁回执出具后按句柄读取节点内制品
- **THEN** 读取 MUST 失败

#### Scenario: 销毁覆盖临时盘
- **WHEN** 节点销毁某作业的制品并落盘本地状态
- **THEN** 落盘快照里 MUST 不再包含该制品与其载荷，重启（重新 hydrate）后也 MUST 读不到——
  「销毁」只有同时覆盖内存与落盘副本才算数

#### Scenario: 销毁回执被冒充
- **WHEN** 已认证发送方 A 提交的销毁回执里 `node` 写成 B（或签名不是 A 的私钥所签）
- **THEN** 平台 MUST 拒收（不得计入「已收到销毁回执」），作业 MUST NOT 进入 `PURGED`

### Requirement: 证明与执行事件的审计回执
节点 SHALL 为「解封、执行、出口、销毁」四类事件各出具一条签名回执，并以 `prev_receipt_hash` 成链。
- 回执内容 MUST 含证明摘要与度量（至少解封与执行两类事件）。
- 平台收链时 MUST **先认身份、再认签名、最后认连续性**：`receipt.signer` 必须就是消息层已认证的
  发送方（否则任何已认证参与方都能把记录写进**别人**的链，把对方的证据链打成 DoS，
  且随后会被锚定）；回执签名 MUST 能被该参与方证书公钥验过（`parseAuditReceipt` 只验形状，
  不验密码学签名）；断链 MUST 被拒绝并指出位置。
- 链头 MUST 可被平台与离线工具锚定与核验。

#### Scenario: 回执链断链
- **WHEN** 平台收到的节点回执其 `prev_receipt_hash` 与上一条不符
- **THEN** 平台 MUST 拒收该回执并指出断链位置

#### Scenario: 回执的 signer 被冒充
- **WHEN** 已认证发送方 A 提交的回执里 `signer` 写成 B（或签名用的是 A 之外的私钥）
- **THEN** 平台 MUST 拒收（`accepted:false` 并给出原因），MUST NOT 落库——
  记录不得被写进 B 的回执链
