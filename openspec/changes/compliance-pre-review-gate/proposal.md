## Why

「合规预审」页（`/space/atlas/compose`）能给出 L2 裁决（批准 / 需审批 / 驳回），但这个结果**没有进入任何实际流程**：
- 合约申请与审批不看它；
- RWS、FL 预测任务的准入不看它；
- SecretFlow 编排器虽然预留了「带组合 ID 先过 L2 裁决」的闸门，前端却从未传过这个 ID。

所以现在预审只是一个孤立页面，页面上也如实写着「仅供参考」。平台的真实流程是「数据产品 → 数字合约 → 任务」，合规裁决应当在这条链路上起约束作用，而不是游离在外。

同时，预审一旦变成真闸门，现有引擎的几个缺口就会直接产生后果：
- 风险维度（参与机构数、是否含人类遗传资源等）完全由申请方自报，也不会上调风险等级；
- medium 风险要求的保障级从不强制，裁决结论和页面上显示的「合规要求」自相矛盾；
- 创建预审时，服务端不校验所选能力对象是否存在、是否已落地。

这些必须在接入之前一并修正。

## What Changes

- **预审绑定合约**：
  - 药企申请合约时，必须引用一份自己的预审。
  - 平台按**当前** L2 规则，结合事实推导出的风险维度重新裁决，然后把裁决快照（预审 ID、裁决 ID、裁决结论、所用规则摘要、推导出的风险维度）写进合约，并计入合约哈希一起存证。
  - 裁决为驳回：不能发起申请。
  - 裁决为需审批：医院审批时必须显式确认，并填写理由，确认记录同样计入合约哈希。
- **任务准入复核**：创建 RWS、FL 预测、SecretFlow 任务时，对每份被引用的合约做三项检查：
  - 合约带有预审快照；
  - 任务的分析类型没有超出预审选定的能力对象范围（分析类型与能力对象的对应关系作为数据维护）；
  - 用事实推导的风险维度（参与机构数取任务实际涉及的医院数；数据敏感度取数据产品的分级标签）按当前规则重评：驳回即拒；需审批只有在合约里有医院显式确认时才放行。
- **SecretFlow 闸门来源改为合约**：闸门从合约快照取预审信息，不再依赖前端传组合 ID。
- **风险维度事实优先**：能从系统事实推导的维度一律推导，推导值与申请方自报不一致时，以推导值为准，并在裁决中注明来源（推导 / 自报）。
- **服务端校验预审组合**：所选场景和各层能力对象必须存在且已落地（`status = active`），否则拒绝创建。
- **L2 引擎修正（成为闸门的前提）**：
  - 风险维度可上调风险等级（例如参与机构 ≥ 3、含人类遗传资源 → high，对齐 `risk-high` 判定标准）；
  - 各风险等级都要求达到「所需保障级」；
  - 保障级的具体口径需要先做一项策略决策，见 design 的待决问题。
- **前端**：
  - 预审页新增「用此预审申请合约」；
  - 申请合约时选择预审；
  - 医院审批页展示裁决快照，需审批时须确认并填写理由；
  - 创建任务页显示每份合约的预审状态；
  - 接入完成后去掉「仅供参考」的提示。
- **治理文档**：FLOWS 增加「预审 → 合约申请」的步骤和准入复核；DOMAIN 登记合约上的预审快照字段和跨平面按值引用；TRUST 新增控制点；DECISIONS 登记「预审在合约层绑定、在任务层复核」以及保障级口径的决策。

## Capabilities

### New Capabilities
- `compliance-pre-review`：合规预审的服务端规则，包括：
  - 组合只能引用已落地的能力对象；
  - 风险维度事实优先，并标注来源；
  - 裁决快照的内容与摘要；
  - 引擎语义：维度上调风险、各风险等级都强制保障级；
  - 三类任务（RWS、FL 预测、SecretFlow）准入时统一复核预审。

### Modified Capabilities
- `digital-contract`：新增需求，不改动已有需求的原文，以免与 `connector-wasm-sandbox-disproportionality` 对同一需求的修改冲突：
  - 合约申请必须附预审，裁决快照计入合约哈希；
  - 裁决为「需审批」的合约，医院签发时必须显式确认。

## Impact

- **控制面 API**：
  - 合约服务：申请时引用预审并重新裁决；签发时对需审批的确认；规范化字段增加预审快照。
  - 准入服务：RWS、FL、SecretFlow 三处 `admit()` 统一调用预审复核。
  - L2 引擎与预审服务：维度上调风险、各级强制保障级、事实推导风险维度、校验能力对象是否已落地。
- **数据**：
  - 控制面合约表增加预审快照列和医院确认列；
  - 预审（`composition`）与裁决（`compliance_evaluation`）仍在主库，合约按值保存快照，不建跨平面外键；
  - 分析类型与能力对象的对应关系作为能力注册表的数据维护。
- **兼容性**：
  - 已有合约没有预审快照，按「未预审」处理，**不能用来创建新任务**（fail-closed）。
  - 演示种子合约在初始化时自动补上预审快照；用户自建的旧合约需要重新申请，不设宽限期（见 design D7）。
- **前端**：申请合约按钮、合约审批操作、预审页、三类任务的创建页。
- **测试**：驳回不能申请；需审批未确认不能签发；越出预审范围的任务被拒；推导维度覆盖自报；规则变严后，已签发合约下的新任务被拒；已有合约无快照时被拒；合约哈希覆盖预审快照。
