## Context

MedTrust 现状是中心化多租户数据平台:原始数据上传汇聚到中心库,隐私计算/区块链/国密作为模块挂在中心。proposal 已确定将定位翻转为**联邦可信数据空间**(数据不出域),并以**药企-医院 RWS(真实世界研究/药物警戒)**为最小切口。

**现有可复用资产**:国密 SM2/3/4(`security/crypto`)、Vault 密钥管理、TEE 模块(`privacy/tee`)、FISCO BCOS 存证(`blockchain`)、FHIR 适配(`fhir`)、审计日志(`audit`)。这些是数据空间需要的底层原语,只是当前装在了错误的(中心化)组织形态里。

**约束**:
- 连接器需能部署在医院内网 / 药企侧,与中心控制面网络隔离,仅通过受控通道通信。
- 医院对"原始数据不出院"是信任前提,不可妥协。
- 需对齐国家数据局《可信数据空间技术架构》(2025.4)三大核心能力,及医保试点四维规则(准入/授权/安全/审计)。

## Goals / Non-Goals

**Goals:**
- 跑通 RWS 最小闭环:1 药企 + 2 医院,药企对医院脱敏数据做信号检测/队列分析,**原始数据从未离开医院**,只回传聚合结果,结果哈希上链。
- 确立"中心控制面(瘦) + 本地连接器(重)"的部署与代码骨架,且骨架不可退化回中心化汇聚。
- 把 `data-asset` 拆为元数据目录、`access-request` 升级为持续使用控制(Usage Control)。

**Non-Goals(本变更明确不做):**
- 联邦学习(FL)多院联合训练通道——第一版只做 TEE 通道,FL 后置。
- 贡献挂钩的结算/激励(价值共创层)。
- 与其他数据空间的跨空间互联(仅在接口层预留,不实现)。
- 前端改造、生产级高可用、真实硬件 TEE 选型落地(见 Open Questions)。

## Decisions

### D1. 联邦连接器架构,而非中心化汇聚 + 隐私计算
**选择**:两个平面。中心控制面只持有元数据(目录/身份/合约/存证),原始数据永久留在各参与方本地连接器。
**理由**:这是"可信数据空间"与"数据中台"的分水岭,也是医院信任的前提。把隐私计算挂在中心化汇聚之上,数据已经出院,隐私计算只是补丁。
**备选**:中心化合规数据平台(数据脱敏后汇聚)——落地快,但本质是数据中介/沙箱,不满足"数据空间"定义,已在 brainstorm 中被否。

### D2. 连接器为独立可部署单元 `apps/connector`
**选择**:新建独立 NestJS 应用 `apps/connector`,不复用 `apps/api`。中心控制面继续用 `apps/api`(瘦身后)。
**理由**:连接器部署在医院内网,信任边界、依赖、发布节奏都与中心不同;独立单元强制划清"哪些代码能碰原始数据"。复用 `packages/database` 拆分出的连接器本地 schema。
**备选**:在 `apps/api` 内用模块开关区分中心/连接器模式——会让中心化假设继续渗透,正是要避免的退化路径。

### D3. RWS 第一版只走 TEE 通道
**选择**:药企提交分析逻辑(队列定义 + 脚本)→ 在医院连接器本地 TEE 内对脱敏数据执行 → 输出聚合结果。
**理由**:RWS 信号检测/队列统计本质是"在本地算一个聚合",机密计算比 FL 训练模型简单、单方即可、更贴场景。FL 适合多院联合建模,是第二通道。
**备选**:首版即上 Flower FL——增加多院同步与建模复杂度,偏离 RWS 的实际需求,推迟闭环验证。

### D4. Usage Control 取代一次性访问审批
**选择**:授权产物是一份**可强制执行的策略**(目的限定 = 药物警戒;留存 = 阅后即焚;输出 = 仅聚合;有效期)。策略下发到连接器的策略执行点(PEP),在每次计算时强制校验。
**理由**:对齐 IDS Usage Control 与医保试点"授权后全程可控"。`access-request` 的一次性审批模型无法约束数据流转后的用法。
**备选**:保留一次性审批 + 事后审计——授权后无强制约束,不满足"全程可控"。

### D5. 输出闸门(Output Gate)在连接器侧强制
**选择**:连接器侧对计算输出做差分隐私 / 小单元格抑制(如 n<5 抑制),只有通过闸门的聚合/信号/模型参数才能离开;原始行级数据物理上无出口。
**理由**:聚合结果也可能重标识(re-identification),闸门是数据不出域的最后保障。
**备选**:仅靠 TEE 隔离不做输出过滤——TEE 保护计算过程,但不防止"把原始数据当作'结果'导出"。

### D6. 上链只存证据,不存数据
**选择**:FISCO BCOS 上链内容 = 任务定义哈希、参与方、授权策略哈希、输入数据指纹、输出结果哈希、时间戳。链上无任何医疗数据。
**理由**:对齐医保试点"全流程日志上链";链是审计/不可抵赖层,不是存储层。

### D7. 数据库拆分,中心库不再汇聚原始数据
**选择**:`packages/database` 拆为「中心控制面元数据 schema」(目录/合约/身份/存证索引)与「连接器本地 schema」(本地数据 + 本地审计)。中心库可继续用 SQLite(元数据量小);连接器本地库由医院环境决定。
**理由**:物理隔离强制"中心无原始数据"。
**备选**:共用一个 DataSource——会再次诱导数据汇聚。

### D8. 国密用于连接器信任链
**选择**:连接器身份用 SM2 证书(中心 CA 签发),连接器↔中心、连接器↔连接器通信用国密加密 + SM3 完整性 + 签名。复用 `security/crypto`。
**理由**:对齐等保/国密合规,复用现有储备。

### 与官方《可信数据空间技术架构》对齐核对表
| 官方核心能力 | 本设计落点 | 本变更覆盖 |
|---|---|---|
| 可信管控 — 双认证/确权/分级分类 | `participant-identity` + PEP | ✅ 第一版 |
| 可信管控 — 使用控制/全程可控 | `usage-control`(D4) | ✅ 第一版 |
| 资源交互 — 连接器/数据目录 | `data-space-connector` + 元数据目录(D7) | ✅ 第一版 |
| 资源交互 — 跨空间互联 | 接口预留 | ⏳ 后置 |
| 价值共创 — 结算/激励 | — | ⏳ 后置 |
| 安全/审计 — 日志上链 | 存证(D6) | ✅ 第一版 |

## Risks / Trade-offs

- **真实硬件 TEE 难获取/难运维** → 第一版用可插拔 TEE 抽象层,先以软件机密计算(进程隔离 + 加密内存模拟)跑通闭环,硬件目标定为海光 CSV(见 D9),作为可替换实现。
- **连接器部署在医院内网,运维/信任成本高** → 第一版用容器化 + 中心远程下发任务、连接器主动外联(不开放入站),降低医院侧接入门槛;先做模拟数据 demo,再谈真实院侧部署。
- **重构 `data-asset`/`access-request` 破坏现有功能** → 采用 connector-first:新路径(连接器 + 新 data-asset 目录 + usage-control)独立跑通后,再切换/下线旧的中心化模块,避免半中心化的中间态。
- **聚合输出仍可能泄露隐私** → 输出闸门强制 DP 预算 + 单元格抑制;策略里声明输出类型,闸门按类型套用规则。
- **SQLite 不适合生产多方场景** → 中心元数据量小可暂用;生产前控制面迁 Postgres(`docker-compose` 已定义,当前未用)。本变更不强制迁移。
- **过度对齐国标导致首版过重** → 严守 Non-Goals,互联/结算只预留接口不实现;先证明"数据不出域出 RWS 结果"。

## Migration Plan

Connector-first,分阶段,旧中心化路径在新路径验证前不动:

1. **骨架**:建 `apps/connector` 空壳;拆 `packages/database` 为控制面/连接器两套 schema。
2. **连接器最小闭环**:连接器本地数据网关(FHIR)+ 本地脱敏 + TEE 抽象层(软件实现)+ 输出闸门;用模拟医院数据,本地跑通"输入分析逻辑 → 出聚合结果"。
3. **中心控制面瘦身**:`data-asset` 拆出元数据目录;新增 `usage-control`(策略产物 + 下发);`participant-identity` 双认证 + SM2 证书。
4. **端到端 RWS**:药企连接器发起任务 → 中心校验合约/授权 → 下发 2 个医院连接器 → 本地 TEE 执行 → 回传聚合 → 上链存证。
5. **切换**:验证通过后,下线旧的中心化 `data-asset` 汇聚与一次性 `access-request` 审批。

**回滚**:阶段 1-4 不触碰旧模块,可随时回退到现状;阶段 5 切换前保留旧路径开关。

## 已决问题(2026-06 调研后)

原 Open Questions 中 3 个已查清并定论,均以国家数标委(TC609)正式标准为准。

### D9. TEE = 软件机密计算抽象 → 硬件目标海光 CSV(非 SGX)
软件机密计算(进程隔离 + 加密内存)先行跑通闭环;硬件首选 **海光 CSV(Hygon)**,通过可插拔 TEE 抽象层接入。
**理由**:信创"应替尽替"(2027);海光 CSV 为 x86 兼容(迁移成本低)、内置国密加速(与本项目 SM2/3/4 栈一致)、在医疗/金融机密计算已有成熟案例。Intel SGX 为境外方案,不作首选;ARM 部署可选鲲鹏 iTrustee/蓬莱。

### D10. 连接器协议 = 对齐国家数据基础设施标准,不自创、不照搬 IDS
连接器与中心、连接器与功能节点的接口对齐国标系列,而非自定义或直接套 IDS-RAM:
- 《数据基础设施 接入连接器技术要求》NDI-TR-2025-05 —— 连接器标准能力:**身份认证、网络接入、数据交付、数据访问控制、日志、运行状态上报**
- 《数据基础设施 互联互通基本要求》NDI-TR-2025-02 —— 统一目录标识/统一身份登记/统一接口
- 《数据基础设施 用户身份管理和接入规范》NDI-TR-2025-03
- 《数据基础设施 数据目录描述规范》NDI-TR-2025-06
- 《可信数据空间 使用控制技术要求》TC609-6-2025-15 —— usage-control 的规范依据
- 《数据基础设施 安全能力通用要求》TC609-6-2025-13
**第一版**:实现上述接口形态即可;真实跨节点互联需经第三方"功能完整性/互操作性/安全"检测(后置),接口先对齐。

### 规范符合性修订(影响 specs,需后续对齐)
《可信数据空间 技术架构》(TC609-6-2025-01)正式稿明确:可信数据空间 = **服务平台 + 接入连接器**;服务平台 7 项最小功能(身份管理、接入连接器管理、目录管理、**数字合约管理**、空间管理、数据使用控制、可选国际互通网关);连接器 5 项(数据交付、数据资源管理、**数据产品管理**、数字合约管理、数据使用控制);核心技术体系 = **数字合约 + 使用控制**。

与本设计的差异,需在 specs 落实:
- 把 `usage-control` 拆成/升级为 **数字合约(digital contract) + 使用控制(usage control)** 两个概念——数字合约是授权载体,使用控制是其强制执行(对齐 TC609-6-2025-15)。
- 引入 **数据产品(data product)** 作为一等概念:连接器对外提供的是数据产品(含元数据/质量/用法),而非裸数据集;RWS 输出也按数据产品管理。
- `participant-identity` 对齐 NDI-TR-2025-03 的身份登记/认证接口。
