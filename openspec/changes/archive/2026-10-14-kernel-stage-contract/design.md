# 设计：契约上移与记录下移（TD-12 边界的两项结构性变更）

## D1 为什么「上移契约」而不是「继续镜像」

结构镜像只保证**单向**可赋值（应用 → 包）。而接线代码天然是**双向**的：包把上游行交回应用实现，
应用把结果交回包。双向就必然要 cast，cast 越多越容易把「类型对不上」误当成「运行时不匹配」。
把契约放进协议核（两边都依赖它）后，**同一份类型**在两侧共用，cast 消失。

## D2 契约放哪一层

- **执行器契约**（`StageInput` / `StageOutput` / handler / 执行器接口）→ `@medtrust/mdop`：零领域语义，
  连接器与行业包都必须看见它；
- **医疗记录类型**（`InternalRecord`，含 `conditions`/`medications`/`adverseEvents` 等字段）→ **行业包**：
  它是医疗领域知识，按 D-SPD-18 的纯度判据不该留在基座；连接器侧的非基座代码（`src/domain/*`）可以直接 import 包，
  基座契约只用中立记录类型。

## D3 迁移顺序（每步可编可验）

1. 协议核新增契约（纯新增，不动任何调用点）；
2. 连接器 `mdop-executor.ts` 改为 **from 协议核 re-export**（调用点不变，编译期暴露遗漏）；
3. 记录类型下移 + 执行器改中立类型；
4. 搬 `l15.ts`（**零 cast** 为验收判据）；
5. 评估 `seal.ts` / `l4.ts`：前者出域关键、后者绑共享运行时，各自按 TD-12 记录单独评估。

## D4 与 FL 迁移（tasks 7.2）的关系

本变更为 `FlPredictionTaskSpec` 的处置提供**中立契约**（规格视图可复用同一套形状约定），但不代替它：
DTO 搬家仍归 FL 迁移（它要动合并口径的类型面 + 等价性证据）。

## 风险

| 风险 | 缓解 |
|---|---|
| 契约上移改坏连接器执行器 | 顺序 1→2 是「新增 + 再导出」，调用点不动；编译期即发现 |
| 记录类型下移后基座出现医疗词 | 基座契约用中立 `Record<string, unknown>`；棘轮不增为硬判据 |
| 顺手把 `seal.ts`/`l4.ts` 也搬 | 本变更显式排除，避免在出域关键路径上冒险 |
