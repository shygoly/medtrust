## 目标

把场景识别、表单生成、数据依赖检查和合约申请从“由 LLM 临时决定调用哪个工具、传哪些 ID”收敛为“场景声明 + 确定性编排”。LLM 只负责意图识别、候选场景说明和结果解释，不生成用途编码、参与方、数据产品配对或合约条款。

## 统一入口原则

- 产品层提供**一个 AI 助手入口**，用户不需要先理解六个助手分别在哪里。
- 入口内部使用意图路由，把请求交给研究设计、访问合约、结果解读、平台运维、合规证据或医院码表中的一个助手配置。
- 统一的是交互、会话 ID、任务草稿、审计和交接；**不统一权限、工具与数据访问平面**。
- 每个助手配置必须分别声明 `plane`、`data-access`、`identity`、允许工具、输出校验和人工确认点，符合 AGENT.md 的平面治理规则。
- 路由器不得扩大权限。用户从研究设计进入合约编排时可以继承草稿，但合约工具仍重新检查角色、授权、合约依赖和人工确认。
- AI 助手属于跨旅程的平台能力，不再归在“研究与任务”分区下，也不按六个业务分区分别设置入口。

## 助手目录

| 助手 | 主要用户 | 适用环节 | 数据边界 | 主要产物 |
|---|---|---|---|---|
| 研究设计与可行性助手 | 药企医学、RWE、注册人员 | 研究问题、外部对照可行性、候选数据产品、Protocol/SAP 草稿 | 目录元数据，不绑定具体医院 | 设计草稿、候选数据源、假设与缺口 |
| 访问与合约编排助手 | 药企研究运营、医院合约管理员 | 多数据源依赖、双方合约包、审批进度、多轮草稿 | 目录、合约、授权元数据 | 合约包、审批状态、可提交场景草稿 |
| 结果解读助手 | 药企统计、医学、研究者 | 已发布 C3 结果的解释 | 仅白名单聚合结果；自托管推理 | 带事实清单的解读草稿 |
| 平台运维助手 | 空间运营、平台运维 | 任务状态、连接器心跳、证明有效期、错误码、发布检查 | 控制面元数据、脱敏日志 | 故障摘要、排查建议、配置差异 |
| 合规与监管证据助手 | 合规、监管、注册人员 | 预审材料、规则映射、执行凭证与证据缺口 | 规则、合约、凭证、已发布结果 | 审阅材料、缺口清单、证据索引 |
| 医院码表与接入助手 | 医院信息科、数据管理员 | 字段名、码表、版本、本体映射与接入问题 | metadata-only；不得接触患者行、MIC 或标识 | 映射契约草案、接入检查单 |

## 根因

- 系统提示词要求先查合约再配置任务，合约不可用时直接停止并返回合约卡，因此不会进入 `buildScenarioFormCard`。
- 单臂外部对照场景没有写死华山和瑞金，参数卡原本应从当前空间目录读取参与方和数据产品；生产会话中的“华山/瑞金”是模型根据产品名称自行推断，不是可审计的业务默认值。
- 首轮尚未确认试验方、试验产品、对照方和对照产品，合约预检缺少确定的数据源选择，导致模型先猜数据源、再查合约。
- 外部对照有两个独立数据源，但 `check_contract_status` 只有一个 `dataProductId`，且查询合约时没有传入 `requirements[]`。
- `contractRequirements` 只在提交工具里按双方数据源提取，没有进入场景定义，也没有复用于前置合约检查。
- 单合约卡生成器只接收一个数据产品，无法一次表达“华山试验臂合约 + 瑞金对照臂合约”。
- 同一 `sessionId` 已支持多轮消息持久化，模型默认会收到最近 20 条历史消息；但没有独立、结构化的场景草稿，超出窗口后仍可能丢失已选场景、数据源和合约状态。

### P0 合约包 ContractBundle

- [ ] 将 `ContractBundle` 定义为一等公民的**版本化治理聚合**，而不是新的法律签署主体；成员合约仍是签名、用途和数据产品授权的最终事实源。
- [ ] 定义不可变 bundle 结构：`bundleId`、`version`、`purpose`、`studyRef`、`members[]`、`effectivePolicySnapshot`、`status`、`createdAt`、`frozenAt`。
- [ ] 定义成员结构：`contractId`、`participantId`、`dataProductId`、`role`、`stageBindings[]`；禁止只靠数组位置解释合约用途。
- [ ] bundle 状态必须由成员合约派生，至少覆盖 `draft`、`partially_active`、`active`、`expired`、`revoked`、`terminated`；禁止人工直接写成 active。
- [ ] 定义组合策略规则：有效期取交集、`minCell` 取最大值、罕见病阈值取更严值、TEE 策略取最严格值、留存取更严要求。
- [ ] 对于由多份合约数据共同生成的 C3，结果接收方取所有相关成员合约的交集，不使用并集；只有所有数据方都允许的接收方才能获得组合结果。
- [ ] `allowed_ops` 按成员和阶段绑定，不采用一个全局并集替代逐源授权；每个封存阶段必须引用对应数据源合约。
- [ ] 保留 MDOP 面向多个成员合约的设计：作业同时保存 `contractBundleId`、`contractBundleVersion`、`contracts[]` 与 `contractBindings[]`，节点仍拿成员合约副本本地验签。
- [ ] 聚合或降密阶段绑定 `bundlePolicy`，不得继续使用 `contracts[0]` 代表整个合约包。
- [ ] 节点复核时必须确认：当前片段涉及的每个数据源都有对应成员合约，且片段使用的 operator、purpose、有效期、接收方和发布策略通过组合策略检查。
- [ ] 合约续签、成员增加或用途变化必须生成新 bundle version；已启动作业固定使用提交时的版本快照，不得随成员合约变化静默漂移。
- [ ] 任一成员撤销或过期时：新作业立即禁止；在途作业按统一撤销语义停止或完成当前批次，并写清对已产生制品、C3 和留存义务的处置。
- [ ] AI 助手、审批页面、任务详情和审计报告统一以 bundle 展示成员完成度、总体状态和待处理项，同时保留成员合约 ID。
- [ ] 兼容迁移期：现有 `contracts[]` 作业仍可读；新作业优先引用 bundle，接口同时回显 bundle version 与 member contracts，防止节点验签失去透明度。

### P0 MDOP Plan DSL

- [ ] 将 MDOP DSL 定位为面向人和 AI 的**声明式计划编排语言**，不是通用编程语言，也不直接作为执行格式。
- [ ] 保持 Canonical Logical Plan JSON 和物理计划为单一事实源；DSL 必须编译为 Canonical Plan，禁止新增绕过 schema、编译器和 plan_hash 的执行捷径。
- [ ] 先定义版本化的 `mdop.plan/v1` 封闭词汇表，覆盖 `purpose`、`applicant`、`sources`、`roles`、`contracts`、`contractBundle`、`operators`、`inputs`、`placement`、`release`、`ethics`、`budget`、`window` 和 `evidence`。
- [ ] 将数据源与参与方表达为角色引用或表单占位符，例如 `${trial}`、`${trialDataProduct}`，禁止在 DSL 中默认写死具体医院或数据产品 ID。
- [ ] 合约依赖必须显式声明到角色和数据源，支持引用 ContractBundle 及 member bindings；合同条款不得由 DSL 或 LLM 临场决定。
- [ ] DSL 只允许声明式引用、参数和有限枚举条件，不支持循环、任意脚本、文件访问、网络请求、动态代码、SQL 或条件表达式求值。
- [ ] 建立 `DSL → AST → Canonical Logical Plan → 物理计划` 的确定性编译链；同一 DSL、版本、表单值和目录状态必须产生相同的 plan_hash。
- [ ] 将 DSL 版本、模板 ID/版本、算子版本、编译器版本和 ContractBundle 版本纳入审计记录；影响语义的版本变化必须进入 plan_hash。
- [ ] 常见场景继续使用专用模板：队列计数、单臂外部对照、跨院去重、联邦预测和 C2 匹配至少各提供一个标准 DSL 示例。
- [ ] 模板可以由 DSL 声明或展开，但模板层仍负责场景必填项、跨字段约束和默认策略，禁止把所有场景压成一份自由 DSL。
- [ ] AI 只能生成标记为 `llm-draft` 的 DSL 草稿；必须经过 schema 校验、服务端模板展开、人工确认和方案冻结，不能直接提交为正式 MDOP 作业。
- [ ] DSL 解析错误必须返回行号、字段路径、封闭枚举候选和修复建议，不能只返回“JSON 非法”。
- [ ] 设计 DSL 版本迁移规则：新增可选字段保持向后兼容；删除字段、改变枚举语义或改变策略合并规则必须升级主版本，并保留旧版本解析器。
- [ ] `External` 或自定义算子必须通过版本化 operator registry 引用，禁止 DSL 携带源码、Wasm 字节或任意 URL。
- [ ] 为 DSL 增加可读的规范化与解释器输出，让人工审阅者能逐项看到“使用谁的数据、依据哪份合约、在哪个节点、允许哪些算子、输出约束是什么”。
- [ ] 将 MDOP DSL 与 Card/场景定义连接：Card 字段值填入 DSL 占位符，服务端从场景契约生成 DSL 草稿，不由 LLM 直接拼最终计划 JSON。

- [ ] 缺少合约时返回一张合约包卡，一次列出双方状态和操作，并保留用户已填参数。
- [ ] 合约包全部生效后继续提交作业；不得要求用户重新描述场景。
- [ ] 如果产品决定允许前置申请，则使用目录中的显式默认依赖生成合约包，仍不得阻断参数卡展示。

### P1 卡片与协议

- [ ] 新增 `contract_bundle` 卡片或在现有 `contract_approval` 上增加 `requirements[]` 与 `allocations[]`。
- [ ] 每行申请按钮携带 `scenarioId`、`role`、`participantId`、`dataProductId`、`purposeCode` 和冻结的请求条款。
- [ ] `request_contract` 支持单个依赖申请，并返回该依赖在 bundle 中的最新状态。
- [ ] 忽略模型回传的用途编码、参与方和数据产品；服务端只用场景声明与用户卡片值。

### P1 测试

- [ ] 快照测试：单臂外部对照提示词必须得到固定 form card JSON，字段顺序和默认值稳定。
- [ ] DSL schema 测试：未知字段、未登记算子、缺失数据源、错误角色引用、非法 placement 和越界参数均必须 fail-closed，并返回字段路径。
- [ ] DSL 编译测试：相同 DSL、版本和输入必须产生逐字节相同的 Canonical Plan、物理计划和 plan_hash；重复编译结果一致。
- [ ] 非图灵完备测试：循环、脚本、文件访问、网络请求、SQL、动态代码和任意表达式一律拒绝。
- [ ] 引用测试：DSL 不得通过默认值、数组第一项或标题相似度自动绑定医院、数据和合约；所有实体必须来自用户确认的表单值或明确引用。
- [ ] 模板一致性测试：模板输入和展开后的 DSL 编译结果一致，跨字段校验不能在两种路径中产生不同结论。
- [ ] AI 草稿测试：LLM 生成 DSL 后必须带 `llm-draft`，在人工确认和冻结前不能进入 MDOP 编译或获取执行凭证。
- [ ] 版本迁移测试：旧 DSL 版本在升级后仍能按原语义解析；语义变化必须拒绝无版本变更的旧计划。
- [ ] 合约包策略测试：成员合约有效期为不同区间时，bundle 有效期取交集；`minCell` 不同时取最大值；TEE 策略不同时取更严格值。
- [ ] 接收方测试：成员合约接收方不同时，组合 C3 只允许交集接收方；并集口径必须有负例证明被拒。
- [ ] 异质合约测试：两份合约的用途、有效期、算子、阈值和接收方不同，作业必须按成员与阶段正确绑定，不能只验证第一份。
- [ ] 合约包撤销测试：任一成员撤销后 bundle 不再 active，新作业被拒，在途作业按既定语义停止并保留审计。
- [ ] 合约包版本测试：成员续签后创建新版本，旧作业仍引用旧版本快照，plan_hash 与审计记录不漂移。
- [ ] 迁移兼容测试：只有 `contracts[]` 的旧作业仍可读取和执行；新 bundle 作业可由旧节点读取 member contracts，但不得丢失 bundle 绑定。
- [ ] 意图路由测试：六类意图各有正例、边界例和歧义例；歧义请求必须返回选择卡，不得静默选择。
- [ ] 权限隔离测试：从低权限助手切换到合约或运维助手时，必须重新执行角色和工具授权检查。
- [ ] 统一入口测试：同一会话可在研究设计、合约编排、结果解读之间交接草稿，但不得泄漏不同助手无权访问的数据。
- [ ] 运维安全测试：平台运维助手只能提出建议，不能直接执行重启、回滚、修改证明策略或触发销毁。
- [ ] 导航测试：AI 助手不再出现在“研究与任务”的二级菜单中，并作为全局工具位对所有获准角色可见。
- [ ] 路由迁移测试：`/space/chat` 永久重定向到 `/space/assistant`，命令面板能通过新名称和旧名称进入。
- [ ] 上下文深链测试：从数据产品、合约、任务和结果页进入 AI 助手时，当前对象与页面被正确填入草稿，且提示词载荷不越级。
- [ ] 多入口会话测试：全局入口打开后再从任务页上下文入口进入，仍落到同一会话和同一助手意图，除非用户明确新建会话。
- [ ] 数据源中立测试：提示词未指定医院时，表单必须展示目录内全部合规候选，不得预设华山或瑞金。
- [ ] 替代医院测试：选择任意两家有对应角色产品的医院时，合约预检和提交载荷必须按用户选择工作，不出现硬编码参与方。
- [ ] 多轮上下文测试：同一会话超过 20 条历史消息后，仍能根据 `ScenarioDraft` 恢复场景、双方数据源和未完成合约。
- [ ] 新会话隔离测试：新 `sessionId` 不得继承旧会话已选的参与方、数据产品、用途或合约状态。
- [ ] 合约矩阵测试：华山与瑞金各一份 active 合约时应判定 ready，不得返回 missing。
- [ ] 双缺失测试：返回一个包含两条依赖的合约包，不得只返回其中一方。
- [ ] 用途漂移测试：模型返回任意用途字符串时，服务端仍使用封闭枚举，契约卡不得出现自由文本用途。
- [ ] 生产复测：药企从自然语言开始，依次得到 form card、双合约包、合约生效、作业提交和结果页。

## 验收判据

- [ ] AI 助手作为全局一级能力可从一个稳定入口发现和进入，不再依附“研究与任务”分区。
- [ ] 业务页面可通过上下文动作打开同一助手，并把当前对象写入 `ScenarioDraft`；不同入口不会分裂会话。
- [ ] 不新增第七个侧栏分区，现有六分区导航约束和角色可见性测试保持通过。
- [ ] MDOP DSL 是声明式、版本化、非图灵完备的编排语言，能够确定性编译为现有 Canonical Logical Plan。
- [ ] AI 生成的计划只能是 `llm-draft`，经过 schema、模板、人工确认和冻结后才可能进入签名与执行链。
- [ ] DSL 中不存在默认医院、第一份数据产品或隐式合约选择；所有参与方、数据和合约均来自显式引用。
- [ ] DSL 版本、模板版本、合约包版本和 plan_hash 可以共同追溯，旧作业不因语言或模板升级而发生语义漂移。
- [ ] MDOP 作业可以引用一个 bundle version 和多个成员合约；每个数据源与封存阶段有确定性绑定。
- [ ] 聚合和降密阶段使用 bundle 的组合策略，不再以 `contracts[0]` 或节点“第一份覆盖合约”代替完整授权。
- [ ] 多合约 C3 的接收方、有效期、发布阈值和证明策略均按明确的最严/交集规则计算，并有异质合约负例覆盖。
- [ ] 任一成员合约撤销或过期时，bundle 状态与在途作业行为一致、可审计，且不产生静默续用。
- [ ] 用户从同一个入口提出六类需求时，系统能路由到正确助手；低置信度时询问用户而不是猜测。
- [ ] 六个助手共享会话和草稿，但各自的数据访问、工具和人工确认边界保持独立。
- [ ] 研究设计助手的候选数据源只有经用户确认后才能进入合约编排，且不得自动绑定医院。
- [ ] 对同一场景、同一目录和同一合约状态，form card JSON 与合约包 JSON 可重复生成且逐字段一致。
- [ ] 不指定医院时，助手只通过参数卡询问数据源，不默认查询或申请华山、瑞金或其他特定医院的合约。
- [ ] 多轮会话即使在 20 条消息窗口之外，仍能从持久化 `ScenarioDraft` 恢复用户已确认的场景和数据源。
- [ ] 外部对照不再出现“已有两份双签合约却报 missing”或“只生成一侧合约申请卡”。
- [ ] 模型输出变化不会改变用途编码、参与方、数据产品配对或合约条款。
- [ ] 报告中的产品可见性证据包含滚动后的 `03a / 03b` 截图，而不是只有目录首屏。
- [ ] 报告中的试验臂和对照臂合约截图分别对应 `56dc0834-...` 与 `f06ce079-...`，且字段与作业载荷逐项一致。
