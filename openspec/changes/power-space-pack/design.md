## Context

医疗空间 `sh-med` 已在运行，目录、合约和成员都挂在这个空间上。空间模型、协作实体、部署白名单和空间启用集已由 `space-and-pack-decoupling` 落地。电力这一册还没有被规格接受：仓库里的 `industries/power` 和启动种子是草稿，把空间标识、自动入域、已确权和出域计数写死了。

本设计把 proposal 里已经同意的交换方式落到现有对象上：一个电力空间、三个 `cp_collaboration`、目录元数据，以及复用基座的 TEE 与联邦编排。不新造合并位置。

## Goals / Non-Goals

**Goals:**

- 在同一部署中增加电力空间，仅该空间启用 `power` 包。
- 三个协作按应用固定合并点：TEE 内存、联邦协调方，或持有方连接器。
- 目录按 `homeSpace` 与协作过滤；公开门户继续只展示默认医疗空间。
- 草稿种子与本设计冲突的行为被替换，而不是在任务里接着扩。

**Non-Goals:**

- 不生成模拟曲线，不注入答案键，不把行级数据写入控制面。
- 不实现新的隐私计算运行时。TEE 用现有远程证明与密封输入；联邦训练用现有编排。
- 不冻结评分或填谷的具体数值算法。算子没有复现摘要之前拒绝执行。
- 不决定电力空间的法定治理主体，也不把隔离强度升到独立实例。
- 不编写电力合规册里的提高最小计数。出域沿用基座缺省最小计数，只强制「户表与政务派生结果只出聚合」。

## Decisions

### 1. 空间标识与包标识分开

电力包标识为 `power`，空间标识为 `hn-power`，显示名「河南电力可信数据空间」。材料中的场景是省级电网、交易和车网，空间标识取河南实证，避免和只覆盖郑州城市试点的标识混用。包标识与空间标识必须不同，否则白名单里的 `power` 会和空间 id 分不清。

备选：空间也叫 `power`。否决，因为启用集、白名单和空间 id 会撞车。备选：`zz-power`。否决，因为三个协作里的交易、断面和车网不是城市试点单方能持有的数据。

`hn-power` 是本部署里的空间记录，不表示已经获得该省的正式授权。治理主体名称仍可由运营方改显示名，不改空间 id。

### 2. 白名单维持部署配置，不写入缺省值

`DEFAULT_ALLOWED_PACKS` 保持只有医疗包。ali29 要同时跑两个空间时，由该部署把 `SPACE_PACKS` 设为 `med,power`。白名单含 `power` 时才注册电力包并确保 `hn-power` 存在，且该空间的启用集为 `["power"]`。白名单不含 `power` 时，不创建该空间，也不改 `sh-med` 的启用集。

白名单含 `power` 且 `sh-med.enabledPacks` 为空时，把它写成 `["med"]`，避免空启用集被界面当成「不过滤」。已有非空启用集保持不变。

备选：缺省白名单直接加上 `power`。否决，因为那会让每个只部署医疗的实例都装载电力包。

### 3. 三个协作用现有实体，补上产品列表

`cp_collaboration` 已有 `spaceId`、`name`、`participants`，没有产品列表。增加 `dataProductIds`（JSON 数组）。三个协作的 `spaceId` 都是 `hn-power`。参与方写入前必须已是该空间成员；种子不制造成员。

草稿里「把运营方和平台管理员自动加入两个空间」废止。入域仍走邀请或审批（D-SPD-14）。没有成员时，空间存在但只有运营方邀请之后才能进入。

### 4. 合并点映射到已有路径

| 合并点 | 实现 |
|---|---|
| TEE 内存 | 现有 TEE 节点的远程证明与密封输入。任务规格由电力包声明，输入在节点内销毁 |
| 联邦协调方 | 现有联邦编排。只有报量报价提交训练任务；协调方只收模型更新 |
| 持有方连接器 | 电网、聚合商、运营商各自的连接器本地计算。跨方收到的是合约允许的汇总值 |

明文发布不是全局开关。数字合约的输出约束里逐项列出允许明文离开的输入（断面裕度、净负荷、AGC、电价、备用需求）。缺项即视为不允许，比较改走 TEE。场站调节能力不进入这份列表。

控制面任务记录只保存合约标识、合并点、输出哈希和拒绝原因，不保存曲线或凭证。

### 5. 目录归属与确权

`CatalogService` 在有请求级空间上下文时按 `homeSpace` 过滤列表和单条读取。公开门户没有空间上下文，固定查询默认空间 `sh-med`。

电力产品由包内清单登记：`rightsConfirmed = false`，`recordCount = 0`，`homeSpace = hn-power`，并写入对应协作的 `dataProductIds`。持有方确权后才允许发布。连接器上报统计后才允许改 `recordCount`。回填只更新 `homeSpace` 为空的行；种子若发现同名产品已属于其他空间，跳过并记录告警。

草稿中「种子即已确权」废止。

### 6. 草稿代码的去留

`industries/power` 的包声明可以保留为装载骨架，但必须改到与本设计和规格一致：出域模板只声明聚合与基座缺省最小计数；算子 `declareOperators` 在没有摘要时返回空集。`PowerSpaceSeedService` 改为：仅白名单含 `power` 时确保空间与三个协作；不写自动成员；产品未确权且行数为 0；不覆盖已有 `homeSpace`。

## Risks / Trade-offs

- [空启用集被写成 `["med"]` 后，医疗空间开始按包过滤导航] → 只在白名单已经包含 `power` 且原启用集为空时写入；基座路由没有包标签，仍然可见。
- [合约漏写明文条款时，弃电和辅助服务全部进 TEE，延迟高于本地比较] → 这是缺省拒绝。需要明文的输入必须写在合约里，不能靠部署开关放开。
- [`dataProductIds` 与目录可能不一致] → 登记产品与写入协作列表放在同一事务；读取时丢掉不属于本空间的 id。
- [草稿种子已在某个环境把运营方写成了两个空间的成员] → 启动时只撤回 `hn-power` 上 `invitedBy = power-space-seed` 且主体类型为用户的行。`sh-med` 的成员行、以及后来人工邀请的成员不删。
- [算子长期没有摘要，场景无法跑出结果] → 规格要求的是拒绝执行而不是假结果。摘要登记是后续算子变更。

## Migration Plan

1. 先改种子与目录过滤，再在目标部署把 `SPACE_PACKS` 扩成 `med,power` 并重启 API。
2. 重启后确认 `sh-med` 的既有产品 `homeSpace` 不变，公开门户条数不增加，`hn-power` 下三个协作和未确权产品可见。
3. 回滚：把 `SPACE_PACKS` 改回 `med` 并重启。电力包不再装载。已写入的空间、协作和未确权产品留在库里，不参与医疗目录。不需要删行。

## Open Questions

- 电力空间的法定运营主体名称，是否替换显示名「河南电力可信数据空间」。空间 id `hn-power` 在本设计中保持不变。
- 户表与政务输出的最小计数是否要高于基座缺省。留给电力合规册，不在本变更改数。
