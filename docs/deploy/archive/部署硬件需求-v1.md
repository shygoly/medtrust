## 1. 结论

### 1.1 最小版本

| 位置 | 台数 | 单台规格 | 上面跑什么 |
|---|---|---|---|
| 平台（运营方） | **1** | **8 vCPU / 32 GB / 500 GB SSD** | nginx、Web（`:5020`）、API（`:5021`）、PostgreSQL 15、Vault、链 Sidecar（`:8090`） |
| 长安链共识节点 | **3** | **4 vCPU / 8 GB / 100 GB SSD** | 每台只跑 ChainMaker。三台分属三台物理机或三个可用区 |
| 每家医院 | **1** | **8 vCPU / 16 GB / 200 GB SSD** | NestJS 连接器 + Python agent + 本院 PostgreSQL。管理面只绑 `127.0.0.1` |

三块合计（尚无医院时）：**20 vCPU、56 GB 内存、800 GB SSD，4 台机器**。每增加一家医院，另加 **8 vCPU / 16 GB / 200 GB SSD**。

共识用 **RAFT**。三台里宕一台，链仍能出块。

### 1.2 可选项（默认不买）

| 可选项 | 增量 | 什么时候再加 |
|---|---|---|
| 平台拆成多机，API 两台，数据库主从 | 见 §4.1 | 医院持续增加到几十家，或要求控制面故障切换 |
| 链节点加大 | 每台升到 8 vCPU / 16 GB / 200–500 GB SSD | 日志和快照要长期留在节点上 |
| 第 4 台共识节点，共识改为 TBFT | 再加 1 台同规格 | 要求容忍一台共识节点作恶，而不只是宕机 |
| Flower 联邦聚合 | 1 台 4 vCPU / 8 GB / 100 GB SSD | 打开 L4 联邦学习 |
| MP-SPDZ 网关 | 1 台 8 vCPU / 16 GB / 100 GB SSD | 打开多方安全计算 |
| 可信空间节点 teeA | TDX 机型。试点 4 vCPU / 16 GB；并发上去后 8 vCPU / 32 GB；盘 100 GB | 打开 C2（数据以密文信封进入硬件飞地） |
| 证明校验 teeB | 4 vCPU / 8 GB / 50 GB，密钥进 Vault 或 HSM | 与 teeA 一起上。试点用过同规格 TDX 4 vCPU / 16 GB |
| 结果解读 LLMA | 已上线形态 2 vCPU / 8 GB；留余量则 4 vCPU / 16 GB。至强 AMX，盘 50 GB | 打开聚合结果的模型解读 |
| 医院加大或拆库 | 整机 8 vCPU / 32 GB / 500 GB；或库单独 4 vCPU / 16 GB / 1 TB | L4 与库同机，或脱敏队列明显超过 200 GB |
| 医院 GPU | 1 张 | 院内做真实联邦训练 |
| 独立跳板机 | 2 vCPU / 4 GB / 40 GB | 院方要求堡垒机与连接器分机 |
| Vault 三节点 | 3 台 2 vCPU / 4 GB / 50 GB | 密钥服务本身要容忍单机故障 |
| 独立监控机 | 2 vCPU / 4 GB / 200 GB | 指标和日志不放在平台机上 |

## 2. 分析

### 2.1 平台为什么最小是一台

控制面进程都是无状态或轻状态的：Next.js、NestJS、Vault、Java Sidecar。真正占磁盘和内存的是 PostgreSQL（业务库、控制面库可以放在同一实例的不同 database）。

同机内存大致是这样分的：

| 进程 | 内存 |
|---|---|
| 操作系统与 Docker | 2 GB |
| nginx + Web | 1 GB |
| API | 4 GB |
| PostgreSQL | 8 GB |
| Vault | 1 GB |
| Sidecar（JDK 17） | 2 GB |
| 余量（日志、镜像拉取、短时峰值） | 14 GB |
| **合计** | **32 GB** |

8 vCPU 给 API、数据库和 Sidecar 同时跑。存证写入频率低，Sidecar 不需要单独一台。

对话 Agent（`:5032`）不在最小集里。控制台的合约、任务、连接器流程不依赖它。要开时先放在这台平台机上，内存吃紧再随 §4.1 拆出去。

现网 ali29 把 Web、API、数据库和示范连接器放在一台机器上，链是 **solo 单节点**。D-RWS-3-b 写明 solo 是中心化背书，生产要多节点。最小版本保留「控制面一台」，把链换成三台。

### 2.2 链为什么最小仍是三台

业务对链的依赖只有存证：`storeAttestation` 写，`getBlockNumber` 读。合约是标准 Solidity，经 Sidecar 的 HTTP 接口（`/attest`、`/block-number`、`/health`）访问。TPS 很低，一条存证是哈希和元数据，不是病历。

节点数由共识决定，不由业务吞吐量决定：

- 三台用 RAFT，可以容忍一台宕机。
- ChainMaker 的 TBFT 按 3f+1 组织。要容忍一台节点作恶，需要四台。四台是可选项，不进最小集。
- 三台必须分开部署。放在同一台宿主机上，主机一停，容错就没有了。

单台 4 vCPU / 8 GB / 100 GB SSD 是 ChainMaker 节点的起步配置，也与 [`医院连接器独立部署准备.md`](../../医院连接器独立部署准备.md) §1 里链节点的最低一行一致。最小集里节点上只有 `chainmaker` 进程，Sidecar 留在平台机。100 GB 对存证状态足够；日志和快照要在节点上留很多年时，再升到 §4.2 的 200–500 GB。

节点之间走专网，时延尽量低于 10 ms（同城三个可用区），带宽至少 100 Mbps。P2P 和 RPC 留在 VPC 内。公网只到平台的 443，再到 Sidecar。

证书和私钥进 Vault（D-RWS-3-a）。

### 2.3 医院为什么单独一台，而且不跑链

连接器是数据面，放在医院 DMZ。一台机器上两个容器：

- NestJS 连接器：领任务、L1.5–L3、输出闸门。
- Python agent：L3 重计算与 L4 训练。

本地库用 PostgreSQL。生产路径不使用 SQLite。

[`医院连接器独立部署准备.md`](../../医院连接器独立部署准备.md) 写明：**最小接入是一台 8 vCPU / 16 GB / 200 GB SSD**，连接器和计算后端同机，即可跑通闭环。连接器进程本身可以更小（文档中的 4 vCPU / 8 GB / 100 GB 只覆盖 NestJS，不含 agent）。最小版本按完整闭环买，避免医院第一次做 L3 时再补机器。

演示加固里的容器限额（连接器 1 vCPU / 1 GB，agent 2 vCPU / 2 GB）是单机模拟两院时的上限，不是采购规格。同机还要给 PostgreSQL 和操作系统留内存，所以整机从 16 GB 起。

医院侧不部署共识节点、Vault、Flower、MPC。存证由平台链完成。院内飞地只有合约写明计算必须发生在医院硬件里时才采购，见 §4.4。

磁盘：系统和镜像约 40 GB，连接器状态库小于 10 GB，其余给脱敏队列。200 GB 覆盖文档中的起步队列。10 万级患者的 OMOP 常见为几十 GB；三甲全量检验会超过 200 GB，那时走 §4.5 拆库，接入前用本院行数估一次。

### 2.4 为什么联邦、MPC、机密计算、解读都不在最小集

这些能力在代码和现网里都有独立进程或独立 ECS，主路径不依赖它们：

| 能力 | 现网事实 | 最小集不包含的原因 |
|---|---|---|
| Flower | 独立服务 `:5023` | L1.5–L3 在医院连接器内完成。L4 才需要平台侧聚合 |
| MP-SPDZ | 独立网关 | 存证、合约、RWS 都不经过它 |
| teeA / teeB | 阿里云 g8i TDX，与 ali29 分开 | 当前院内执行的 `attestationLevel` 为 `software`。C2 要等硬件证明和真实 KMS |
| LLMA | 独立 ECS，2 vCPU / 8 GB，Qwen3-1.7B int4，OpenVINO，只听 `127.0.0.1:8000` | 解读挂了，结果页面仍在。未配置时接口返回 503 |

`fly-services/llm/fly.toml` 里的 L40S 与 7B 模型是另一条推理规格，不是 [`DEPLOY.md`](../../../DEPLOY.md) §4.4 已上线的那台。

医院连接器设 `NODE_ENV=production` 时，在硬件飞地接上之前，软件实现不能冒充 C2（进程会拒绝启动）。最小版本走院内计算、聚合结果出域，按软件隔离部署，不采购 TDX。

## 3. 最小版本明细

### 3.1 平台机

| 项 | 值 |
|---|---|
| 数量 | 1 |
| 规格 | 8 vCPU / 32 GB / 500 GB SSD |
| 系统 | Linux x86_64（Ubuntu 22.04 / 24.04 或同等），Docker 24+ |
| 运行时 | Node.js 20，PostgreSQL 15，JDK 17（仅 Sidecar），HashiCorp Vault |
| 进程 | nginx、`medtrust-web`、`medtrust-api`、PostgreSQL、Vault、ChainMaker Java Sidecar |
| 磁盘 | 系统与镜像、数据库、Vault 数据、日志共用这块 500 GB |
| 网络 | 对公网只开 443。API 与浏览器同源，由 nginx 转到本机 `:5021` |

PostgreSQL 至少覆盖两个库：`medtrust_api`、`medtrust_controlplane`。每日备份到另一块盘或对象存储；备份介质不计入这 500 GB。

### 3.2 三台共识节点

| 项 | 值 |
|---|---|
| 数量 | 3，禁止同宿主机 |
| 单台 | 4 vCPU / 8 GB / 100 GB SSD |
| 软件 | ChainMaker v2.3.0 |
| 共识 | RAFT |
| 容错 | 1 台宕机后仍可出块 |
| 网络 | 节点之间专网；不对公网暴露 P2P / RPC |
| 对外入口 | 平台机上的 Sidecar `:8090`，只给 API 用 |

### 3.3 每家医院

| 项 | 值 |
|---|---|
| 数量 | 每家 1 台 |
| 规格 | 8 vCPU / 16 GB / 200 GB SSD |
| 系统 | Linux x86_64，Docker 24+ / Compose v2+ |
| 进程 | `rws-worker`（NestJS，`:5022` 只在本机回环）、Python agent（院内网络）、PostgreSQL |
| 数据 | 只读脱敏视图或已导入的脱敏队列。原始库留在 HIS |
| 出站 | TCP 443 到平台域名，带宽 ≥ 10 Mbps |
| 入站 | 数据面不开。运维 SSH 可并在这台宿主上，密钥登录，源 IP 限制 |
| 身份 | 平台签发的 SM2 证书。私钥只在这台机器上 |

药企只消费结果、不提供数据时，不部署连接器。药企自己的数据要参与计算时，机器与医院相同。

### 3.4 最小集的网络关系

```
医院连接器  --仅出站 443-->  平台机 :443
                              ├─ Web / API / PostgreSQL / Vault
                              └─ Sidecar :8090
                                    │
                    专网            ├─ 共识节点 1
                                    ├─ 共识节点 2
                                    └─ 共识节点 3
```

医院防火墙只放行平台域名的 443 出站。这条审批通常比机器采购更慢，和采购并行。

## 4. 可选项明细

### 4.1 把平台拆开，并做控制面高可用

医院数量上来、或要求 API / 数据库单机故障后仍可服务时，用下面这组替换那一台 8 vCPU / 32 GB。链的三台不变。

| 机器 | 数量 | 规格 | 作用 |
|---|---|---|---|
| 接入 + Web | 1，可再加 1 台 | 4 vCPU / 8 GB / 100 GB | nginx 与 Next.js |
| API | 2 | 8 vCPU / 16 GB / 100 GB | NestJS 与长轮询。Sidecar 挂在其中一台 |
| PostgreSQL | 1 主 + 1 从 | 8 vCPU / 32 GB / 500 GB SSD | 主从切换与备份 |
| Vault | 1 | 2 vCPU / 4 GB / 50 GB | 从平台机上拆出。要容忍 Vault 单机故障时改为 §4.7 的三节点 |
| 监控 | 1 | 2 vCPU / 4 GB / 200 GB | 指标、日志、备份暂存 |

对话 Agent 放在 API 机器上即可，不必单独采购。

### 4.2 加大链节点

| 项 | 升级后单台 |
|---|---|
| CPU / 内存 | 8 vCPU / 16 GB |
| 磁盘 | 200 GB SSD；按长安链生产环境的常见余量则为 500 GB SSD |
| 台数 | 仍是 3，仍然分机 |

存证业务本身不会把磁盘撑满。加大是为了节点日志、快照和更长的本地保留。

### 4.3 第四台共识节点（TBFT）

再加 1 台，规格与当时的共识节点相同。共识从 RAFT 改为 TBFT 后，可以容忍一台节点作恶。合约和 Sidecar 的 HTTP 接口不变。

### 4.4 机密计算与结果解读

与控制面分开买，沿现网 teeA / teeB / LLMA 的拓扑。

| 机器 | 试点已验证 | 建议规格 | 磁盘 | 作用 |
|---|---|---|---|---|
| teeA | `ecs.g8i.xlarge`，4 vCPU / 16 GB，购买时勾选 TDX | 8 vCPU / 32 GB TDX | 100 GB | 可信空间节点，真实 quote。由中立第三方或监管侧运营 |
| teeB | 另一台 g8i.xlarge，另一个 VPC | 4 vCPU / 8 GB，密钥进 Vault 或 HSM | 50 GB | 证明校验与密钥释放 |
| LLMA | `ecs.g9i.large`，2 vCPU / 8 GB，至强 6 AMX | 4 vCPU / 16 GB AMX | 50 GB | OpenVINO，Qwen3-1.7B int4，只听本机 8000 |

试点里的 teeB 把密钥放在内存里，重启即丢。生产把密钥放到 Vault 或 HSM，再把校验服务指到那里。

TDX 实例需要机密虚拟机机型（阿里云 g8i 或同等能力）。普通云主机不能产出这类证明。

### 4.5 医院加大

| 场景 | 规格 |
|---|---|
| L4 与 PostgreSQL 仍同机 | 整机改为 8 vCPU / 32 GB / 500 GB SSD |
| 脱敏库超过几百 GB | 应用留 8 vCPU / 16 GB；库单独 4 vCPU / 16 GB / 1 TB SSD |
| 真实联邦训练 | 在 agent 那台加 1 张 GPU。[`医院连接器独立部署准备.md`](../../医院连接器独立部署准备.md) 对计算后端的生产建议是 16 vCPU / 32 GB 再加 GPU |
| 堡垒机必须分机 | 另加 2 vCPU / 4 GB / 40 GB，只做 SSH 跳转，不放业务数据 |
| 合约要求飞地在院内 | 另加海光 CSV 或 Intel TDX/SGX 机型，按当时机型选型。默认的可信空间节点在 §4.4，不放医院 |

### 4.6 联邦学习与 MPC

| 服务 | 规格 | 打开条件 |
|---|---|---|
| Flower | 1 台 4 vCPU / 8 GB / 100 GB | L4。表格模型、医院数量在几十家以内 |
| MP-SPDZ | 1 台 8 vCPU / 16 GB / 100 GB | 多方安全计算。CPU 占用高，与 API 分开 |

两台都放在运营方 VPC，医院不部署。

### 4.7 Vault 高可用与独立监控

| 项 | 规格 |
|---|---|
| Vault Raft | 3 台，每台 2 vCPU / 4 GB / 50 GB |
| 监控 | 1 台 2 vCPU / 4 GB / 200 GB。已在 §4.1 拆机时列入的，不要再买第二台 |

## 6. 采购时怎么加总

**只有平台和链（最小集）：** 4 台，20 vCPU，56 GB 内存，800 GB SSD。

**再加医院：** 每家 +1 台，+8 vCPU / 16 GB / 200 GB SSD。两家医院时是 6 台，36 vCPU，88 GB，1.2 TB SSD。

**可选项互不绑定。** 例如只加 Flower、不加 TDX，就只多 1 台 4 vCPU / 8 GB / 100 GB。把 §4 全部打开（平台拆机与主从、链升到 8 vCPU / 16 GB / 500 GB、第 4 共识节点、Flower、MPC、teeA、teeB、LLMA、Vault 三节点、监控、一家医院升到 32 GB / 500 GB）才是完整生产形态；那一档按当时要开的能力逐项加，不必一次买齐。
