## 1. 结论

### 1.1 最小版本

| 位置 | 台数 | 单台规格 | 上面跑什么 |
|---|---|---|---|
| 平台（运营方） | **1** | **8 vCPU / 32 GB / 500 GB SSD** | nginx、Web（`:5020`）、API（`:5021`）、PostgreSQL 15、Vault、链 Sidecar（`:8090`） |
| 长安链共识节点（自建链时） | **3** | **4 vCPU / 8 GB / 100 GB SSD** | 每台只跑 ChainMaker。三台分属三台物理机或三个可用区。**对接丝路数港区域节点存证时不需要这三台**，见 §4.9 |
| 每家医院 | **1** | **8 vCPU / 16 GB / 200 GB SSD** | NestJS 连接器 + Python agent + 本院 PostgreSQL。管理面只绑 `127.0.0.1` |

三块合计（尚无医院、自建链时）：**20 vCPU、56 GB 内存、800 GB SSD，4 台机器**。每增加一家医院，另加 **8 vCPU / 16 GB / 200 GB SSD**。

**存证走区域节点时（§4.9 的形态 B）**，共识节点为 0 台，最小版本变成 **平台 1 台 + 每家医院 1 台**：平台机合计 **8 vCPU / 32 GB / 500 GB**。这一减法是**条件性**的——三问（写 / 读 / 背书）未由对方接口文档确认之前，仍按上表采购。

共识用 **RAFT**。三台里宕一台，链仍能出块。

### 1.2 可选项（默认不买）

增量只有两种算法：**追加**是最小集原样保留、再买机器；**替换**是撤掉最小集里的某一台，改用下面的规格。功能和场景的展开在 §4。

| 可选项 | 增量 | 会用到的功能 | 典型场景 | 详见 |
|---|---|---|---|---|
| 平台拆机，API 两台，数据库主从 | **替换**平台那 1 台。改为 7 台：40 vCPU / 112 GB / 1.55 TB。净增多 6 台 | 登录、合约、长轮询领任务、结果汇总、存证入口 | 医院几十家同时在线，或控制面要能单机维护 | §4.1 |
| 三台链节点加大 | **替换**每台 4C/8G/100G。升到 8C/16G 后，三台净增 12 vCPU / 24 GB；盘升到 200G 或 500G | 仍是存证、区块查询、结算锚定。不增加新功能 | 节点日志和快照要在本地留多年 | §4.2 |
| 第 4 台共识节点 | **追加** 1 台，规格与当时的共识节点相同。共识改为 TBFT | 存证写入。容错从「防宕机」变为「防一台节点作恶」 | 三台分属不同机构，不能假设每家都诚实 | §4.3 |
| 跨组织 C2 节点 teeA + 校验 teeB（**中立第三方/监管侧**，非院内） | **追加** 2 台。生产建议 teeA 8C/32G TDX + teeB 4C/8G，合计 +12 vCPU / +40 GB / +150 GB | 跨机构逐人对齐后再统计：SCRI、疫苗效果、跨院去重、主体配对（密文信封出域、飞地内解密） | 两家数据缺一不可、又不能交换行级记录 | §4.4.1 |
| 结果解读 LLMA | **追加** 1 台。建议 4 vCPU / 16 GB / 50 GB（试点 2C/8G 已跑通） | 作业详情页「结果解读」草稿 | 研究者要一段只引用已发布数字的中文说明 | §4.4.2 |
| 医院内存与磁盘加大 | **替换**该院 8C/16G/200G 为 8C/32G/500G。净增 16 GB 内存、300 GB 盘 | 本院 L3 因果重计算、L4 / SecretFlow 训练 | 训练和本地库同时占内存 | §4.5.1 |
| 医院数据库拆出 | **追加** 1 台 4 vCPU / 16 GB / 1 TB。应用机仍是 8C/16G | 连接器读本院脱敏库做纳排和取数 | 脱敏 OMOP 或检验宽表超过 200 GB | §4.5.2 |
| 医院 GPU | **追加** 1 张训练卡到该院 agent 所在机器。表格模型按 16 GB 显存准备 | 本院 SecretFlow / L4 的 torch 训练 | CPU 训一轮的时间不可接受 | §4.5.3 |
| 医院独立跳板机 | **追加** 1 台 2 vCPU / 4 GB / 40 GB | 无业务功能。SSH、升级、看日志 | 院方要求堡垒机与连接器分机 | §4.5.4 |
| 院内硬件飞地 | **追加** 1 台海光 CSV 或 Intel TDX/SGX，规格按当时机型 | 合约指定计算发生在本院硬件里 | 医院要求密文投影也不能离开本院网络 | §4.5.5 |
| Flower 聚合机 | **追加** 1 台 4 vCPU / 8 GB / 100 GB | `/api/v1/flower` 联邦训练的 FedAvg 聚合 | 多院同时训一个模型，且聚合不要占 API 的 CPU | §4.6.1 |
| 对话 Agent | **追加** 0 台（先叠在平台机，约 2 GB）；要隔离再加 1 台 2C/4G/40G | 研究设计、合约、码表、运维、合规证据助手 | 研究者用中文描述队列，生成任务草稿 | §4.8 |
| Vault 三节点 | **追加** 3 台 2 vCPU / 4 GB / 50 GB（若 §4.1 已拆出 1 台，再加 2 台） | SM2 发证、密钥读取、链证书 | 密钥服务要在单台维护时继续可用 | §4.7.1 |
| 独立监控 | **追加** 1 台 2 vCPU / 4 GB / 200 GB。§4.1 已含则不要再买 | 无业务功能。健康检查、磁盘、日志留存 | 审计日志保留期长，不能挤占数据库磁盘 | §4.7.2 |

**已明确不采购：MPC 网关（MP-SPDZ）。** 跨院聚合走 MDOP 的 `secure_aggregate` 算子（`apps/connector/src/mdop/aggregation/`），在连接器与平台通道内完成，不需要额外机器。它的性质要写准：**对平台保密、对参与方不保密**——每家连接器用各参与方公钥各封一份（`ciphertext.ts#sealContribution`），因此每家都能解开别家的贡献明文。若业务要求参与方之间也互不可见，要改的是连接器的聚合实现（加性掩码 / 同态加法），仍不需要机器；只有出现通用安全电路需求（PSI 以外的自定义电路）才另立项，见 §4.6.2。

药企只看汇总数字的场景由**出域闸门**把关（合约 `outputPolicy` 的 `minCell` / `minCellRare`），不依赖 MPC。这条边界的风险不在「谁算的」，而在「能不能被多轮查询反推」，见 §4.6.2 末段。

## 2. 分析

### 2.1 平台为什么最小是一台

控制面进程都是无状态或轻状态的：Next.js、NestJS、Vault、Java Sidecar。真正占磁盘和内存的是 PostgreSQL（业务库、控制面库可以放在同一实例的不同 database）。

同机内存大致是这样分的：

| 进程 | 内存 |
|---|---|
| 操作系统与 Docker | 2 GB |
| nginx + Web | 1 GB |
| API | 4 GB |
| PostgreSQL | 8 GB |
| Vault | 1 GB |
| Sidecar（JRE 17） | 2 GB |
| 余量（日志、镜像拉取、短时峰值） | 14 GB |
| **合计** | **32 GB** |

8 vCPU 给 API、数据库和 Sidecar 同时跑。存证写入频率低，Sidecar 不需要单独一台。

对话 Agent（`:5032`）不在最小集里。控制台的合约、任务、连接器流程不依赖它。要开时先放在这台平台机上，内存吃紧再随 §4.1 拆出去。

现网 ali29 把 Web、API、数据库和示范连接器放在一台机器上，链是 **solo 单节点**。D-RWS-3-b 写明 solo 是中心化背书，生产要多节点。最小版本保留「控制面一台」，把链换成三台。

### 2.2 链为什么最小仍是三台

业务对链的依赖只有存证：`storeAttestation` 写，`getBlockNumber` 读。合约是标准 Solidity，经 Sidecar 的 HTTP 接口（`/attest`、`/block-number`、`/health`）访问。TPS 很低，一条存证是哈希和元数据，不是病历。

节点数由共识决定，不由业务吞吐量决定：

- 三台用 RAFT，可以容忍一台宕机。
- ChainMaker 的 TBFT 按 3f+1 组织。要容忍一台节点作恶，需要四台。四台是可选项，不进最小集。
- 三台必须分开部署。放在同一台宿主机上，主机一停，容错就没有了。

单台 4 vCPU / 8 GB / 100 GB SSD 是 ChainMaker 节点的起步配置，也与 [`医院连接器独立部署准备.md`](../医院连接器独立部署准备.md) §1 里链节点的最低一行一致。最小集里节点上只有 `chainmaker` 进程，Sidecar 留在平台机。100 GB 对存证状态足够；日志和快照要在节点上留很多年时，再升到 §4.2 的 200–500 GB。

节点之间走专网，时延尽量低于 10 ms（同城三个可用区），带宽至少 100 Mbps。P2P 和 RPC 留在 VPC 内。公网只到平台的 443，再到 Sidecar。

证书和私钥进 Vault（D-RWS-3-a）。

### 2.3 医院为什么单独一台，而且不跑链

连接器是数据面，放在医院 DMZ。一台机器上两个容器：

- NestJS 连接器：领任务、L1.5–L3、输出闸门。
- Python agent：L3 重计算与 L4 训练。

本地库用 PostgreSQL。生产路径不使用 SQLite。

[`医院连接器独立部署准备.md`](../医院连接器独立部署准备.md) 写明：**最小接入是一台 8 vCPU / 16 GB / 200 GB SSD**，连接器和计算后端同机，即可跑通闭环。连接器进程本身可以更小（文档中的 4 vCPU / 8 GB / 100 GB 只覆盖 NestJS，不含 agent）。最小版本按完整闭环买，避免医院第一次做 L3 时再补机器。

演示加固里的容器限额（连接器 1 vCPU / 1 GB，agent 2 vCPU / 2 GB）是单机模拟两院时的上限，不是采购规格。同机还要给 PostgreSQL 和操作系统留内存，所以整机从 16 GB 起。

医院侧不部署共识节点、Vault、Flower、MPC。存证由平台链完成（走区域节点时由对端承担，见 §4.9）。院内飞地只有合约写明计算必须发生在医院硬件里时才采购，见 §4.5.5。

磁盘：系统和镜像约 40 GB，连接器状态库小于 10 GB，其余给脱敏队列。200 GB 覆盖文档中的起步队列。10 万级患者的 OMOP 常见为几十 GB；三甲全量检验会超过 200 GB，那时走 §4.5 拆库，接入前用本院行数估一次。

### 2.4 为什么联邦、MPC、机密计算、解读都不在最小集

这些能力在代码和现网里都有独立进程或独立 ECS，主路径不依赖它们：

| 能力 | 现网事实 | 最小集不包含的原因 |
|---|---|---|
| Flower | 独立服务 `:5023` | L1.5–L3 在医院连接器内完成。L4 才需要平台侧聚合 |
| MP-SPDZ | 独立网关 | 存证、合约、RWS 都不经过它 |
| teeA / teeB | 阿里云 g8i TDX，与 ali29 分开；**放置在中立第三方/监管侧，不在院内** | 当前院内执行的 `attestationLevel` 为 `software`。C2 要等硬件证明和真实 KMS |
| LLMA | 独立 ECS，2 vCPU / 8 GB，Qwen3-1.7B int4，OpenVINO，只听 `127.0.0.1:8000` | 解读挂了，结果页面仍在。未配置时接口返回 503 |

`fly-services/llm/fly.toml` 里的 L40S 与 7B 模型是另一条推理规格，不是 [`DEPLOY.md`](../../DEPLOY.md) §4.4 已上线的那台。

医院连接器设 `NODE_ENV=production` 时，在硬件飞地接上之前，软件实现不能冒充 C2（进程会拒绝启动）。最小版本走院内计算、聚合结果出域，按软件隔离部署，不采购 TDX。

## 3. 最小版本明细

### 3.1 平台机

| 项 | 值 |
|---|---|
| 数量 | 1 |
| 规格 | 8 vCPU / 32 GB / 500 GB SSD |
| 系统 | Linux x86_64（Ubuntu 22.04 / 24.04 或同等），Docker 24+ |
| 运行时 | Node.js 20，PostgreSQL 15，JRE 17（仅 Sidecar 运行时），HashiCorp Vault |
| 进程 | nginx、`medtrust-web`、`medtrust-api`、PostgreSQL、Vault、ChainMaker Java Sidecar |
| 磁盘 | 系统与镜像、数据库、Vault 数据、日志共用这块 500 GB |
| 网络 | 对公网只开 443。API 与浏览器同源，由 nginx 转到本机 `:5021` |

PostgreSQL 至少覆盖两个库：`medtrust_api`、`medtrust_controlplane`。每日备份到另一块盘或对象存储；备份介质不计入这 500 GB。

### 3.2 三台共识节点

| 项 | 值 |
|---|---|
| 数量 | 3，禁止同宿主机 |
| 单台 | 4 vCPU / 8 GB / 100 GB SSD |
| 软件 | ChainMaker v2.3.0 |
| 共识 | RAFT |
| 容错 | 1 台宕机后仍可出块 |
| 网络 | 节点之间专网；不对公网暴露 P2P / RPC |
| 对外入口 | 平台机上的 Sidecar `:8090`，只给 API 用 |

**前提**：本节成立的前提是**自建链**。若存证改由丝路数港区域节点承载（§4.9 形态 B），本节三台不采购，Sidecar 从「连自己的节点」改为「连区域节点的存证接口」；三问未确认前仍按本节采购。

### 3.3 每家医院

| 项 | 值 |
|---|---|
| 数量 | 每家 1 台 |
| 规格 | 8 vCPU / 16 GB / 200 GB SSD |
| 系统 | Linux x86_64，Docker 24+ / Compose v2+ |
| 进程 | `rws-worker`（NestJS，`:5022` 只在本机回环）、Python agent（院内网络）、PostgreSQL |
| 数据 | 只读脱敏视图或已导入的脱敏队列。原始库留在 HIS |
| 出站 | TCP 443 到平台域名，带宽 ≥ 10 Mbps |
| 入站 | 数据面不开。运维 SSH 可并在这台宿主上，密钥登录，源 IP 限制 |
| 身份 | 平台签发的 SM2 证书。私钥只在这台机器上 |

药企只消费结果、不提供数据时，不部署连接器。药企自己的数据要参与计算时，机器与医院相同。

### 3.4 最小集的网络关系

```
医院连接器  --仅出站 443-->  平台机 :443
                              ├─ Web / API / PostgreSQL / Vault
                              └─ Sidecar :8090
                                    │
                    专网            ├─ 共识节点 1
                                    ├─ 共识节点 2
                                    └─ 共识节点 3
```

医院防火墙只放行平台域名的 443 出站。这条审批通常比机器采购更慢，和采购并行。

## 4. 可选项明细

每一项都按同一顺序写：**增量**（相对最小集多买或换掉什么）、**功能**（控制台或接口里哪条路径会走到这台机器）、**场景**（什么业务才需要）、**不上时**（最小集仍然提供什么）。

### 4.1 把平台拆开，并做控制面高可用

**增量：替换。** 撤下平台那 1 台 8 vCPU / 32 GB / 500 GB，改成下面 7 台。链的三台不动。

| 机器 | 数量 | 规格 | 作用 |
|---|---|---|---|
| 接入 + Web | 1（可再加 1 台做入口冗余） | 4 vCPU / 8 GB / 100 GB | nginx 与 Next.js |
| API | 2 | 8 vCPU / 16 GB / 100 GB | NestJS 与连接器长轮询。Sidecar 挂在其中一台 |
| PostgreSQL | 1 主 + 1 从 | 8 vCPU / 32 GB / 500 GB SSD | 业务库与控制面库。从库用于切换和备份 |
| Vault | 1 | 2 vCPU / 4 GB / 50 GB | 从应用机拆出。密钥本身要多副本时再按 §4.7.1 扩成三台 |
| 监控 | 1 | 2 vCPU / 4 GB / 200 GB | 指标、日志、备份暂存 |

替换后合计 **40 vCPU / 112 GB / 1.55 TB，7 台**。相对最小集的那一台，净增 **6 台、32 vCPU、80 GB 内存、约 1 TB 磁盘**。

**功能。** 这组机器承接最小集里平台机的全部功能，只是拆开并多一份热备：

- 控制台登录，以及提供方、使用方、运营方、合规、管理员五种角色的页面。
- 数字合约的起草、要约、医院侧审批、使用控制。
- 连接器长轮询领任务、回传聚合结果。
- 任务状态、结算记录写入数据库。
- 存证请求进入 Sidecar，再由 Sidecar 发给三台共识节点。

**场景。** 同时在线的医院到几十家，每家连接器都保持最长约 25 秒的长轮询，API 和数据库开始互相抢 8 个 vCPU。或者合同要求控制面一台机器维护、重启时，登录和领任务仍可用。主库磁盘故障时，从库可以接管，缩短停写时间。

**不上时。** 最小集那一台继续提供上面全部功能。它重启或磁盘故障期间，控制台、领任务和新的存证会停；三台链还在，只是没有 API 就不会有新交易。

对话 Agent 放在两台 API 之一即可，不必为它再买机器。规格见 §4.8。

### 4.2 加大三台链节点

**增量：替换。** 三台都还在，每台从 4 vCPU / 8 GB / 100 GB SSD 升到 8 vCPU / 16 GB。磁盘升到 200 GB，或按长安链生产环境常见余量升到 500 GB。

| 磁盘档 | 三台净增 |
|---|---|
| 升到 200 GB | +12 vCPU、+24 GB 内存、+300 GB 磁盘 |
| 升到 500 GB | +12 vCPU、+24 GB 内存、+1.2 TB 磁盘 |

**功能。** 不增加新功能。仍然是这些已有路径在写链：

- 合约与任务关键事件的哈希存证（`storeAttestation`），控制台查看区块高度。
- 结算记录的链上锚定。
- 若以后打开 §4.4.1，证明摘要也会记到同一条链上。

一条存证是哈希和时间戳，不是病历。按存证的写入量，4 vCPU / 8 GB 的节点足够出块。

**场景。** 审计要求节点日志、区块库和快照在共识节点本地保留数年；100 GB 会被日志先占满。或者三台节点除了 `chainmaker` 之外还要留出运维代理、备份进程的内存。

**不上时。** 三台 4 vCPU / 8 GB / 100 GB 继续按 RAFT 出块，宕一台仍可写。

### 4.3 第四台共识节点（TBFT）

**增量：追加 1 台**，规格与当时三台共识节点相同（最小集是 4 vCPU / 8 GB / 100 GB；若已做 §4.2，则与加大后的规格相同）。共识算法从 RAFT 改为 TBFT。合约字节码和 Sidecar 的 `/attest`、`/block-number`、`/health` 不用改。

**功能。** 存证、结算锚定、区块查询这些功能不变。变的是容错语义：四台按 3f+1 组织，可以在一台节点给出错误区块时仍由其余节点达成一致。

**场景。** 四台节点分属平台运营方、两家参与机构和一家监管或公证机构，任何一家都可能停机，也可能运行被改过的节点程序。三台 RAFT 只能覆盖「一台宕机」；「一台仍在线但行为错误」要第四台。

**不上时。** 三台 RAFT 继续服务。一台宕机时链仍出块。

### 4.4 机密计算与结果解读

这两项都追加在运营方侧，与控制面、链分开。teeA 和 teeB 必须成对；LLMA 可以单独加。

#### 4.4.1 跨组织 C2 节点（中立第三方 teeA + 证明校验 teeB）

> **这是默认放置。** 飞地放在**中立第三方或监管侧**，不放在医院内；医院侧的「本院飞地」是 §4.5.5 的例外，
> 只解决内部信任、**不承担跨组织对齐**。两处都叫「TEE」，别混。

**增量：追加 2 台。** 最小集的平台机和三台链都保留。

| 机器 | 试点已跑通 | 生产建议 | 磁盘 | 放置 |
|---|---|---|---|---|
| teeA | 阿里云 `ecs.g8i.xlarge`，4 vCPU / 16 GB，购买时勾选 TDX | 8 vCPU / 32 GB 的 TDX 机型 | 100 GB | 中立第三方或监管侧的 VPC。医院连接器只出站把密文信封送到这里 |
| teeB | 另一台 g8i.xlarge，另一个 VPC | 4 vCPU / 8 GB | 50 GB | 与 teeA 不同的信任域。负责验 quote、按证明释放密钥 |

**出域形态与定性（别写成「明文出域」，也别写成「数据没出医院」）。**

进出 teeA 的是**密文信封**，不是明文：信封里是密文 + 密文摘要 + 被包裹的数据密钥引用 + 使用策略（合约 / 用途 / 允许算子 / 证明策略 / `export=C3_only` / 到期）+ 水印 + 持有方签名，`aad` 绑定作业、凭证、合约（换一项就解不开）。解密只发生在通过远程证明的飞地内。

但**法律定性仍是「数据出域 / 委托处理」**（`REGULATORY.md` REG-08），理由不是「明文离开」，而是：

1. 数据离开数据控制者（医院）的控制边界，解密与计算发生在院外；
2. 控制者仍是医院、处理者变成节点运营方 → 需书面委托协议、明确控制者/处理者关系；
3. 可核查性路径改变：原始记录在院内可现场核查，出域后要在加密执行环境里另做方案。

**所以「密文出域」不等于「谁都解不开」。** 风险取决于**谁持钥**，不是传输是否加密：

| 运营方 | 数据密钥归属 | 实际保护 |
|---|---|---|
| 中立第三方 / 监管侧 | 医院（或共管） | 跨组织信任：双方都不必信任对方，也不必信任平台 |
| **平台（运营方）** | **平台** | **禁止**（D-TEE-1）：平台持钥 = 密文等同明文 |
| 平台（运营方） | 医院 | 平台读不到明文，但仍有运营层能力：度量白名单/版本回滚、可用性、拒绝续期、访问模式与侧信道、KMS 请求元数据 |

结论：平台可以运营 teeA，但**不得持有数据密钥**；密钥由数据持有方自建或共管（D-TEE-1）。表述统一写成**「密文信封出域、飞地内解密、只出 C3 聚合；定性为委托处理」**。

**「不能挪作他用」的真实含义。** TEE 保证的不是「数据只能用于某个业务算法」，而是**「解密密钥只释放给被度量、且在策略内的代码」**——这是同一件事在技术上的可达形态：

- **谁能解开**：度量在白名单（注册中心签名）、TCB ≥ `min_tcb`、证明未过期、凭证与合约有效；
- **何时给钥**：KMS 按 `evaluateKeyRelease` 释放，密钥用证明报告里的**一次性公钥**封装，只活在该实例内存；
- **能给谁用**：`aad` 绑定作业/凭证/合约（换作业即解不开），`export=C3_only` 限定出口形态；
- **可追溯**：释放凭据带摘要、会话有见证、关键事件可锚定到链。

**它不保证**：① 代码本身正确——测得出「是这段代码」，测不出「这段代码有没有 bug」；② 语义用途——「科研 vs 营销」要靠合约与出域闸门，TEE 不认识业务词；③ 可用性——运营方仍可拒绝服务、限流、断网；④ 侧信道——TDX/SEV-SNP 不防护内存访问模式（`TRUST.md` P-CTL-8 已记）。

因此「不能滥用」由四件事共同构成：**证明 + 引用值**（能跑什么）、**KMS 释放策略 + 密钥归属分离**（何时给钥）、**可复现构建 + 白名单签名**（跑的是什么）、**出域闸门 + 存证**（出去什么）。TEE 只是第一件；若运营方同时持钥或能改白名单，其余三件全部失效——这正是 D-TEE-1 要求运营权与密钥释放权分离的原因。

按生产建议，净增 **12 vCPU / 40 GB / 150 GB，2 台**。只做与试点同等的单作业验证时，两台都用 4 vCPU / 16 GB 即可，净增 8 vCPU / 32 GB / 150 GB。

TDX 必须买机密虚拟机机型（阿里云 g8i 或具备同等能力的实例）。普通云主机开不了这类证明。试点的 teeB 把已托付的密钥放在内存里，进程一重启就丢，在途作业要重提。生产把密钥放到 Vault 或 HSM，teeB 只做校验和按策略释放。

**功能。** 合约里写了证明策略（`attestation_policy`）的作业，才会把密文投影送进 teeA。节点内已落地、并且设计上要在飞地里做的算子：

| 算子 | 功能 |
|---|---|
| `rws.vaccine-scri` | 自身对照风险期（SCRI）：按人比较接种日后的风险期与接种前的对照期 |
| `rws.ve-tnd` | 检测阴性设计：按人比较检测日与末剂接种日，得到保护效果 |
| `rws.dedup-incidence` | 多家医院的人、观察期、事件做并集和去重，再算发病率 |
| `rws.paired-cohort` | 跨院主体配对，把两边的字段按人对齐 |
| `rws.distinct-count` | 分层去重人数 |
| 服务计算流水线 | 语料以密文落在节点上，多个算子在飞地内分步执行，到期销毁 |

出飞地的只有过了小单元格审查的聚合结果。证明摘要可以再锚定到 §3.2 的链上。

**场景。** 计算必须看到两个机构的行，而任何一方都不把行交给对方，也不交给平台明文库：

1. **疫苗不良反应主动监测。** 疾控有接种日期，医院有就诊事件日期。风险期是否命中，要逐人做日期差。这条已在 Intel TDX 上跑通过。
2. **疫苗真实世界保护效果。** 疾控有接种史，医院有检测结果。是否「检测前至少 14 天完成接种」同样要逐人比日期。
3. **跨院去重的发病率与罕见病登记。** 同一患者在两家医院都有记录，直接把两家的人数相加会重复计数。去重要看到两边的人，又不能把名单交换出来。
4. **跨院主体配对。** 暴露在一家、结局在另一家，配对统计发生在飞地内。

**不上时。** 各院在自己连接器里算完、只把计数或效应量交出来的路径继续可用，包括药物警戒四格表（L1.5）、多中心 Meta（L2）、单院数据足以完成的因果分析（L3）。上面四个场景没有 teeA / teeB 就没有执行位置。

#### 4.4.2 结果解读 LLMA

**增量：追加 1 台。** 与 teeA 无关，可以只买这一台。

| 档 | 规格 | 说明 |
|---|---|---|
| 试点已上线 | 2 vCPU / 8 GB / 50 GB，至强 6（AMX） | OpenVINO Model Server，模型 `Qwen3-1.7B-int4`，只听 `127.0.0.1:8000` |
| 建议 | 4 vCPU / 16 GB / 50 GB，同样要 AMX | 同一模型留出并发解读的余量 |

净增按建议档是 **4 vCPU / 16 GB / 50 GB，1 台**。`fly-services/llm/fly.toml` 里的 GPU 与 7B 模型不在这条已上线路径上，不要按那份配置采购。

平台 API 经 SSH 隧道访问这台机器的本机端口。推理机不进 TEE，它只接触已经允许发布的聚合数字。

**功能。** 作业详情页的「结果解读」面板。研究者输入一个问题，接口把白名单内的聚合字段交给模型，返回一段中文草稿，页面标明「模型生成的草稿，待研究者确认」。模型只能引用结果里原有的数字。当前会出解读入口的分析类型：

- `disproportionality`：药物警戒失衡信号（四格表、PRR/ROR）。
- `paired-cohort`：配对后的暴露与结局计数。
- `vaccine-scri`：SCRI 的分层风险期 / 对照期计数。
- `external-control-registration`：外部对照注册研究的已发布结果。

**场景。** 多中心结果已经算完并发布，临床研究者希望先看到一段谨慎的文字说明，再自己改。疫苗 SCRI 真机演练里，解读接在发布审查之后。

**不上时。** 结果表、任务状态和存证都在。解读接口返回 503，面板报错，任务本身不算失败。

### 4.5 医院侧加大

最小集的每院 1 台 8 vCPU / 16 GB / 200 GB 继续作为起点。下面五项按该院实际要跑的功能单选或叠加，只加在这一家，不加到平台。

#### 4.5.1 内存和磁盘加大到 8 vCPU / 32 GB / 500 GB

**增量：替换该院这一台。** CPU 不变。净增 **16 GB 内存、300 GB 磁盘**，台数不变。

**功能。** 本院 Python agent 上的重计算：

- L3 因果：PSM / IPTW、Cox、Kaplan–Meier。队列大时，匹配和生存分析的中间表会占内存。
- L4 联邦预测、SecretFlow 训练轮次。torch 与本地 PostgreSQL 同时驻留。

**场景。** 这家医院参加联邦训练或大队列因果分析，16 GB 被数据库和训练过程分完，容器被系统杀掉或训练被取消。

**不上时。** 四格表、Meta 分析所需的效应量、较小队列上的 L3，仍可在 16 GB 上完成。

#### 4.5.2 数据库单独一台

**增量：追加 1 台** 4 vCPU / 16 GB / 1 TB SSD。连接器和 agent 留在原来的 8 vCPU / 16 GB 上，只把 PostgreSQL 迁走。

**功能。** 连接器从本院脱敏库做队列筛选、纳排、特征提取、导入后的本地审计。计算仍在应用机。

**场景。** 本院准备放入连接器的 OMOP 或检验宽表超过 200 GB。10 万级患者的核心表常见为几十 GB；多年全量检验、影像索引或宽表会超过起步盘。接入前用本院行数估一次容量，再决定是否拆。

**不上时。** 脱敏队列能放进 200 GB（还要留出系统和 WAL）就保持单机。

#### 4.5.3 GPU

**增量：追加 1 张训练卡**，插在跑 Python agent 的那台机器上。仓库没有锁定型号。表格模型和小型网络按 **16 GB 显存**准备。[`医院连接器独立部署准备.md`](../医院连接器独立部署准备.md) 对这条计算后端的生产建议是整机 16 vCPU / 32 GB 再加 GPU；若采用该档，相对最小医院机还要再加 8 vCPU 和 16 GB 内存。

**功能。** 本院参与的 SecretFlow 训练、L4 联邦预测的本地轮次。梯度或模型增量算出后才出域，训练数据留在本院。

**场景。** 用 CPU 训完一轮的时间超过任务窗口（轮次超时、医院无法在约定期限内交回更新）。

**不上时。** 小模型可以用 CPU 训练，只是更慢。L1.5 到 L3 的统计不使用这张卡。

#### 4.5.4 独立跳板机

**增量：追加 1 台** 2 vCPU / 4 GB / 40 GB。上面不装数据库、不放脱敏数据，只放运维账号。

**功能。** 没有产品功能。运维经这台 SSH 到连接器宿主，做发布、看日志、健康检查。连接器管理面仍然只绑 `127.0.0.1`。

**场景。** 院方安全规范要求堡垒机与业务机分离，连接器宿主不对运维网开 SSH。

**不上时。** SSH 开在连接器宿主上（密钥登录、源 IP 限制）。数据面依然只出站 443。

#### 4.5.5 院内本地飞地（仅内部信任，不扩展跨组织信任域）

**增量：追加 1 台** 海光 CSV，或 Intel TDX / SGX 机型。具体 vCPU 和内存按采购时该机型的可选规格填写，不在最小集里给死一个数字。

**它解决的问题与 §4.4.1 不同。** 院内飞地保护的是「本院数据不被本院运维/外包运维看见」（内部信任）；它**不建立**跨组织信任——另一家医院或药企凭什么相信本院的运营权（root、引导、固件）？跨院逐人对齐仍要回到 §4.4.1 的中立节点。

**功能。** 合约把执行环境写成「本院硬件飞地」时，密文投影在这台机器里解开并计算。这是 §4.4.1 的另一种放置：飞地在医院网络内，而不是中立第三方的 teeA。

**场景。** 医院书面要求，连密文投影也不能离开本院网络；两院对齐类的计算若因此不能使用平台侧 teeA，就只能在每家医院各放一台飞地，并另行约定跨院投递方式。当前默认架构是飞地放在 §4.4.1，医院不采购。

**不上时。** 本院本地统计走最小集的连接器。需要把两家行级投影放到同一台飞地里的作业，走 §4.4.1。

### 4.6 联邦聚合（多方安全计算：不采购）

本节的机器放在运营方 VPC，医院不部署。医院侧的训练压力在 §4.5.1 和 §4.5.3。原先并列的 MPC 网关见 §4.6.2，结论是不买。

#### 4.6.1 Flower 聚合机

**增量：追加 1 台** 4 vCPU / 8 GB / 100 GB SSD。净增 4 vCPU / 8 GB / 100 GB。

**功能。** 只服务 `/api/v1/flower` 这条联邦训练通道：提交训练任务、按轮收集各院更新、用 FedAvg 聚合成新的全局模型、保存模型产物。控制台里走 Flower 的联邦任务，聚合步骤发生在这台机器，而不是 API 进程。

医院连接器（或 agent）负责本地训练。Flower 机器只接收更新，不接收病历。

另一条 L4 不经过这台机器：SecretFlow / 联邦预测由医院 agent 在本院训练，平台侧的 FedAvg 合并可以留在 API 进程里。只有明确走 Flower 通道、并且不希望聚合和长轮询抢 CPU 时，才加这一台。表格模型、同时训练的医院在几十家以内，4 vCPU / 8 GB 够用。

**场景。** 多家医院同时训练一个预测模型，一轮里每家都上传模型更新，平台要在几分钟内做完加权平均并进入下一轮。这段 CPU 若和合约审批、连接器长轮询挤在最小集那 8 个 vCPU 上，领任务会变慢。

**不上时。** 失衡检测、Meta、因果分析不受影响。走 API 内合并的那条联邦预测也不依赖这台机器。`/api/v1/flower` 的健康检查会显示未配置。

#### 4.6.2 MPC 网关（MP-SPDZ）：不采购

**结论：不进采购清单，也不预留机器。** 需要跨院聚合时走 §4.6.1 的通道或 MDOP 的 `secure_aggregate`，两者都不需要这台机器。

**为什么。** 现在会用到「只出合计、不出分项」的业务只有两类，都已有落点：

- 联邦训练聚合：MDOP `secure_aggregate` 算子，编译期闭合全部数据持有节点、平台不得作为聚合参与方、输出必须是 C3（`apps/api/src/mdop/compiler/aggregate-stage.ts`）；执行在连接器内（`apps/connector/src/mdop/aggregation/handler.ts`），平台只做密文 blob 中继。
- 统计出表：本地 `declassify` 后交平台合并 C3，逐格过 `minCell` / `minCellRare`。

**现网实测，`/privacy/mpc` 这条路径达不到宣传口径。** 三处事实：

1. 各方提交的 `value` 是**明文数字**（`SubmitShareDto.value: number`），先进入平台 API 进程内存（`mpc.service.ts` 的 `sessionShares`）。
2. 收齐后，API 把全部参与方的值一起 POST 给单机网关，网关在本机写 `Input-P{i}-0` 再跑 `shamir.sh`（`fly-services/mp-spdz-gateway/gateway.py`）。没有分布式参与方，也没有份额分片。
3. 因此「平台在计算完成前看不到各家的小计」不成立；单机网关也提供不了这项承诺。

`ComputeMethod.MPC` 在 `compute-task.service.ts` 里只做参数校验标签，没有 dispatch 到网关的分支；`/privacy/mpc` 也没有控制台入口。它在主路径上是孤岛。

**替代方案的性质要写准。** `secure_aggregate` 当前是 **per-recipient 信封**：每个参与方公钥各封一份（`apps/connector/src/mdop/aggregation/ciphertext.ts#sealContribution`）。于是对平台保密，但**每家都能解开别家的贡献明文**。若医院要求参与方之间也互不可见，改的是连接器内的聚合实现（加性掩码 / 同态加法，`apps/connector/src/domain/he-aggregator.ts` 已有 CKKS PoC），不是机器。

**真正要守的边界是反推，不是隔离。** 药企拿分中心数字时，风险来自「同一家医院反复换条件查，把 3 例、4 例的格子拼出来」，不是「别家医院看到了数字」。对应的三件事：

| 边界 | 机制 | 现状 |
|---|---|---|
| 单格太小 → 直接反推个体 | 合约 `outputPolicy` 的 `minCell`（缺省 5）+ 罕见病列 `minCellRare`（缺省 10） | 已实现 |
| 多指标 × 多轮 → 交叉反推 | 查询预算记账 + 二次抑制 | 仅 C2 节点路径（D-TEE-2），C3 平台侧无记账 |
| ε 加噪 + 预算账本 | `outputPolicy.dp` | **未落地**：`TRUST.md` P-CTL-3 记 `dp` 恒 `mode=none`，无 ε 加噪/记账 |

**触发再立项的条件。** 出现通用安全电路需求（PSI 以外的自定义电路）、或监管要求参与方之间零知识式的互不可见，届时单独立项并评估；不是本次采购范围。

**不上时。** RWS 阶梯、合约、存证、联邦训练、统计出表都不调用它。`/api/v1/privacy/mpc` 返回未配置。

### 4.7 Vault 高可用与独立监控

#### 4.7.1 Vault 三节点

**增量：追加。** 最小集里 Vault 是平台机上的一个进程。改成 Raft 三节点时，买 **3 台 2 vCPU / 4 GB / 50 GB**，净增 6 vCPU / 12 GB / 150 GB。若已经按 §4.1 拆出 1 台 Vault，只需再买 2 台同样规格。

**功能。**

- 连接器注册后的 SM2 证书签发与私钥保管。API 对密钥有约 5 分钟缓存。**（注：这一项在代码里还没有实现，`VaultService` 只有 KV / Transit / DB 三类，没有 PKI 引擎调用；见下文第 3 条。）**
- 链 Sidecar 要用的节点证书和私钥（D-RWS-3-a：生产环境这些材料进 Vault，不放在镜像和仓库里）。**（同上：Sidecar 目前仍从 `CHAIN_CONFIG_DIR` 读文件。）**
- 若打开 §4.4.1，按证明释放的数据密钥也以 Vault 或 HSM 为落点。teeB 是校验和释放策略，不是密钥的唯一副本。

**场景。** 发证和读密钥要在一台 Vault 维护时继续可用。等保或密钥管理制度要求密钥管理与业务进程分开，并且至少三副本。

**不上时。** 平台机上的单节点 Vault 继续签发和读取。平台机停机时，新证书和缓存过期后的密钥读取会停。

**采购前必须先做的三件事（当前实现状态）。**

1. **不能拿 dev 模式上生产。** 现在两处配置都是 `server -dev`：`docker-compose.yml`（`VAULT_DEV_ROOT_TOKEN_ID=dev-token-12345`）和 `fly-services/vault/fly.medtrust-vault.toml`。dev 模式是内存存储、固定 root token，重启即丢、拿到 8200 端口就等于拿到全部密钥。生产要 Raft 持久存储 + auto-unseal（KMS/HSM 托管封印密钥）+ 非 root token 的按路径 policy。
2. **接口侧已是硬门禁。** `apps/api/src/security/vault/vault.service.ts#onModuleInit`：`NODE_ENV=production` 且 Vault 健康检查失败时，API 直接抛错不启动。所以 Vault 在最小集里是**必须部署**，不是可选件。
3. **接上了，但主路径还没用它加密。** `setEncryptionServices()` 目前只在 spec 里被调用，实体上的 `@EncryptedColumn` 仍是注释（`patient.entity.example.ts`），种子数据也标注「@EncryptedColumn 列加密未启用」；`DEPLOY.md` §4「生产环境未落地要求」第 5 条另记「密钥仍可由环境变量直接注入，未强制走 Vault」。也就是说最小集里 Vault 的状态是「必须先具备、但业务还没真正依赖它」。验收时按这三条如实描述，别写成「密钥已全部托管」。

#### 4.7.2 独立监控机

**增量：追加 1 台** 2 vCPU / 4 GB / 200 GB。§4.1 的 7 台里已经有一台监控时，不要再买。

**功能。** 没有业务功能。采集 API、数据库、三台链、各院连接器的健康检查，保存磁盘水位和日志。连接器日志的业务副本仍在医院本地；这台只收平台侧能看到的运维信号。

**场景。** 审计要求平台日志保留期长于数据库备份周期，继续写在平台机的 500 GB 上会和 PostgreSQL 抢空间。

**不上时。** 日志留在各自机器的本地磁盘，由运维登录查看。

### 4.8 对话 Agent

**增量。** 先叠在平台机上，约占 **2 GB** 内存，不增加机器。最小集平台机的内存余量大约 14 GB，这一项放得下。若要求助手进程和 API 分开重启，再 **追加 1 台 2 vCPU / 4 GB / 40 GB**。已做 §4.1 时，放在其中一台 API 上即可。

**功能。** 控制台助手（`/space/assistant`）把自然语言收成可确认的卡片，再落到合约或 MDOP 作业草稿。入口包括：研究设计、访问合约、结果解读的提问入口、平台运维、合规证据、医院码表。没有配置外部模型密钥时，走确定性回退，问题文本不出平台。

结果解读的正文生成不在这台机器上。研究者在作业页点击生成解读时，请求发到 §4.4.2 的 LLMA。助手只负责把人带到对应流程。

**场景。** 研究者用一段中文描述病种、结局和参与医院，希望先得到一份研究规格或合约草稿，再在表单里改。手填表单的路径不经过助手。

**不上时。** 控制台表单、合约审批、任务提交、结果页都在。助手页不可用。

### 4.9 存证落点：自建链，或对接丝路数港

**这是唯一一条会把机器减下来的选择项。**

| 形态 | 共识节点 | 平台机 | 何时成立 |
|---|---|---|---|
| A. 自建链（当前实现） | 3 台（要容错）/ 1 台（现网 solo） | 保留 Sidecar | 默认；需要自定义合约、SM2 背书独立核验、或不能依赖外部网络时 |
| B. 对接区域节点存证 | **0 台** | 保留 Sidecar（改为存证适配器） | 丝路数港接口满足下面三问时 |

**切换到 B 之前，必须由对方接口文档回答三问**（登记在 [`docs/丝路数港-接口对拍表.md`](../丝路数港-接口对拍表.md) §6）：

1. **写**：能否写入「任意业务哈希 + attester + 时间戳」，而不是只收固定类型的数据流通行为（主体 / 产品 / 合约 / 交易）。
2. **读**：有没有「按哈希查询存证时间与存证方」的接口。只能写不能查，`verifyAttestation` 就失去独立核验能力。
3. **背书**：是否允许连接器用自己的 SM2 证书对结果签名并一同存证。这是「第三方凭平台 CA 公钥即可核验某院背书」（CTL-23）的前提。

**收益。**

- 省 **12 vCPU / 24 GB / 300 GB**（三台 4C/8G/100G）。
- 更重要的是信任锚：现在是平台自己运营链，`TRUST.md` P-CTL-4 记的「平台遗漏/不锚某条记录仍无对抗手段」正是缺第三方托管；换成区域节点运营，这一条直接补上。**省机器只是副产品。**

**代价（必须写进合同，四项）。**

- 存证链路的可用性与故障恢复方式；
- 按哈希查询的时延、留存期、批量导出接口；
- 退出/迁移时的导出格式与历史存证的可核验性；
- 对端不可用时的**本地降级**：本地落库 + SM2 签名 + 事后补锚，不得静默丢存证。

**三问缺任意一条**：不要删 Sidecar，也不要删链；按 §1.1 的自建形态部署，等对拍结果再定。接口未确认前，「三台共识节点」仍在采购清单上。

**改造面很小。** `ChainAdapter` 是唯一访问链的接缝（全 HTTP：`/attest`、`/attestation/<hash>`、`/block-number`），上层业务零改动；需要新增区域节点的存证读写方法与鉴权——`apps/api/src/runtime/silk-road/silk-road.client.ts` 目前只有 `subjects` / `catalog` / `audit-digest` 三个方法，鉴权在接口对拍表 §4 仍标「待接口文档」。

## 6. 采购时怎么加总

**只有平台（存证走区域节点，§4.9 形态 B）：** 1 台，8 vCPU，32 GB 内存，500 GB SSD。

**只有平台和链（自建链，最小集）：** 4 台，20 vCPU，56 GB 内存，800 GB SSD。

**再加医院：** 每家 +1 台，+8 vCPU / 16 GB / 200 GB SSD。两家医院时是 6 台，36 vCPU，88 GB，1.2 TB SSD。

**可选项按 §1.2 的「追加 / 替换」逐项加，互不绑定。** 例如只要 Flower、不要机密计算：在最小集上追加 1 台 4 vCPU / 8 GB / 100 GB，总账变为 5 台、24 vCPU、64 GB、900 GB。又要结果解读：再追加 1 台 4 vCPU / 16 GB / 50 GB。医院加大只改那一家的台账，不改平台和链。

下面是一条常见的「最小集 + 两家医院 + 打开跨院飞地和解读」算法，便于对表：

| 组成 | 算法 | 结果 |
|---|---|---|
| 最小集平台 + 三台链（自建链） | §1.1 | 4 台，20 vCPU，56 GB，800 GB |
| 两家医院 | 每家追加 8C/16G/200G | +2 台，+16 vCPU，+32 GB，+400 GB |
| teeA + teeB | §4.4.1 生产建议，追加 | +2 台，+12 vCPU，+40 GB，+150 GB |
| LLMA | §4.4.2 建议档，追加 | +1 台，+4 vCPU，+16 GB，+50 GB |
| **合计** | | **9 台，52 vCPU，144 GB，约 1.4 TB** |

同一档若存证走区域节点（§4.9 形态 B）：**8 台，40 vCPU，120 GB，约 1.1 TB**（减三台共识节点）。前提是对方接口的三问已确认。

这一档仍然不含平台拆机、第四台共识节点、Flower、MPC、Vault 三节点和医院 GPU。那些要等对应功能立项再加。
