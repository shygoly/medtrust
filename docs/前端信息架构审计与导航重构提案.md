# 前端信息架构（IA）审计与导航重构提案

> 范围：`apps/web` 控制台 `(console)/space/*`（31 个页面路由）+ `SpaceNav` 侧栏（22 个菜单项 / 6 个分组）。
> 性质：**调研 + 提案**，不含代码改动。落地需按 §11 分阶段并同步 `DESIGN.md`（UI 唯一事实源）。
> 方法：静态盘点（脚本 + 逐页实读）与外部 IA 研究交叉验证；所有结论附文件路径与行号。
> **局限**：盘点为**静态代码实读**，未做浏览器运行时验证；路由可达性结论基于 App Router 文件结构推导（`/space/infer` 无 `page.tsx` → 404）。角色/鉴权结论已在服务端逐控制器核对（§2.5）。
> 日期：2026-09（基线 commit 见仓库当前 HEAD）。

## 1. 结论摘要（先看这 8 条）

1. **菜单按“面/主题”切，业务按“旅程”切，两者正交且无桥。** 16 条 `FLOW-x` 契约中，每一条都跨 ≥2 个菜单分组；其中 FLOW-RWS-04 的终点页 `/space/infer/[taskId]` **根本不在菜单里**。
2. **组织方案混用**：6 个分组同时用了 4 种分类法——架构平面（声明面/运行面）、受众（使用方）、主题（合规）、内部职能（运营/管理）。这是 IA 教科书级反模式（同一菜单混用多种方案）。
3. **同一批数据最多在 5 个页面各渲染一遍**：结算 5 处、存证 5 处、SecretFlow 任务 3 列表 + 2 详情、审计日志 3 页 3 口径。
4. **总览页是 mock**：`/space` 零后端调用，6 个 Stat 与 3 张列表全部来自 `lib/space-mock` → `@medtrust/demo-scenario` 静态 JSON，且任务链是死链（详情页查真实 API）。
5. **孤儿页**：`/space/infer`（无 index → 404）、`/space/infer/[taskId]`（仅深链可达，是 FLOW-RWS-04 的**法定终点 actor**）。
6. **前端门控不一致（非越权）**：8 个页面在菜单里按角色分组，页面内却零门控（`audit`、全部 `admin/*`）。**服务端鉴权完备**（`JwtAuthGuard` + `ParticipantRolesGuard` + `@ParticipantRoles(...)`，逐控制器核对见 §2.5），所以这是 **UX 问题**：无权限用户能进页面、看到按钮，点下去才失败，而不是安全漏洞。另有一处**反向偏差**：`/space/admin/interop` 的 API 允许 `operator`，菜单组却只给 `admin` → operator 有能力但没入口。
7. **两套设计语言并存**：`atlas` 引入 14 个 `--at-*` 令牌 + `.codex` shadcn 重映射，与 `--cs-*`（14 个）平行——直接违反 `DESIGN.md §9.5「禁引入第二设计语言」`；9 个页面自造页头绕过 `PageHeader`。
8. **角色词汇三处不统一**：`DESIGN.md §8` / `ARCHITECTURE.md:267` 写 4 角色（provider/consumer/operator/compliance），`lib/auth.ts:10` 与 `auth-gate.tsx:16` 是 5 角色（含 `admin`），而 `admin/users` 的下拉枚举又缺 `admin`。

### 2.6 视觉/标签一致性

- **第二设计语言**：`app/(console)/space/atlas/atlas.css` 定义 **14 个 `--at-*` 令牌**（与 `console.css` 的 14 个 `--cs-*` 平行）+ `.codex` 重映射 shadcn 令牌 → 违反 `DESIGN.md §9.5`。

### 3.2 关键设计思路（按对本仓的适用度排序）

1. **IA 是四个系统，不是一个菜单**（organization / labeling / navigation / search）。本仓目前只做了 organization 的一半（22 项平铺），labeling 不一致（§2.6），navigation 无局部导航/面包屑，search 完全缺失。“漂亮的导航条架在坏掉的分类法上 = 迷宫上的口红”。
2. **先选组织方案，一次只用一个**。候选：task（按用户要做的事）、topic、audience、lifecycle、chronology。**禁止在同一级菜单混用**。本仓现状混了 4 种 → 应选定 **task/journey 为主干**，把 plane/audience 降级为 facet 与权限。
3. **宽而浅优先**（broad-and-shallow）：同级 5–9 项、内容在根下 3–4 层内。“用户宁可扫 9 个选项，也不愿在不确定中连点 3 层”。本仓 22 项一级平铺 = 宽但无结构，且 6 组里有 1 项组（使用方）。
4. **⌘K 命令面板 + 全局对象搜索分离**：前者是动作与跳转（power-user 签名能力），后者是检索（若检索是核心能力，两者必须同级而非嵌套）。22 项菜单的复杂度应主要靠 ⌘K 消解，而不是继续堆侧栏。
5. **面包屑是钻取页的强制项**（Carbon/Primer）：“从父到子必须有清晰回程”。本仓 8 个详情页中，只有少数有返回链接，且 `infer` 无归属。
6. **上下文导航（contextual / related）替代人肉记忆**：related links 应由**内容模型的关系**生成，而非手写。本仓 `DOMAIN.md:107-114 / 203-211 / 417-426` 已有关系表（合约↔任务↔作业↔交付物↔存证↔结算），关系图是现成的——菜单没接上去。
7. **分面（facet）替代“一通道一页面”**：多属性对象（任务有 workload/state/我方角色/时间）应用分面组合，而不是为每种通道建一个列表页。这是消灭 A1/A2/A9 的标准解。
8. **渐进披露 + Shneiderman 箴言**（overview first → zoom & filter → details on demand）：总览只放概览，明细按需下钻，而不是把明细复制到 5 个页面。
9. **URL 即 IA**：搜索词/分面/排序/分页写入 URL，可分享、可回退、可被 agent 调用；旧路径 301。
10. **意图驱动界面（2026 趋势）**：企业 UI 的垄断正被 agent 打破——入口从“浏览目录”转向“表达意图”，导航退化为**可寻址的状态**（[Everest Group](https://www.everestgrp.com/blogs/ai-agents-are-breaking-the-enterprise-applications-ui-monopoly/)、[Sinequa: from search box to agent](https://www.sinequa.com/resources/blog/enterprise-search-development-start-with-the-user-interface/)）。对本仓的含义：导航要能被 **agent 调用**（稳定的动作名 + 可寻址 URL），同时保留人类可扫的结构。
11. **用研究而不是争论来定 IA**：card sort（发现分类）→ tree test（验证可寻性）→ first-click（验证标签）三步，成本极低。本仓有 4 类真实角色，完全可做。
12. **复杂度管理**：[NN/g 渐进披露](https://www.nngroup.com/articles/progressive-disclosure/)、[Managing Visual Complexity](https://www.nngroup.com/videos/managing-visual-complexity/)。

### 4.2 逐层说明

**Layer 0 顶栏（现在完全没有）**
- 空间/租户切换器（视觉区分，`saas-navigation` 要求）；
- 全局对象检索（合成/合约/任务/作业/凭证/存证 跨类型，结果带类型徽标 + 所属面包屑）；
- **⌘K 命令面板**：动作（发起 RWS / 发起 L4 / 签发合约 / 导出审计）+ 跳转（任意对象按 ID）+ 上下文感知（当前页相关动作置顶）+ 展示快捷键；
- 通知与用户。utility 全部集中到右上，不散进内容菜单。

**Layer 1 侧栏 5 项，按“用户要做的事”而非“系统有什么表”**
| 侧栏项 | 收纳现状 | 为什么 |
|---|---|---|
| ① 工作台（角色化首页） | 新页；吸收 `/space` 概览 | 4 个角色的“今天该干什么”不同，用**角色化首页**替代“整组隐藏菜单”。provider=待接单/待签发/待复核；consumer=我的任务/可推理；compliance=越限/告警/待审计；operator=待审认证/系统告警 |
| ② 数据与合约 | catalog + contracts + connectors | 同一对象族（数据产品↔合约↔连接器）三个视角 → 局部 tab，而不是三个一级项 |
| ③ 研究与任务 | tasks + tasks/new* + mdop/jobs + federated + deliverables + infer | **一个统一任务面**，按 workload 分面/分 tab；详情页统一骨架（吸收 A1/A2/A9） |
| ④ 合规与监查 | compliance + rbqm + alerts + audit + attestations | 把横切的“存证”收进合规成链：预审→合约→任务→存证→结算→监查 |
| ⑤ 平台 | admin/*（角色可见） | admin 5 页合并为局部 tab，并补齐 in-page 门控 |
| ⑥ 能力与准入（声明面） | atlas×4 | **二选一**：纳入 console 设计系统（删 `--at-*`、改用 `PageHeader`），或明确升格为**独立子产品入口**（独立顶栏 + 明确“这是设计/准入平面”）。不要在同一个侧栏里混两套设计语言 |

**Layer 2 局部导航**：每个 section 的 tab + **面包屑**（钻取页强制）+ 空态返回路径。

**Layer 3 对象详情统一骨架**：`概览 | 分派执行 | 结果 | 交付物 | 存证 | 结算`——`federated/[taskId]` 与 `deliverables/[taskId]` 变成同一页的两个视角（差异是权限，不是页面）。

**横切 ①：⌘K + 全局检索**（消解 22 项菜单的复杂度）
**横切 ②：关联对象区**（由 `DOMAIN.md` 关系表生成，消灭 H1/H2/H3/B1/B2 类断链）

## 6. 治理提案：把 IA 变成机器可校验的契约（★ 最贴合本仓）

本仓的既有范式是**元语 + 守护 + 负例自检**（`AGENTS.md`：`check:meta` / `governance` / `governance:negative`，且“不跑的守护等于没有守护”）。
IA 目前是唯一没有守护的横切契约。提议：新增 `apps/web/src/nav.manifest.ts` 作为**导航单一事实源**，字段：

```ts
{ route, label, group, section, entity /* cp_* */, viewLayer /* list|detail|form|ledger */,
  roles: Role[], flow?: FlowId, entry: 'menu'|'contextual'|'internal' }
```

配套 `scripts/check-nav.mjs`，挂进 `pnpm test`，规则（每条各带负例）：

1. **无孤儿**：每个 `page.tsx` 必须在 manifest 中（`entry:'internal'` 也要登记）→ 卡住 `/space/infer/[taskId]` 这类。
2. **无死链**：manifest 中每个 route 必须存在对应 `page.tsx`。
3. **无重复**：同一 `(entity, viewLayer)` 不得映射到两个 `entry:'menu'` 路由 → **机器卡住 A1/A9 这类“一通道一列表页”**。
4. **门控一致**：`roles` 非全集的 route，其页面必须出现 `RoleGate` 或显式 `ALLOWED` 判断（静态扫描），消除四种写法并存 → 卡住 §2.5 的 ❌ 行。
5. **菜单不严于服务端**：manifest 的 `roles` 必须覆盖该路由命中的 `@ParticipantRoles(...)` → 卡住 `/space/admin/interop` 这类“有能力无入口”。
6. **流程可达**：`FLOWS.md` 中 `ts:apps/web/...` 形式的 actor 必须在 manifest 且菜单可达 → 卡住 §2.4 的“契约在线、导航离线”。
7. **角色在册**：manifest 的角色枚举必须与 `DOMAIN.md`/`ARCHITECTURE.md` 的角色表一致 → 卡住 admin 词汇三处不统一。
8. **标签唯一**：同一 `entity` 的菜单 label 与页面 `PageHeader` title 必须同源（或显式登记差异）→ 卡住「本院连接器/本院节点」。

> 这条路的价值：不是“画一个更好看的菜单”，而是让**“菜单 ↔ 路由 ↔ 领域实体 ↔ 流程契约 ↔ 角色”五者互相对拍**——与本仓 `DOMAIN.md` 覆盖矩阵 ↔ `@Entity` 对拍的做法同构。信息架构从“设计意见”变成“可回归的契约”。

## 7. 验证方法（不要靠争论定 IA）

| 方法 | 问什么 | 怎么做 | 输出 |
|---|---|---|---|
| **Open card sort** | 用户怎么归类和命名 | 把 22 个菜单项 + `FLOW-x` 旅程写成卡片，让 4 类角色各 3–5 人分堆并命名 | 候选分类法（很可能会得到“按研究阶段/按我的活儿”而非“按声明面/运行面”） |
| **Closed card sort** | 卡片是否落进我们的新分组 | 用 §4.2 的 5 项侧栏做封闭分堆 | 目标结构的第一轮修正 |
| **Tree test** | 在新层级里找得到吗（只看结构+标签，无 UI） | 给 8–10 个真实任务（如“某药企要核验本院胰腺炎识别算法的 Se/Sp”“某院要吊销一张 CA 证书”“查某 L4 任务的权重包是否可下载”） | 任务成功率 + 直达率 |
| **First-click test** | 第一次点击是否落在正确路径 | 上述任务配线框图 | 首点正确率（首点对 → 整体成功率高 2–3 倍） |
| **上线后指标** | 长期可寻性 | 检索零结果率、pogo-sticking/回退率、⌘K 使用率、浏览 vs 检索比 | 迭代 backlog |
