MedTrust 平台架构

医院只把元数据发布到平台，计算在院内连接器里完成，离开医院的只有聚合结果。系统支持协同计算（单次任务数据就地计算，出 C3 聚合结果即销毁中间态）与服务计算（合约期内 C2 密态语料受控托管，声明式服务协议标准强约束，飞地内分步管道执行、全周期累积预算与执行轨迹见证）；上层由AI 助手层把自然语言变成 Card 表单与 MDOP 作业（六类意图路由，含 AGT-06 注册研究工具链；出域只送提示词，结果解读走自托管推理）。下图按代码、线上部署与实机试点逐项核对后的真实状态标注：哪些在用、哪些已实现未上线、哪些只是部署了但没有接入。MDOP 编排内核（作业 → 片段 → 凭证 → 执行 → C3 → 销毁 → 锚定）已于 2026-09-25 在 ali29 跑通；TDX 试点已于 2026-10-03 在真实硬件上跑通 C2 主路径（合成数据，非生产）。

一条任务怎么走

从医院发布数据产品到平台结算，六步依次发生；括号里是负责的一方和发生的位置。第 4–6 步在 MDOP 通道里换了实现（平台只发片段、只收 C3），见下一节泳道图。

  1. 01发布数据产品医院 · 平台 API只登记元数据：字段结构、记录数、分级标签、本地数据路径。平台上看不到任何一条原始记录。
  2. 02合规预审药企 · L2 引擎选场景和已落地的能力组合，引擎裁决批准、需审批或驳回。已接入闸门（compliance-pre-review-gate 已上线）：申请合约时绑定预审快照，创建任务时按参与方复核，命中红线（如 block-cross-inst-low-k）即驳回。
  3. 03申请与签发合约药企 → 医院 · 平台 API药企申请、确认知悉规则，医院签发。合约写死目的、留存、输出范围和有效期，哈希上链。
  4. 04创建任务药企 · 平台 API选生效合约和研究方案；平台按合约准入，为每家医院生成一条派发记录。
    也可以从控制台对话入口让 AI 助手生成同一张 Card 表单与作业草稿——助手只是把自然语言变成载荷，不扩大权限、不代签合约。
  5. 05院内计算连接器 · 医院内连接器领到任务，按合约校验，在本地库守卫内去标识、计算，经输出闸门后回传聚合结果和它的 SM3。
    MDOP 通道：先做七项本地复核（只认本地合约副本）并用本院私钥签接受，平台收齐后才签发执行凭证；执行前再校验凭证与数据快照，C3 制品还要过出节点守卫才投递。
  6. 06合并、存证、结算平台 API · 长安链平台验 SM3，做跨院 Meta 合并，结果哈希上链，再按贡献记账。
    MDOP 通道：合并落库即完成发布（本期合约预授权自动放行），随后向两院发PurgeOrder销毁院内制品，收齐回执进 PURGED，两院回执链头上链。

联邦训练的第 5 步：连接器经长轮询领到训练轮次后，在院内调用本院 Python agent（下发全局 LoRA 参数、收回 LoRA 增量），再由连接器签名回传。平台不再直接连进医院——outbound-longpoll-agent-auth 阶段 3-4 已上线，原来那条平台入站调用的边已移除。

MDOP 泳道：一次作业跨了哪些边界

同一条任务链换成 MDOP 编排时的真实时序（2026-09-25 ali29 实跑的那一票）。四行是四个责任方， 横向是时间。绿色实线＝跨医院边界的消息（都由连接器主动外联），琥珀虚线＝销毁指令与回执， 灰色点线＝链头哈希上链。左侧竖线上标注的是协议里的字段口径。

读这张图只需记住一条：医院那一行的每个方块都在院内完成，行级数据从不出现在任何一根箭头上；平台那一行拿到的最“生”的东西是四格表（C3），它已经过了小单元格抑制。

合约预检是一段可判定的代码，不是提示词：evaluatePrerequisites 依次做三件事——空间成员 → 产品级 ACL（cp_data_access_grant，fail-closed）→ 合约可用性（逐条镜像 assertUsableForJob 的五条判据，失败时点明是哪一条）。两层正交：ACL 回答「能不能碰这个数据产品」，合约回答「以什么条款执行」，两层都过才放行（D-ACL-1）。无可用合约时，助手代用户发起申请（draft），平台按预授权自动推进要约，但不代签——签不签由医院连接器按院内本地策略决定（D-MDOP-9）。

如实边界（不写成「AI 能替你做合规决定」）：① 六类意图里只有「访问与合约编排」（含 AGT-06 注册研究工具）能真正提交作业，其余是只读或草稿；② 外部供应商仍会收到组织级敏感信息（机构名、研究意图），分级见 TRUST CTL-11；③ 结果解读用的是 1.7B 小模型（OpenVINO int4），产物恒为「待研究者确认」的草稿，不做统计推断；④ 注册研究报告中的数字与证据指纹不经 LLM 填写（D-TRUST-13），模拟报告须标明 SIMULATION ONLY；⑤ 通知落站内信（cp_notification），邮件/短信/Webhook 未做；⑥ 会话存储可选 memory 或 SQLite，跨实例共享未做（Redis 只作缓存，不改变正确性）。

什么时候必须上可信空间节点（TEE）

协议把「数据在可信空间内受控流动」定为 C2。它的放置以目标节点的证明登记为准：证明有效（未过期、度量与 TCB 达标）且合约声明了证明策略才可放置；没有硬件证明的部署里 C2 仍为零（2026-09-26 起判定开关已翻转，软件实现不得作 C2 目标）。最新实机结论见本节末 2026-10-03 条：TDX 试点已在真实硬件上跑通 C2 主路径（合成数据），但生产 C2 仍为零。 原因很简单：C2 的代价远高于聚合出域（C3）——多出一整层「硬件证明 + 代码度量 + 密钥释放 + 运营方」的信任面。 判断标准不是数据多少，而是要算的函数可不可分解。以下判断表摘自 MDOP 协议 §4.5（v0.2 起沿用，v0.3 的安全聚合未改判定口径）。

分析形态聚合出域能做到吗原因
计数 / 求和 / 均值 / 率 / PRR·ROR·IC / Meta 合并能可分解：各院出局部量，平台能加总——这正是当前 L1.5–L3 走的通道
分位数 / 中位数 / 去重人数 / 集合交并很勉强不可分解，或需跨节点排序与去重
跨院同一患者配对（join）做不到需要可对齐的标识符出域，而标识符出域是红线；这是数学上无解，不是工程难度
亚组 / 新切点的重新计算做不到分层维度在提交时即冻结，已出的统计量把其他维度边缘化掉了，要重跑整个作业
非线性模型（提升树 / 深度模型 / 聚类）严重受限分裂点搜索与逐样本迭代难以联邦化；当前 L4 只能用逻辑回归与 LoRA 增量，正是这个约束的结果
影像 / 病理 / 文本 / 多模态近乎不能特征化即丢信息；只能模型下到各院各训一份再合并
交互式探索（先看数据再决定怎么切）做不到每次探索都是一次新作业，且探索路径本身构成泄露

换来的代价（对比要对称）：信任锚从「医院自己的物理控制」变成「CPU 厂商证明根 + 代码度量 + 可信空间运营方 + 密钥释放策略」；合规定性变成委托处理 / 数据出域，需额外协议与告知；出域内容不再是人一眼可审的数字，而只能「信任度量」；数据一旦出域不可撤回；内存访问模式侧信道不在 TDX/SEV-SNP 防护范围内；药企自建节点时医院常不接受，通常须中立第三方或监管侧运营、密钥释放权留在医院或共管。

C2 绝不等于「可以随便查」：查询预算、差分隐私与发布审查必须在可信空间节点内部由被测代码强制，否则它会退化成「把医院数据库的远程终端交给申请方」——用大量允许出域的小统计量反推个体，后果与直接出明细同级。所以节点内的 C0/C1 一律不得回流，离开节点的仍然只有经发布审查的 C3。

2026-09-25 进展（代码已落地；09-26 判定开关已翻转，部署仍为零）：C2 的协议核心、节点运行时与节点组件已经落地并有可复跑用例——数据信封 mdop.env/1.0、封装算子 seal、证明契约（含一次性公钥与身份绑定）、KMS 释放凭据与释放判据、节点入口守卫、发布审查、出口守卫、回执链、销毁、两院 C2 会话装配（用共享假名键跑通「封存 → 证明 → KMS 释放 → 解封 → 节点内跨院配对 → 发布审查 → 只出 C3 → 回执成链 → 销毁」），以及节点组件（自持身份 0600、配置闸门拒绝「软件顶上」、证明提供者与 KMS 两处可插拔接缝、见证上报，独立进程部署）。首个业务场景定为跨院队列交集（D-TEE-4），证明链按 D-TEE-3 的条件式默认（有信创硬要求则海光 CSV 优先，否则云上 TDX 先打通、CSV 并行申请）。
「持有方独立校验证明」的载体是四段闭环：节点 →平台（AttestationReport）→持有方（AttestationWitness），送出的是见证本体（证明报告 + KMS 释放凭据）；验签公钥来自部署配置，平台只搬运、不下结论（它能「不给」，做不到「伪造」），持有方通过记 WITNESS_VERIFIED、拒绝记 WITNESS_REJECTED，都进审计回执链。C2 数据面也通了主路径：持有方 →平台（C2EnvelopeSubmit，平台只转运不解密——数据密钥封给节点本次会话的一次性公钥）→节点（C2EnvelopeRelay）→ 节点跑会话 → 回投 C3 与见证；平台在中继上做六项可判定检查（含密文摘要与「目标必须是本作业的片段节点」）。控制台也能看到这条链的证据：作业详情逐节点展示「会话证明与本院核验」（通过 / 未通过 / 尚未核验三态分开），以及 C3 交付物随带的发布审查清单（抑制汇总数、DP 声明、预算消耗；逐格明细仍留在节点本地与回执里）。仍缺三样，因此 C2 在真实部署里仍为零：① 真实硬件证明与真实 KMS（现在的提供者与 KMS 都是替身，软件实现必然过不了 C2 判定）；② 假名键方案定稿（PSI vs 共享盐）；③ 带链上锚定的整跑（与真实实现一起做）。

节点侧两阶段执行（2026-09-25 补）：会话拆成「跑阶段」与「出口」两半，发布审查整个流程只做一次（由 declassify 阶段承载）；节点内中间制品（跨院配对结果）留在本节点制品库、只登记句柄不出节点，出口与否只看片段里「有没有同节点下游」这一条结构事实；一次阶段可吃多家持有方各自的封存输入（齐了才跑、一次会话解封全部）；每个阶段结束节点都回报StageStatus（成功带摘要与等级、失败带错误码），平台据此推进下游与退避重试。于是合成数据上「两院封存 → 平台中继 → 节点内配对 → 节点内降密 → C3 → 平台收集」已端到端可跑。

节点是一等参与方（2026-09-25 补）：平台下发给节点的五类消息此前只有一半有处置——要约与销毁指令被长轮询记为「收到但暂无处理器」，后果不是少个功能而是链跑不通：平台要收齐全部片段节点的接受签名才签发凭证（节点不接受 → 作业永远停在要约阶段），也要收齐全部销毁回执才进 PURGED（节点不回执 → 永远进不了终态）。现在：要约走九项本地复核并按本节点自己签名接受（复核不过只回错误码与一句说明）；凭证到达即校验（含执行环境快照比对，环境漂移即 E_SNAPSHOT_CHANGED、作业须重新要约——登记为 D-TEE-5）；C2 信封按已复核片段里的入边绑定到阶段（目标不从消息猜）；信封与阶段派发两个来源做会合（先到的一方只登记、不把竞态误报成失败）；销毁指令销毁制品并回签名回执。仍缺：节点守护进程的长驻循环与真实证明/KMS（部署动作）。

作业之前的证明登记已关闭（2026-09-25，D-TEE-6）：编译期要求「该节点有一份未过期的证明登记」，而会话见证要等一次作业绑定的密钥释放——先有鸡还是先有蛋，除「刚跑完一次会话的窗口内」作业都会在编译期被判 E_ATTESTATION_FAILED。现在由部署白名单内的校验方（KMS / 证明服务）在作业之前对证明摘要签名推送（协议核 attestation/push.ts 共享判据 + 部署侧接口 POST /mdop/attestations），平台用部署配置的 KMS 公钥验签、仍不自己验 quote；节点侧配一条探针（真跑一次证明交校验方），并自己验回传的背书是否就是给本次这份证明的。备选（心跳带背书）保留，放宽编译期判定已否决（那等于把 fail-closed 换成「最近看起来还行」）。探针节拍必须短于背书有效期。

节点执行面接齐（2026-09-25）：配对阶段此前在节点组件里一步也跑不了——执行器要求本节点接入 wasm 沙箱，而节点没有任何接线（用例里都是自己塞一个假 runner），真实部署会直接 E_CAPABILITY_MISMATCH。现在：按摘要从节点本地模块库取字节（取不到即拒，不现取平台）、宿主显式判定调用形状（配对是 5 参数字列 ABI，既有 L1.5 仍是缺省的 4 参形状、行为一行未改）、宿主适配做投影与回填并校验不变量；降密仍是节点内发布审查。对齐与分层留在宿主：模块只认「已对齐的下标与标志」，所以「共享盐 vs 跨院 PSI」这个仍未定的选择不改模块与调用代码。同一轮还补上了节点的清单/吊销/模块库（此前节点既不收算子清单也不收吊销名单，真实部署下每个阶段都会被 E_OP_NOT_WHITELISTED 拒）：清单用部署配置的注册中心公钥验签、吊销名单用平台节点公钥验签且版本单调、未同步到有效吊销名单即拒绝执行 wasm；平台消息只能「提供清单」与「吊销」，给不了节点「凭空多一个能跑的算子」。

节点进程可启动（2026-09-25 续）：每块都对、整条不通的问题也补上了——此前没有进程把心跳、探针、长轮询、清单应用与消息处置串起来。现在 tee-node -- serve 长驻运行：心跳 60s、证明探针 5min（须短于校验方给的背书有效期）、长轮询 25s，一个 tick 内先应用清单与吊销再处置消息，单条消息失败不影响其余，轮询失败退避重试而不退进程；配置不全起不来（缺平台公钥/注册中心公钥/证书指纹都报错，软件替身要显式开关且生产环境拒绝）。另外，复核用的已双签合约副本现在随要约下发（此前节点不是合约提供方、拿不到 ContractOffer，每一份要约都会被 E_CONTRACT_UNSIGNED 拒）：节点用部署配置的平台公钥验副署、用部署锚里的参与方公钥表验持有方签名，验不过即整条丢弃。

首个 C2 场景已单进程端到端跑通（2026-09-25 续）：一条链从证明背书推送开始，经编译（C2 放置）、要约（带已双签合约副本）、三方签名接受、签发凭证（冻结节点执行环境期望）、各院封存、C2 中继（平台只转运）、节点内配对（C2 制品不出节点）、节点内降密（只出 C3）、平台收集，直到作业 SUCCEEDED、销毁编排收齐含节点在内的全部回执才 PURGED。这条用例一次抓出两处「分块用例各自都过、整条链才暴露」的真 bug：①节点发出的句柄缺 expires_at（平台解析器把它列为必填，真实部署下每一次句柄登记都会被判非法）；②节点的 C3 载荷只出 buckets、缺平台收集方要读的规范分层表 strata（配对作业会在收集阶段以「缺分层表」拒收）。两处都已修复并有用例钉住——被抑制的分层现在整格清零并标记，平台拿不到未抑制的分层计数。

已知缺口

  • 院内连接器的 TEE 是软件实现：同进程、无隔离、无远程证明，对外不称可信执行环境（云上 TDX 试点是另一条链，见上；试点不等于院内生产）。
  • CA 根密钥已挂卷持久化：重建 API 不再重生——但必须带 -f compose.hardening.yaml（该 overlay 才挂 medtrust_api-data 卷）；漏挂则控制面库落到临时层，CA 与证书仍会失效。
  • L3 因果线上未接通：接通前要先修复 Cox 在小样本时返回固定值的问题。
  • agent 直接读本院数据：不经过连接器的本地库守卫和输出闸门，只有自己的一套输出白名单。
  • 两院隔离是网络层面的：ali29 单机模拟，外网隔离依赖云安全组，主机防火墙只管 80 端口。
  • MDOP 发布审批未实现：本期合约全部预授权自动放行——合并落库即进 RELEASING → SUCCEEDED，协议里的 ReleaseRequest/ReleaseApprove 路径没有代码。
  • MDOP 的 C2 生产不可用：放置判定已于 2026-09-26 翻转为「目标节点证明有效才可放置」（D-MDOP-6 翻转补注）——翻转的是判定方式、不是能力：没有硬件证明就没有任何节点通告 tee{kind}，且软件实现不得作为 C2 目标。2026-10-03 的 TDX 试点已在真硬件上跑通 C2 主路径（合成数据），但 KMS 是试点形态、假名键未定稿，生产部署里 C2 仍为零。
  • C2 的缺环：① 真实生产 KMS 未接（真实硬件证明已由 TDX 试点跑通；节点组件的身份、注册、心跳与能力通告均已接线，通告取自真跑证明，不虚标）；② 跨院假名键对齐方案（PSI vs 共享盐）等医院/合规取向——配对算子本身已入库（packages/wasm-algorithms 的 paired-cohort.wasm，数字列 ABI、可复现、与 TS 参考语义逐字段对拍），模块对两种对齐方式都中立，试点里的关联假名是人为注入的；③ 全程合成数据，患者数据闸门（REG-08）未动。三者齐备前不得通告 TEE 能力。
  • 连接器侧凭证与片段只在内存：重启后靠平台按至少一次投递重发要约与凭证恢复（重放要约会重新走七项复核）；本地持久化未做。
  • 发件箱没有接收方确认：靠「终态即清理」保持队列有界，未对每条消息做逐条 ack；重复投递由接收方幂等消化。
  • AI 助手只能「代发申请」，不能代签：平台按预授权自动推进要约，签名仍由医院连接器按院内本地策略给出——没有配置 autoConfirmRules 的医院不会被绕过；六类意图里只有「访问与合约编排」（含 AGT-06 注册研究提交）能真正提交作业，其余是只读或草稿。
  • 外部 AI 供应商仍收组织级敏感信息：机构名与研究意图会离边界（TRUST CTL-11）；无 key 的 rule-based 模式能力显著弱于真实模型，适合开发/演示而非复杂意图。
  • 结果解读是 1.7B 小模型：OpenVINO int4、非 TEE；产物恒为「待研究者确认」的草稿，不做统计推断；SSH 隧道断开即 503，不回落外部供应商。
  • AI 通知只有站内信：cp_notification 有未读与待办面板，邮件 / 短信 / Webhook 未接（本仓没有生产邮件通道）。
