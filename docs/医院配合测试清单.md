# MedTrust 医疗可信数据空间 — 医院配合测试清单

> 本文档说明一家医院参与 MedTrust 端到端测试所需的设备、网络、数据与人力准备。
> 基于项目的实际架构（连接器主动外联模式 + 数据不出域守卫 + 国密安全信道）编写。

---

## 一、硬件设备

| 设备 | 规格 | 数量 | 说明 |
|------|------|------|------|
| 应用服务器 | 8 核 CPU / 16 GB RAM / 200 GB SSD | 1 台 | 运行连接器（Connector）节点，承载脱敏数据 + 本地计算 |
| 机密计算节点（可选） | 海光 CSV 或 Intel SGX 机型 | 1 台 | 生产环境硬件 TEE；**测试阶段可用软件模式，不强制** |
| 网络设备 | 可出公网 HTTPS 的出口 | 现有即可 | 连接器只需**主动外联**到控制面 API，不需要开放入站端口 |

> **测试最小配置**：一台普通 x86 服务器（8C / 16G）即可运行完整 RWS + FL 流程。

---

## 二、软件环境

| 软件 | 版本 | 用途 |
|------|------|------|
| Docker | 24+ | 容器化运行连接器节点 |
| Docker Compose | v2+ | 编排连接器及其本地依赖 |
| PostgreSQL **或 SQLite** | 15+ / 3.x | 连接器本地数据库；**测试建议用 SQLite（零运维）** |
| Node.js | 20 LTS | 连接器 NestJS 运行环境 |
| Python | 3.10+ | L4 联邦学习 SecretFlow Agent（仅 L4 场景需要） |

---

## 三、网络要求

| 项目 | 要求 | 说明 |
|------|------|------|
| 出站 HTTPS | ✅ **必须** | 连接器通过 HTTPS 轮询控制面 API 拉取任务 |
| 入站端口 | ❌ **不开** | 架构设计为"主动外联"——医院侧不开放任何入站端口 |
| 到控制面网络 | ✅ 公网可达 | 控制面当前部署在新加坡；需医院网络能出公网 HTTPS |
| 带宽 | ≥ 10 Mbps | 传输的是聚合结果（KB 级），非原始数据，带宽要求极低 |
| DNS | 能解析外网域名 | 需解析 `medtrust-api.fly.dev` 等控制面域名 |

> **防火墙策略**：仅需白名单放行 `*.fly.dev:443` 出站即可。**不需要** VPN、专线、或端口映射。

---

## 四、数据准备

| 事项 | 工作量 | 说明 |
|------|--------|------|
| 数据脱敏 | 1–2 天 | 将待分析的临床数据（患者表、诊断、用药、检验）做脱敏处理。项目提供 `Deidentifier` 组件 |
| FHIR 转换（可选） | 3–5 天 | 若使用标准 FHIR 格式接入，需将院内数据映射到 FHIR Schema；**测试可用 CSV 直接导入** |
| 数据导入脚本 | 0.5 天 | 将脱敏数据写入连接器本地 SQLite，项目提供 `ingest` 命令行 |
| 确认数据范围 | 沟通 | 确认参与计算的队列定义（如：CKD 患者、随访数据时间范围等） |

> **测试阶段**：可用项目自带的 Synthea 合成数据（已内置华山 / 瑞金各 100+ 模拟患者），无需真实数据即可完成全流程联调。

## 五、人员配合

| 角色 | 投入 | 职责 |
|------|------|------|
| IT 工程师 | 1–2 天 | 部署连接器容器、配置网络白名单、确认服务器正常运行 |
| 临床数据分析师 | 2–4 小时 | 确认数据范围、配合脱敏规则审核、验证计算结果合理性 |
| 信息科（可选） | 4 小时 | 协调数据库只读账号、确认 HIS / EMR 视图范围（仅 HIS 对接场景需要） |

## 六、部署与对接时序

```
Day 1 ─ IT 部署连接器 + 网络就绪
  ├─ 服务器就绪
  ├─ Docker 启动连接器容器 → health 检查通过
  └─ 出站 HTTPS 到 medtrust-api.fly.dev 通

Day 2 ─ 数据准备
  ├─ 脱敏脚本运行（或选用合成数据）
  ├─ 数据导入连接器本地库
  └─ 确认 catalog 数据产品可见

Day 3 ─ 联调测试
  ├─ 控制面创建数字合约
  ├─ 医院审批合约
  ├─ 消费方发起 RWS / FL 任务
  └─ 连接器拉取 → 本地计算 → 回传聚合 → 验证结果
```

---

## 七、医院不需要做的

| 项目 | 不需要的原因 |
|------|------------|
| 不需要开放入站端口 | 连接器是主动外联模式，无需 VPN / 专线 |
| 不需要部署区块链节点 | 存证由控制面统一处理 |
| 不需要安装数据库集群 | 本地 SQLite 即可满足测试需求 |
| 不需要配置负载均衡 | 单个连接器节点足够测试 |
| 不需要采购硬件 TEE | 测试阶段用软件 TEE 模式即可 |
| 不需要提供原始 / 明文数据 | 数据在院内脱敏后入库，原始数据不出 HIS |
| 不需要购买额外域名 / 证书 | 连接器不需要公网域名或 TLS 证书 |

---

## 八、关键风险点

1. **控制面 API 域名变更**：当前 `medtrust-api.fly.dev` 为演示环境。正式测试时切换为生产地址，需同步修改连接器 `CONTROL_PLANE_URL` 配置

2. **数据编码差异**：若院内数据的诊断编码（ICD 版本）、用药编码（ATC 等）与测试合成数据不一致，需调整特征映射脚本

3. **出口白名单审批——最常见瓶颈**：部分医院信息科需要 **1–2 周** 完成防火墙策略变更，建议尽早启动网络开通流程

4. **机密计算承诺声明**：若使用软件 TEE 模式测试，结果**不能**对医院声称"硬件级机密计算"，需在所有沟通中标注 `software-isolation` 模式
